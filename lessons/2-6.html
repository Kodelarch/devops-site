О чём урок

ℹ️Зачем это нужно

SQL — язык, на котором ты «разговариваешь» с базой данных: просишь показать, отфильтровать, отсортировать нужные строки. Почти любой backend, аналитика или дашборд рано или поздно упирается в SQL-запрос — это не опция, а базовый навык наравне с самим программированием.

📘Словарик на будущее
  • Таблица — структура данных из строк (записей) и столбцов (полей), как лист Excel с фиксированными колонками.
  • Первичный ключ (Primary Key) — столбец (или набор столбцов), уникально идентифицирующий строку в таблице; в наших таблицах это всегда id.
  • Внешний ключ (Foreign Key) — столбец, ссылающийся на первичный ключ другой таблицы — так таблицы связываются друг с другом.
  • Запрос (query) — инструкция, которая просит базу данных вернуть (или изменить) какие-то данные.
  • Подзапрос (subquery) — запрос, вложенный внутрь другого запроса.
// шаг 2/21 · теория · ~1 мин

Учебная база для всех SQL-уроков

Все SQL-уроки используют одну и ту же учебную базу — маркетплейс электроники, где на одной площадке торгуют несколько магазинов. Схема и тестовые данные лежат в файле _assets/sql/shop.sql: создай базу командой createdb shop и загрузи их через psql -d shop -f shop.sql, тогда любой пример из уроков можно выполнить самой.

  • store (магазины на площадке) — id, name, rating (0–5).
  • customer (покупатели) — id, name, age, city, premium (есть ли платная подписка).
  • product (товары конкретного магазина) — id, store_id → store, title, price, stock (остаток на складе).
  • store_visit (журнал просмотров витрины магазина) — id, customer_id → customer, store_id → store, visit_date.
  • purchase (журнал покупок) — id, customer_id → customer, product_id → product, purchase_date.
💡Важная деталь

Просмотр витрины и покупка — разные, не связанные напрямую события. Покупатель может открыть магазин, посмотреть товары и ничего не купить, а купить в другой день по прямой ссылке из рассылки, вообще не заходя на витрину. Это нормальная «неидеальность» реальных данных: события пишутся в разные таблицы разными частями системы.

SELECT и WHERE — первый запрос

Аналогия: SELECT — это «покажи мне колонки X и Y», а WHERE — «но только те строки, где выполняется условие». Как попросить официанта показать меню, но только вегетарианские блюда.

SELECT name, age
FROM customer
WHERE city = 'Казань';

SELECT name, age — какие столбцы нужны в результате. FROM customer — из какой таблицы. WHERE city = 'Казань' — фильтр по значению столбца.

Важная деталь, которая часто путает новичков: писать запрос принято именно в порядке SELECT → FROM → WHERE, но реально выполняется он в другом порядке: сначала база смотрит, из какой таблицы вообще брать данные (FROM), затем отфильтровывает строки по условию (WHERE), и только в самом конце решает, какие именно столбцы показать в результате (SELECT). Из-за этого, например, в WHERE нельзя сослаться на псевдоним столбца, придуманный в SELECT этого же запроса — на момент выполнения WHERE этот псевдоним ещё просто не существует.

Полный порядок выполнения стоит запомнить сразу — он объясняет сразу несколько правил, которые иначе выглядят произволом: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Отсюда же следует и разница между WHERE и HAVING (2.9 Агрегация): первый отбрасывает строки до группировки, второй — целые группы после неё.

// шаг 4/21 · теория · ~1 мин

Сортировка результата: ORDER BY

Аналогия: ORDER BY — как попросить библиотекаря выдать книги не как попало, а по алфавиту.

SELECT name, age
FROM customer
WHERE city = 'Казань' AND premium
ORDER BY name;

AND комбинирует несколько условий — обе части должны быть истинны одновременно. premium — логический столбец, поэтому его можно писать в условии как есть, без = true. По умолчанию ORDER BY сортирует по возрастанию (ASC); чтобы отсортировать по убыванию, добавляют DESC.

// шаг 5/21 · теория · ~1 мин

Операторы сравнения и BETWEEN

Аналогия: «рейтинг от 3.5 до 5» можно сказать двумя способами — либо явно «не меньше 3.5 и не больше 5», либо одним словом «между 3.5 и 5». Смысл одинаковый, слова разные.

-- через операторы сравнения
SELECT name, rating
FROM store
WHERE rating >= 3.5 AND rating <= 5
ORDER BY rating;

-- то же самое через BETWEEN
SELECT name, rating
FROM store
WHERE rating BETWEEN 3.5 AND 5
ORDER BY rating;

BETWEEN a AND b включает обе границы (это как >= a AND <= b), а не «строго между».

// шаг 6/21 · теория · ~1 мин

Уникальные значения: DISTINCT

Аналогия: если покупатель несколько раз открывал один и тот же магазин, его всё равно нужно посчитать как одного посетителя, а не несколько раз — как список гостей на вечеринке без дублей.

SELECT DISTINCT customer_id
FROM store_visit
WHERE visit_date BETWEEN '2026-03-02' AND '2026-03-05'
   OR store_id = 2
ORDER BY customer_id DESC;

DISTINCT убирает повторяющиеся строки результата — ровно тот же смысл, что и set() в Python (см. урок 2.1). OR — «выполнено хотя бы одно из условий», в отличие от AND.

// шаг 7/21 · теория · ~1 мин

Вычисляемый столбец из текста и данных

Аналогия: вместо того чтобы отдавать голые значения по отдельности, можно попросить базу «собрать» их в одну готовую фразу — как автоматическая подпись к фотографии.

SELECT name || ', ' || age || ' лет, город ''' || city || '''' AS customer_card
FROM customer
ORDER BY customer_card;

|| — оператор конкатенации (склеивания) строк в SQL, аналог + для строк в Python. Получится строка вида Анна, 27 лет, город 'Москва'. Одинарная кавычка внутри строки экранируется удвоением ('') — поэтому в конце примера видно '''': это строка, состоящая из одной кавычки. У покупателей без города или возраста результат окажется пустым — почему, разобрано в §11.

// шаг 8/21 · теория · ~1 мин

Подзапрос в SELECT

Аналогия: подзапрос в SELECT — как записка внутри записки: сначала находишь ответ на маленький вопрос («как зовут этого человека?»), а потом подставляешь его в основной ответ.

SELECT
    (SELECT c.name FROM customer c WHERE c.id = pu.customer_id) AS customer_name
FROM purchase pu
WHERE pu.product_id IN (9, 14)       -- сетевые кабели из двух магазинов
  AND pu.purchase_date >= '2026-03-04';

Подзапрос выполняется отдельно для каждой строки основного запроса и подставляет результат как обычное значение столбца. IN (9, 14) — короткая запись для product_id = 9 OR product_id = 14. Тот же результат обычно получают через соединение таблиц (2.7 Соединения) — для больших таблиц это быстрее, чем подзапрос на каждую строку.

// шаг 9/21 · теория · ~1 мин

Логическое условие как отдельный столбец

Аналогия: вместо того чтобы просто отфильтровать строки, можно оставить их все, но добавить колонку-пометку «да/нет» — как галочка в чек-листе рядом с каждым пунктом, а не удаление невыполненных пунктов.

SELECT
    (SELECT c.name FROM customer c WHERE c.id = pu.customer_id) AS customer_name,
    (SELECT c.name FROM customer c WHERE c.id = pu.customer_id) = 'Анна' AS is_anna
FROM purchase pu
WHERE pu.product_id = 9 OR pu.product_id = 14;

Сравнение (= 'Анна') само по себе возвращает true/false — в PostgreSQL это можно использовать прямо как значение столбца, без обёртки в CASE WHEN.

// шаг 10/21 · теория · ~1 мин

Множественные условия: CASE WHEN

Аналогия: CASE WHEN — это if/elif/else внутри SQL-запроса (см. урок 2.1, раздел 4), только результат не печатается, а становится значением нового столбца.

SELECT
    id,
    name,
    CASE
        WHEN age < 18 THEN 'подросток'
        WHEN age < 30 THEN 'молодой'
        WHEN age < 60 THEN 'взрослый'
        ELSE 'старший или неизвестно'
    END AS age_group
FROM customer
ORDER BY age_group;

Условия проверяются по порядку сверху вниз, срабатывает первое подходящее — совсем как if/elif/else в Python. Поэтому во второй ветке достаточно age < 30: до неё дойдут только те, кому уже не меньше 18. Покупатель без возраста (NULL) не подойдёт ни под одно условие и попадёт в ELSE — об этом в §11.

// шаг 11/21 · теория · ~1 мин

Чётные и нечётные значения

Аналогия: тот же остаток от деления, что уже встречался в уроке 2.1 (% в Python) — только в SQL он называется MOD или обозначается тем же символом %.

SELECT *
FROM purchase
WHERE id % 2 = 0
ORDER BY id;

id % 2 = 0 — «остаток от деления id на 2 равен нулю», то есть число чётное. SELECT * означает «все столбцы таблицы», без перечисления по именам.

// шаг 12/21 · теория · ~1 мин

Подзапрос в FROM (производная таблица)

Аналогия: подзапрос в FROM — это отчёт, построенный не по исходным данным напрямую, а по уже готовому промежуточному отчёту — как посчитать средний балл по оценкам, которые сначала сам отфильтровал.

SELECT
    (SELECT c.name FROM customer c WHERE c.id = sv.customer_id) AS customer_name,
    (SELECT s.name FROM store s WHERE s.id = sv.store_id) AS store_name
FROM (
    SELECT customer_id, store_id
    FROM store_visit
    WHERE visit_date BETWEEN '2026-03-03' AND '2026-03-06'
) AS sv
ORDER BY customer_name ASC, store_name DESC;

Подзапрос в FROM обязательно должен иметь алиас (здесь — AS sv) — база данных должна как-то называть эту временную «виртуальную таблицу», чтобы можно было обращаться к её столбцам дальше в запросе.

// шаг 13/21 · теория · ~4 мин

NULL — не значение, а его отсутствие

Аналогия: в анкете поле «телефон» может быть пустым. Это не значит, что телефон равен пустой строке или нулю — это значит, что телефон неизвестен. Сравнивать неизвестное с чем-либо бессмысленно, даже с другим неизвестным.

Тема, которую в учебных базах обходят стороной, а в реальных она даёт больше всего тихих ошибок. И самый частый вопрос на собеседовании по SQL.

-- ✘ вернёт ноль строк, но НЕ выдаст ошибку
SELECT * FROM customer WHERE city = NULL;
SELECT * FROM customer WHERE city != NULL;

-- ✔ единственно верный способ
SELECT * FROM customer WHERE city IS NULL;
SELECT * FROM customer WHERE city IS NOT NULL;

Причина в трёхзначной логике: кроме true и false в SQL есть третье состояние — unknown. Любое сравнение с NULL даёт именно его, включая NULL = NULL. А в WHERE строка попадает в результат, только если условие истинно; unknown отбрасывается наравне с false. Отсюда и получается пустая выборка вместо ошибки — запрос «работает», просто молча возвращает не то.

Тот же эффект в арифметике и склейке строк:

SELECT 100 + NULL;              -- NULL, а не 100
SELECT 'Заказ №' || NULL;       -- NULL — пропадает вся строка целиком

Именно так в отчётах появляются пустые ячейки там, где ожидался текст: одно неизвестное поле обнуляет всю собранную строку.

Как с этим работать:

-- подставить значение по умолчанию
SELECT name, COALESCE(city, 'адрес не указан') AS city
FROM customer;

-- превратить конкретное значение обратно в NULL
SELECT NULLIF(rating, 0) FROM store;

COALESCE возвращает первый не-NULL аргумент из перечисленных — прямой аналог ${VAR:-default} из bash (1.3 Bash, §9) и .get(key, default) из Python.

🛑Ловушка NOT IN — почти гарантированный вопрос на собеседовании
SELECT * FROM customer
WHERE id NOT IN (SELECT customer_id FROM store_visit);   -- ✘ опасно

Если подзапрос вернёт хотя бы один NULL, весь запрос вернёт ноль строк. Всегда. Логика такая: id NOT IN (1, 2, NULL) разворачивается в id != 1 AND id != 2 AND id != NULL, а последнее условие даёт unknown, и всё выражение перестаёт быть истинным для любой строки.

С IN этой проблемы нет — там достаточно одного совпадения. Поэтому запрос с IN работает, а его «зеркальный» вариант с NOT IN внезапно даёт пустоту, и найти причину без знания этой особенности почти невозможно.

Безопасные варианты: NOT EXISTS вместо NOT IN, либо явное WHERE customer_id IS NOT NULL внутри подзапроса.

Ещё две особенности, которые всплывают на практике: при сортировке PostgreSQL по умолчанию ставит NULL в конец при ASC и в начало при DESC (управляется через NULLS FIRST / NULLS LAST), а COUNT(столбец) не считает строки с NULL, в отличие от COUNT(*) — подробнее в 2.9 Агрегация.

// шаг 14/21 · теория · ~1 мин

Поиск по шаблону: LIKE

Аналогия: фильтр «начинается на» в поиске по контактам.

SELECT name FROM store    WHERE name LIKE 'Умн%';       -- начинается с «Умн»
SELECT title FROM product WHERE title LIKE '%кабель%';  -- содержит «кабель»
SELECT name FROM customer  WHERE name LIKE '_нна';      -- ровно один символ, затем нна
SELECT title FROM product WHERE title ILIKE '%КАБЕЛЬ%';  -- без учёта регистра (PostgreSQL)

Символ % заменяет любое количество любых символов (включая ноль), _ — ровно один символ. ILIKE — расширение PostgreSQL, то же самое без учёта регистра; в других СУБД пишут LOWER(name) LIKE LOWER('...').

⚠️Почему LIKE '%текст%' тормозит

Шаблон, начинающийся с %, не может воспользоваться обычным индексом: база не знает, с чего начинается искомое, и вынуждена просмотреть все строки целиком. На таблице в миллион записей это заметно. Шаблон вида 'Умн%' (без ведущего %) индекс использовать может — разница принципиальная. Подробнее про индексы — в 2.8 Индексы, а для полноценного текстового поиска в PostgreSQL есть отдельный механизм.

// шаг 15/21 · теория · ~1 мин

LIMIT и OFFSET

Аналогия: «покажи первые десять» и «а теперь следующие десять» — обычная постраничная выдача.

SELECT name, rating FROM store ORDER BY rating DESC LIMIT 5;
SELECT name, rating FROM store ORDER BY rating DESC LIMIT 5 OFFSET 10;

LIMIT ограничивает число строк, OFFSET пропускает первые N. Вместе они дают постраничный вывод, к которому сводится почти любой список в интерфейсе.

Две детали, о которых стоит знать сразу. Во-первых, LIMIT без ORDER BY не имеет смысла: база не обязана возвращать строки в каком-либо порядке, поэтому «первые пять» без сортировки могут оказаться разными при каждом запуске. Во-вторых, большие OFFSET работают медленно: чтобы пропустить 100 000 строк, база их всё равно прочитает. Для глубокой пагинации используют другой приём — фильтр по последнему увиденному значению (WHERE id > последний_id LIMIT 20).

// шаг 16/21 · теория · ~3 мин

psql: как зайти в базу и осмотреться

Аналогия: прежде чем писать запросы, надо уметь открыть дверь и понять, что вообще лежит внутри.

Для DevOps это едва ли не более частая задача, чем написание сложных запросов: подключиться к незнакомой базе, посмотреть, какие есть таблицы, проверить размер, найти застрявший запрос.

psql -h localhost -U postgres -d shop         # подключиться
psql "postgresql://user:pass@host:5432/dbname"    # то же одной строкой подключения

Служебные команды psql начинаются с обратного слеша и к SQL отношения не имеют:

\l              список баз
\c shop      переключиться на базу
\dt             список таблиц
\d customer       структура таблицы: столбцы, типы, индексы, ключи
\du             список пользователей и их прав
\dt+            таблицы с размерами
\x              переключить вывод в вертикальный вид — спасение для широких таблиц
\timing         показывать время выполнения каждого запроса
\q              выйти

Запустить запрос из скрипта, не входя в интерактивный режим:

psql -d shop -c "SELECT count(*) FROM customer;"       # одна команда
psql -d shop -f migration.sql                          # выполнить файл
psql -d shop -At -c "SELECT count(*) FROM customer;"      # только значение, без рамок

Флаги -A (без выравнивания) и -t (без заголовков) дают чистое значение, которое удобно положить в переменную bash — так пишут проверки состояния базы для мониторинга.

Пара запросов, которые пригодятся в эксплуатации сразу:

SELECT pg_size_pretty(pg_database_size('shop'));    -- сколько весит база
SELECT count(*) FROM pg_stat_activity;                   -- сколько сейчас соединений
SELECT pid, state, query_start, query
FROM pg_stat_activity
WHERE state != 'idle' ORDER BY query_start;               -- что выполняется прямо сейчас

Последний — первое, что смотрят, когда «база тормозит». Подробнее про диагностику и блокировки — в 2.10 Транзакции.

⚠️SELECT * — не для рабочего кода

В консоли SELECT * удобен. В коде приложения — нет: он тянет лишние данные по сети, ломается при добавлении столбца в таблицу и мешает базе использовать покрывающие индексы. Правило простое: в консоли можно, в коде перечисляй столбцы явно.

// шаг 17/21 · итоги · ~1 мин

Если запомнить только главное

  • Порядок частей запроса — SELECT → FROM → WHERE → ORDER BY, даже если реально база выполняет их в другом порядке внутри.
  • BETWEEN a AND b включает обе границы.
  • DISTINCT убирает дубликаты строк результата — как set() в Python.
  • Подзапрос можно поставить и в SELECT (вычислить одно значение), и в FROM (построить временную таблицу) — у подзапроса в FROM обязателен алиас.
  • CASE WHEN ... THEN ... ELSE ... END — это if/elif/else языка SQL.
  • Порядок выполнения: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Псевдоним из SELECT доступен в ORDER BY, но не в WHERE.
  • NULL — отсутствие значения, а не значение. Только IS NULL / IS NOT NULL; = NULL молча вернёт пустоту. COALESCE подставляет значение по умолчанию.
  • NOT IN с NULL в списке всегда возвращает ноль строк — используй NOT EXISTS.
  • LIKE '%текст%' не может использовать индекс; LIKE 'текст%' — может.
  • LIMIT без ORDER BY не гарантирует ничего; большие OFFSET медленные.
  • psql: \dt таблицы, \d имя структура, \x вертикальный вывод, -At -c для скриптов. pg_stat_activity — что выполняется прямо сейчас.
  • SELECT * — только в консоли, в коде перечисляй столбцы.

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

  • Задание 1 (PostgreSQL в Docker с учебной базой) — база для приложения в P1: каркас shop-api использует ту же схему.

Задание 1 — база в Docker

Подними PostgreSQL в контейнере с томом для данных, создай базу shop и загрузи в неё _assets/sql/shop.sql.
Проверка: docker compose down && docker compose up -d — данные на месте; \dt в psql показывает пять таблиц.

Задание 2 — базовые выборки

Напиши запросы: покупатели с подпиской старше 25 лет по алфавиту; магазины с рейтингом от 4 до 5 через BETWEEN; уникальные идентификаторы покупателей, открывавших витрины с 3 по 6 марта; товары, в названии которых есть «кабель», дешевле 500 рублей.
Проверка: каждый запрос проверен на ожидаемое число строк, сортировка явная.

Задание 3 — CASE и вычисляемые столбцы

Выведи покупателей с колонкой segment: «подписчик» для premium, «постоянный» для тех, у кого больше одной покупки (через подзапрос), «новичок» для остальных; и строку вида «Анна из Москвы, 27 лет».
Проверка: покупатели без города или возраста не теряются и не дают пустых строк — используй COALESCE.

Задание 4 — ловушки NULL

В базе уже есть покупатель без города. Сравни результаты WHERE city = NULL, WHERE city IS NULL и WHERE city <> 'Москва'.
Проверка: объясняешь, почему первый запрос пуст, а третий не включает покупателя без города.

Задание 5 — постраничный вывод

Выведи каталог товаров по 5 позиций на страницу, третья страница, с сортировкой по цене и названию.
Проверка: при одинаковых ценах порядок стабилен между запусками.
