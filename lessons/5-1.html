О чём урок

ℹ️Зачем это нужно

Docker Swarm (урок 4.1) — простой оркестратор «из коробки». Kubernetes — куда более сложный и мощный инструмент, ставший фактическим стандартом индустрии для крупных приложений с множеством сервисов. Освоить его базовые понятия — pod, service, деплой через манифесты — необходимо почти для любой DevOps-вакансии.

📘Словарик на будущее
  • Манифест — YAML-файл, декларативно описывающий, каким должно быть состояние объекта в кластере (не «что сделать», а «как должно быть»).
  • Pod — минимальная единица развёртывания в Kubernetes: один или несколько тесно связанных контейнеров, работающих вместе как единое целое.
  • Service — стабильная точка доступа к набору подов, которые сами по себе могут пересоздаваться и менять IP.
  • ConfigMap — объект для хранения несекретной конфигурации отдельно от кода приложения.
  • Secret — объект для хранения чувствительных данных (пароли, ключи), закодированных в base64.
// шаг 2/21 · теория · ~1 мин

Kubernetes vs Docker Swarm

Аналогия: если Docker Swarm — небольшая семейная мастерская, где прораб лично знает каждого работника, то Kubernetes — огромный завод с отдельными цехами, конвейерами и системой учёта для тысяч единиц оборудования.

Docker Swarm проще в освоении и достаточен для несложных случаев. Kubernetes сложнее, но предназначен для куда более серьёзных нагрузок: большого количества сервисов, сложного взаимодействия между ними, тонкой настройки распределения ресурсов. Kubernetes также включает больше встроенных инструментов «из коробки» — например, собственную систему мониторинга состояния кластера.

// шаг 3/21 · теория · ~1 мин

minikube: Kubernetes на одной машине для обучения

Аналогия: minikube — как тренажёр-симулятор настоящего самолёта: полноценная кабина со всеми приборами, но помещается в одну комнату, а не требует настоящего аэродрома.

minikube start --memory=4096
minikube status

minikube разворачивает полноценный (хотя и однонодовый) кластер Kubernetes прямо на локальной машине — этого достаточно, чтобы изучить все базовые понятия и команды, не имея доступа к настоящему многоузловому production-кластеру.

// шаг 4/21 · теория · ~1 мин

Манифест: декларативное описание желаемого состояния

Аналогия: манифест — не пошаговая инструкция «сначала сделай это, потом то», а техническое задание архитектору: «хочу дом с тремя комнатами и окнами на юг» — как именно это будет построено, решает уже сам Kubernetes.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-api
spec:
  replicas: 1
  selector:
    matchLabels:
      app: shop-api
  template:
    metadata:
      labels:
        app: shop-api
    spec:
      containers:
        - name: shop-api
          image: username/shop-api:1.0
          ports:
            - containerPort: 8080

kubectl apply -f shop-api-deployment.yaml

kubectl apply не «выполняет команду однократно», а сообщает Kubernetes желаемое состояние — Kubernetes сам сравнивает его с текущим состоянием кластера и делает всё необходимое, чтобы привести одно к другому (создать под, если его ещё нет; ничего не делать, если уже всё так).

// шаг 5/21 · теория · ~1 мин

Pod — минимальная единица развёртывания

Аналогия: pod — не то же самое, что контейнер: это, скорее, «стручок гороха» — небольшая капсула, внутри которой может быть один основной контейнер (чаще всего) или несколько тесно связанных, живущих и умирающих вместе.

kubectl get pods
kubectl describe pod shop-api-7d4b8f9c-x2n4k
kubectl logs shop-api-7d4b8f9c-x2n4k

В большинстве простых случаев pod содержит ровно один контейнер, и в быту про них часто говорят как о синонимах — но технически именно pod, а не контейнер, является минимальной управляемой единицей в Kubernetes: у него общий сетевой адрес и общее хранилище для всех контейнеров внутри.

// шаг 6/21 · теория · ~1 мин

Service — стабильный адрес для подов

Аналогия: поды — как временные сотрудники, которых может уволить и нанять заново система (с новым внутренним ID каждый раз), а Service — это постоянный номер горячей линии компании, который не меняется, даже если сотрудник, отвечающий на звонки, сменился.

apiVersion: v1
kind: Service
metadata:
  name: shop-api
spec:
  selector:
    app: shop-api
  ports:
    - port: 8080
      targetPort: 8080

Поды могут пересоздаваться (при сбое, обновлении, масштабировании) и каждый раз получать новый внутренний IP — обращаться напрямую к поду ненадёжно. Service находит подходящие поды по selector (совпадению меток) и предоставляет для них общий стабильный адрес, который не меняется.

// шаг 7/21 · теория · ~2 мин

ConfigMap: конфигурация отдельно от кода

Аналогия: ConfigMap — как отдельная записка с адресом на холодильнике, а не адрес, вытатуированный прямо на теле курьера — поменять адрес намного проще, чем переделывать самого курьера.

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: "postgres-service"
  DB_PORT: "5432"

containers:
  - name: shop-api
    envFrom:
      - configMapRef:
          name: app-config

ConfigMap хранит несекретные значения конфигурации (хосты, порты, флаги) отдельно от самого образа приложения — поменять адрес базы данных можно, обновив только ConfigMap, без пересборки образа. envFrom в манифесте контейнера говорит «забери все пары ключ-значение из указанного источника и сделай их переменными окружения внутри контейнера»; configMapRef: name: app-config указывает, из какого именно ConfigMap их брать — в результате внутри контейнера появятся переменные DB_HOST и DB_PORT, как если бы их прописали вручную при запуске.

// шаг 8/21 · теория · ~1 мин

Secret: чувствительные данные

Аналогия: Secret — это конверт с надписью «конфиденциально», но не запертый сейф: сам по себе base64 — это не шифрование, а просто другой способ записи тех же символов, который любой может «открыть» одной командой.

kubectl create secret generic db-secret \
  --from-literal=password=supersecret

kubectl get secret db-secret -o jsonpath='{.data.password}' | base64 --decode

Значения внутри Secret кодируются в base64 — это защищает не от намеренного взлома, а скорее от случайного отображения пароля в логах или интерфейсе «как есть». Настоящая защита секретов в реальных кластерах обеспечивается правами доступа (RBAC) и шифрованием на уровне etcd, а не самим base64.

// шаг 9/21 · теория · ~1 мин

kubectl: основные команды

Аналогия: kubectl — пульт управления с несколькими режимами: «применить план», «посмотреть список», «спросить подробности», «почитать журнал происшествий».

kubectl apply -f manifest.yaml       # применить манифест
kubectl get pods                      # список объектов (можно get service, get deployment...)
kubectl describe pod <имя>            # подробная информация об объекте
kubectl logs <имя_пода>               # логи контейнера внутри пода

get даёт краткую сводку, describe — подробности вплоть до истории событий (почему под не запустился, если что-то пошло не так), logs — прямой доступ к выводу самого приложения внутри пода.

// шаг 10/21 · теория · ~1 мин

Доступ и визуализация: minikube service, minikube dashboard

Аналогия: если кластер — это закрытое здание завода, minikube service — временный туннель прямо к конкретному цеху, а minikube dashboard — застеклённая смотровая галерея, откуда видно вообще всё производство сразу.

minikube service shop-api --url
minikube dashboard

minikube service создаёт временный туннель с локальной машины до конкретного Service внутри кластера — без этого сервисы Kubernetes по умолчанию недоступны снаружи. minikube dashboard открывает встроенный веб-интерфейс с визуализацией всех объектов кластера — подов, деплойментов, логов, конфигураций — без запоминания команд kubectl для каждого действия.

// шаг 11/21 · теория · ~2 мин

Стратегии обновления: recreate и rolling

Аналогия: recreate — как полностью закрыть магазин на ремонт, а потом открыть заново — быстро по шагам, но с полным простоем; rolling — как ремонтировать по одному прилавку за раз, не закрывая весь магазин целиком, но сам процесс растягивается дольше.

spec:
  strategy:
    type: Recreate   # или RollingUpdate

При Recreate Kubernetes сначала полностью останавливает все старые поды и только потом запускает новые — приложение на время обновления недоступно, зато переход происходит быстро и предсказуемо. При RollingUpdate (по умолчанию) старые поды заменяются новыми постепенно, по одному — приложение остаётся доступным всё время обновления, но само обновление занимает больше времени, так как одновременно должны существовать и старая, и новая версия.

Отдельно стоит знать про иерархию: Deployment управляет ReplicaSet, а тот — подами. При обновлении создаётся новый ReplicaSet, старый остаётся с нулём реплик — именно поэтому возможен мгновенный откат:

kubectl rollout status deployment/shop-api    # следить за ходом обновления
kubectl rollout history deployment/shop-api    # список версий
kubectl rollout undo deployment/shop-api        # откатиться на предыдущую

Это та самая «кнопка отката» из 3.2 CI-CD, §15, только встроенная в оркестратор.

// шаг 12/21 · теория · ~2 мин

Пробы: liveness, readiness, startup


Аналогия: врач задаёт три разных вопроса — «жив ли пациент», «может ли он работать» и «закончился ли наркоз». Ответы на них означают разные действия, и путать их нельзя.

Без проб Kubernetes считает под здоровым, пока процесс внутри не умер. Приложение может зависнуть, потерять связь с базой, отвечать ошибками на всё подряд — трафик всё равно будет идти. Пробы дают кластеру возможность это понять.

containers:
  - name: app
    livenessProbe:
      httpGet: { path: /healthz, port: 8000 }
      initialDelaySeconds: 10
      periodSeconds: 10
      failureThreshold: 3

    readinessProbe:
      httpGet: { path: /readyz, port: 8000 }
      periodSeconds: 5

    startupProbe:
      httpGet: { path: /healthz, port: 8000 }
      failureThreshold: 30
      periodSeconds: 5        # даёт до 150 секунд на запуск

Вот те самые эндпоинты из 2.5 Бэкенд-сервис, §11 — теперь видно, кто их читает.

liveness отвечает на вопрос «процесс не завис». Не прошла — под перезапускают. Поэтому проверять в ней что-либо внешнее нельзя: если база ушла на обслуживание, перезапуск приложения ничем не поможет.

readiness отвечает «можно ли слать трафик». Не прошла — под убирают из Service, но не трогают. Вот здесь и проверяют зависимости: база, очередь, кеш. Как только всё вернётся, под сам вернётся в ротацию.

startup нужна для медленно стартующих приложений. Пока она не прошла, остальные пробы не выполняются вовсе. Без неё liveness с коротким интервалом убьёт под, который просто не успел запуститься за отведённое время, и приложение уйдёт в бесконечный цикл перезапусков.

🛑Проверка базы в liveness — типовая авария

База ушла на десять минут обслуживания. Kubernetes видит, что liveness не проходит, убивает под, поднимает новый — тот тоже не может достучаться до базы, и цикл повторяется, пока база не вернётся. При этом настоящей проблемы с приложением не было ни секунды.

Правило: liveness проверяет только себя и почти всегда отвечает успешно; readiness проверяет зависимости и может честно сказать «сейчас не готов». Это ровно то различие, что разбиралось в 2.5 Бэкенд-сервис, §11, — и в Kubernetes цена ошибки становится наглядной.

// шаг 13/21 · теория · ~2 мин

Requests и limits

Аналогия: requests — бронь столика, limits — потолок счёта. По брони планировщик решает, поместишься ли ты в ресторан вообще.

    resources:
      requests:
        memory: "256Mi"
        cpu: "250m"
      limits:
        memory: "512Mi"
        cpu: "1000m"

requests — гарантированный минимум, по которому планировщик выбирает узел. Если на всех узлах свободно меньше, чем запрошено, под останется в состоянии Pending и не запустится нигде.

limits — потолок. Превышение по памяти означает убийство контейнера с состоянием OOMKilled; превышение по процессору — просто замедление, ничего не падает. Асимметрия та же, что разбиралась в 4.1 Compose и Swarm, §11.

Единицы стоит запомнить: 250m — это 0.25 ядра («milliCPU»), 256Mi — мебибайты (не мегабайты, разница около 5%).

Из соотношения requests и limits выводится класс обслуживания (QoS), по которому Kubernetes решает, кого убивать первым при нехватке памяти на узле:

Класс Когда Кого убьют
Guaranteed requests равны limits последним
Burstable requests меньше limits вторым
BestEffort ничего не указано первым

Отсюда практический вывод: под без указанных ресурсов не просто рискует съесть всё — он ещё и первый кандидат на вытеснение. Для важных сервисов requests и limits ставят равными.

⚠️Как подбирать значения

Не угадыванием: посмотреть фактическое потребление под нагрузкой через метрики из 4.5 Наблюдаемость и взять пиковое значение с запасом. Слишком низкий лимит памяти даёт регулярные OOMKilled под нагрузкой; слишком высокие requests не дают поду разместиться на узле. И то и другое видно в метриках, а не в интуиции.

// шаг 14/21 · теория · ~2 мин

Как трафик попадает внутрь: типы Service и Ingress

Аналогия: ClusterIP — внутренний добавочный номер, NodePort — прямой городской номер конкретного здания, LoadBalancer — единый номер call-центра, Ingress — секретарь, который по названию отдела соединяет с нужным добавочным.

В §5 разобран Service в варианте по умолчанию. Их четыре типа:

Тип Что даёт Где применяется
ClusterIP адрес только внутри кластера по умолчанию, для связи сервисов между собой
NodePort порт на каждом узле кластера отладка, простые случаи
LoadBalancer внешний балансировщик от облака боевой доступ снаружи, по одному на сервис
ExternalName псевдоним для внешнего адреса обращение к сервису вне кластера

Проблема с LoadBalancer в том, что облако создаёт (и тарифицирует) отдельный балансировщик на каждый такой сервис. Для десятка сервисов это десяток балансировщиков и десяток внешних адресов.

Ingress решает это: один вход снаружи, маршрутизация внутрь по имени домена и пути.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: main
spec:
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port: { number: 8080 }
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port: { number: 80 }
  tls:
    - hosts: [shop.example.com]
      secretName: shop-tls

По сути это тот же nginx как reverse proxy из 1.2 Сети, §11, только описанный манифестом. Сам Ingress — лишь правила; выполняет их Ingress-контроллер (Traefik, HAProxy, NGINX Gateway Fabric и другие; долго самым популярным был ingress-nginx, но с марта 2026 года он больше не поддерживается), который надо установить в кластер отдельно. Забыть про это — типовая причина того, что манифест применился, а ничего не работает.

Ingress же обычно завершает TLS, а в связке с cert-manager сертификаты выпускаются и продлеваются автоматически — окончательный ответ на вопрос из 1.2 Сети, §3.

// шаг 15/21 · теория · ~2 мин

Namespace и организация кластера

Аналогия: папки в одном файловом хранилище. Ничего не мешает свалить всё в корень, пока файлов десять.

kubectl create namespace staging
kubectl apply -f app.yaml -n staging
kubectl get pods -n staging
kubectl config set-context --current --namespace=staging   # чтобы не писать -n каждый раз

Пространства имён разделяют объекты внутри кластера: тестовое и предпродакшн окружение, команды, инфраструктурные компоненты. Имена объектов уникальны внутри пространства, а не во всём кластере, — можно иметь app в каждом из них.

К пространствам привязываются квоты ресурсов (ResourceQuota), сетевые политики и права доступа (RBAC), поэтому разделение по ним — не косметика, а основа управления.

Обращение к сервису в другом пространстве идёт по полному имени:

имя-сервиса.пространство.svc.cluster.local

Внутри одного пространства достаточно короткого имени — то же самое, что имена сервисов в Compose из 3.1 Docker, §11.

// шаг 16/21 · теория · ~4 мин

Под не работает: порядок разбора


Аналогия: статус в списке подов — как код ошибки на панели прибора: он почти всегда сразу называет причину, если знать расшифровку.

Это то, что просят продемонстрировать на собеседовании чаще всего остального по Kubernetes.

Шаг 1 — посмотреть статус:

kubectl get pods
Статус Причина Куда смотреть
CrashLoopBackOff контейнер стартует и падает по кругу logs --previous
ImagePullBackOff образ не скачивается тег, доступ к реестру
Pending планировщик не нашёл узел requests, ограничения размещения
OOMKilled превышен лимит памяти утечка или заниженный лимит
Running, но 0/1 READY readiness не проходит зависимости приложения
Terminating надолго не завершается по SIGTERM обработка сигнала, terminationGracePeriodSeconds

Шаг 2 — журнал событий, где почти всегда лежит точная причина:

kubectl describe pod <имя>          # события в самом низу вывода
kubectl get events --sort-by=.lastTimestamp

Шаг 3 — логи, в том числе от предыдущего упавшего запуска:

kubectl logs <под>                   # текущий контейнер
kubectl logs <под> --previous         # предыдущая упавшая попытка — ключевое при CrashLoop
kubectl logs -l app=shop-api --tail=50  # по метке, со всех подов сразу

Шаг 4 — зайти внутрь и проверить руками:

kubectl exec -it <под> -- sh
kubectl port-forward <под> 8080:8000       # пробросить порт к себе, минуя Service

port-forward полезен для важной проверки: если через него приложение отвечает, а через Service нет — проблема в selector сервиса или в readiness, а не в самом приложении.

💡Частая причина «манифест применился, ничего не работает»

Метки в selector сервиса не совпадают с метками подов. Kubernetes при этом не выдаёт ошибки — Service просто не находит ни одного пода и никуда не направляет трафик. Проверяется мгновенно:

kubectl get endpoints shop-api     # пусто — значит selector не совпал

Пустой список конечных точек — первое, что стоит смотреть, когда сервис не отвечает.

// шаг 17/21 · итоги · ~1 мин

Если запомнить только главное

  • Манифест — декларативное «как должно быть», а не пошаговая инструкция; kubectl apply сводит текущее состояние к желаемому.
  • Pod — минимальная управляемая единица, не то же самое, что контейнер (хотя чаще всего один под = один контейнер).
  • Service даёт стабильный адрес для подов, которые сами могут пересоздаваться и менять IP.
  • ConfigMap — для несекретной конфигурации, Secret — для чувствительных данных (base64 — не шифрование, а кодирование).
  • kubectl get/describe/logs — три основных способа посмотреть, что происходит в кластере.
  • minikube service пробрасывает временный туннель к сервису, minikube dashboard визуализирует весь кластер.
  • Recreate — быстрое обновление с простоем, RollingUpdate — постепенное обновление без простоя, но дольше. Откат — kubectl rollout undo.
  • Три пробы, три действия: liveness не прошла — под перезапускают, readiness — убирают из Service, startup — даёт время на медленный запуск. Проверять базу в liveness — значит устроить цикл перезапусков.
  • requests определяют, куда планировщик поставит под; limits — потолок. Превышение памяти = OOMKilled, превышение CPU = замедление. Под без ресурсов убивают первым.
  • Типы Service: ClusterIP внутри, NodePort для отладки, LoadBalancer по одному балансировщику на сервис. Ingress — один вход и маршрутизация по домену и пути; требует отдельно установленного контроллера.
  • Пространства имён разделяют объекты и служат точкой привязки квот, прав и сетевых политик.
  • Разбор упавшего пода: статус в get pods → события в describe → logs --previous → exec и port-forward. Пустой get endpoints означает, что selector не совпал с метками подов.

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

💡В портфолио
  • Задания 1–3 — основа приложения в кластере для P3: Deployment с пробами и ресурсами, Service, выкатка и откат.
  • Те же манифесты, превращённые в шаблоны, — начало M4.

Задание 1 — первый Deployment

В minikube или kind разверни приложение Deployment'ом на 3 реплики с Service типа ClusterIP, ConfigMap и Secret.
Проверка: kubectl get pods -o wide — 3 пода в Running; удаление одного пода (kubectl delete pod) через секунды восстанавливает число реплик.

Задание 2 — пробы и ресурсы

Добавь readiness и liveness-пробы на /readyz и /healthz, requests и limits.
Проверка: при сломанной базе поды выходят из Endpoints Service (kubectl get endpoints), но не перезапускаются.

Задание 3 — rolling update и откат

Обнови образ через kubectl set image, затем выкати заведомо битый тег и откати через kubectl rollout undo.
Проверка: во время обновления цикл curl не получает ошибок; битый релиз не убил старые поды, откат восстанавливает работу.

Задание 4 — Ingress

Включи Ingress-контроллер и открой приложение по имени хоста.
Проверка: curl -H "Host: shop.local" http://<ip-ingress> возвращает ответ приложения.

Задание 5 — разбор неработающего пода

Сломай под тремя способами: несуществующий образ, неверная команда, слишком маленький лимит памяти.
Проверка: для каждого случая находишь причину через kubectl describe pod, kubectl logs --previous и kubectl get events, называешь статус (ImagePullBackOff, CrashLoopBackOff, OOMKilled).
