О чём урок

ℹ️Зачем это нужно

Это урок про то, что происходит вокруг самого запроса: как сохранить часто используемый запрос под именем (VIEW), как ускорить его выполнение (индексы) и как защитить данные от ошибок ещё на уровне базы (ограничения). Именно эти три вещи чаще всего спрашивают на собеседованиях после базового SELECT/JOIN.

📘Словарик на будущее
  • Представление (VIEW) — сохранённый запрос, который выглядит как таблица, но не хранит собственных данных.
  • Материализованное представление — то же самое, но с реально сохранёнными (закэшированными) результатами на момент последнего обновления.
  • Индекс — дополнительная структура данных, ускоряющая поиск нужных строк без полного перебора таблицы.
  • Ограничение (constraint) — правило на уровне базы данных, не позволяющее записать в таблицу заведомо некорректные данные.
  • Последовательность (sequence) — отдельный счётчик в базе данных, обычно используемый для автогенерации первичных ключей.
// шаг 2/25 · теория · ~1 мин

VIEW — сохранённый запрос как виртуальная таблица

Аналогия: VIEW — как ярлык на рабочем столе: выглядит как отдельный файл, но на самом деле просто указывает на настоящий файл (или в данном случае — на настоящий запрос к реальным таблицам).

CREATE VIEW v_premium_customers AS
SELECT id, name, city FROM customer WHERE premium;

После создания к v_premium_customers можно обращаться как к обычной таблице (SELECT * FROM v_premium_customers), но физически никаких новых данных не появилось — при каждом обращении база заново выполняет запрос из определения VIEW к настоящей таблице customer.

// шаг 3/25 · теория · ~1 мин

Представления как строительные блоки

Аналогия: если уже есть два готовых узких списка (например, «подписчики» и «покупатели из Казани»), их можно объединить в один общий список — представления так же комбинируются друг с другом, как обычные таблицы.

SELECT name FROM v_premium_customers
UNION
SELECT name FROM v_kazan_customers
ORDER BY name;

Представление можно использовать в FROM, JOIN, UNION — везде, где допустима обычная таблица, потому что для остальной части запроса VIEW неотличим от таблицы.

// шаг 4/25 · теория · ~1 мин

VIEW с генератором данных

Аналогия: если один и тот же «полный список дат» нужен в нескольких разных запросах — логичнее сохранить сам генератор один раз под именем, чем копировать generate_series(...) каждый раз заново.

CREATE VIEW v_generated_dates AS
SELECT gs::date AS generated_date
FROM generate_series('2026-03-01'::date, '2026-03-31'::date, '1 day') AS gs;

Теперь вместо повторения generate_series в каждом запросе на поиск пропущенных дат достаточно написать FROM v_generated_dates (см. урок 2.7, раздел 8).

// шаг 5/25 · теория · ~1 мин

Материализованное представление — VIEW, которое реально хранит данные

Аналогия: обычный VIEW — это как спросить у справочной каждый раз заново, а материализованное представление — как распечатанная копия ответа, которая лежит у тебя на столе и не меняется, пока ты сам её не обновишь.

CREATE MATERIALIZED VIEW mv_store_daily_revenue AS
SELECT s.name AS store_name, pu.purchase_date, SUM(pr.price) AS revenue
FROM purchase pu
JOIN product pr ON pu.product_id = pr.id
JOIN store s ON pr.store_id = s.id
GROUP BY s.name, pu.purchase_date;

В отличие от обычного VIEW, здесь результат запроса физически сохраняется на диск в момент создания — последующие обращения читают уже готовые данные, а не пересчитывают запрос заново. Типичное применение — отчёты и дашборды: выручка по магазинам за день считается по миллионам покупок один раз, а открывается мгновенно.

// шаг 6/25 · теория · ~1 мин

REFRESH MATERIALIZED VIEW — когда данные устаревают

Аналогия: если исходные данные изменились, а «распечатанная копия» — нет, нужно явно попросить переиздать её заново.

REFRESH MATERIALIZED VIEW mv_store_daily_revenue;

Без явного REFRESH материализованное представление продолжит показывать старые данные, даже если исходные таблицы уже изменились — это и есть плата за более быструю скорость чтения.

// шаг 7/25 · теория · ~1 мин

VIEW или материализованное представление?

Аналогия: обычный VIEW — как живой курс валют на сайте банка (всегда свежий, но требует запроса каждый раз); материализованное представление — как курс валют, распечатанный на бумаге утром (быстро посмотреть, но к вечеру может устареть).

VIEW Materialized VIEW
Хранит данные физически Нет Да
Всегда актуален Да Нет, до следующего REFRESH
Поддерживает INSERT/UPDATE/DELETE (с оговорками) Да Нет, только чтение
Можно создавать индексы Нет Да
// шаг 8/25 · теория · ~1 мин

Индексы: зачем они нужны

Аналогия: искать слово в книге без оглавления — читать страницу за страницей. С алфавитным указателем в конце книги — сразу открыть нужную страницу. Индекс в базе данных — тот же алфавитный указатель, только для строк таблицы.

CREATE INDEX idx_product_store_id ON product (store_id);

Без индекса поиск по store_id требует последовательного просмотра всех строк таблицы (Seq Scan) — время растёт линейно с размером таблицы. С B-Tree индексом время поиска растёт логарифмически: для 1 000 000 строк это разница между условной 1 000 000 и примерно 20 операциями сравнения.

// шаг 9/25 · теория · ~1 мин

EXPLAIN ANALYZE — доказательство, что индекс работает

Аналогия: EXPLAIN ANALYZE — как навигатор, который не просто довозит до места, а показывает, каким маршрутом он поехал и сколько это заняло по факту.

EXPLAIN ANALYZE
SELECT pr.title, s.name
FROM product pr
JOIN store s ON pr.store_id = s.id;

В выводе нужно увидеть строку вроде Index Scan using idx_product_store_id on product — это подтверждает, что база реально воспользовалась индексом, а не просканировала таблицу целиком (Seq Scan). Иногда индекс существует, но не используется — планировщик посчитал, что для маленькой таблицы последовательное чтение дешевле.

// шаг 10/25 · теория · ~1 мин

Функциональный индекс

Аналогия: обычный индекс сортирует значения «как есть», а функциональный — заранее пересчитанный результат формулы, как оглавление, составленное не по названиям глав, а по их сокращённым кодам.

CREATE INDEX idx_customer_name_upper ON customer (UPPER(name));

Такой индекс ускоряет именно запросы, где фильтрация или сортировка идёт по UPPER(name), а не по голому name — база использует индекс, только если запрос обращается к данным той же формулой, по которой индекс построен.

// шаг 11/25 · теория · ~1 мин

Многоколоночный индекс и Index Only Scan

Аналогия: если почти всегда ищут «по фамилии и дате рождения вместе» — логичнее сделать один составной алфавитный указатель по обоим полям сразу, а не два отдельных.

CREATE INDEX idx_purchase_multi ON purchase (customer_id, product_id, purchase_date);

Если все нужные запросу столбцы (customer_id, product_id, purchase_date) уже есть внутри самого индекса, база может вообще не заглядывать в саму таблицу — в плане запроса это видно как Index Only Scan вместо Index Scan, что ещё быстрее.

// шаг 12/25 · теория · ~1 мин

Уникальный индекс — целостность плюс скорость

Аналогия: уникальный индекс — это одновременно и алфавитный указатель, и охранник на входе, не пускающий вторую запись с уже занятым значением.

CREATE UNIQUE INDEX idx_product_unique ON product (store_id, title);

Теперь база физически не позволит завести в одном магазине второй товар с тем же названием — попытка вызовет ошибку нарушения уникальности. Побочный эффект — такой индекс, как и обычный, ускоряет поиск по этим же столбцам.

// шаг 13/25 · теория · ~1 мин

Частично уникальный индекс

Аналогия: «уникальность, но только при определённом условии» — как правило «у пользователя может быть сколько угодно отменённых заказов, но только одна активная корзина».

CREATE UNIQUE INDEX idx_one_active_cart
ON cart (customer_id)
WHERE status = 'active';

Уникальность здесь действует только среди строк, удовлетворяющих условию WHERE: у покупателя может быть только одна корзина в статусе active, а оплаченных и брошенных — сколько угодно. Таблицы cart в учебной базе нет — создай её сама в задании 4.

// шаг 14/25 · теория · ~1 мин

Ограничения (constraints): NOT NULL, CHECK, DEFAULT

Аналогия: ограничения — это правила заполнения бумажной анкеты, которые проверяют на входе, а не после: «это поле обязательно», «значение должно быть в диапазоне 0–100», «если не заполнено — подставь ноль».

ALTER TABLE promo_code
    ALTER COLUMN discount SET NOT NULL,
    ALTER COLUMN discount SET DEFAULT 0,
    ADD CONSTRAINT ch_discount_range CHECK (discount BETWEEN 0 AND 100);

Здесь три вида ограничений на столбце скидки в таблице промокодов: NOT NULL — значение обязательно, DEFAULT — что подставить, если при вставке его не указали, CHECK — любое логическое условие, которому обязаны соответствовать значения столбца. Нарушение ограничения при INSERT/UPDATE завершается ошибкой, а не тихой записью неверных данных.

// шаг 15/25 · теория · ~1 мин

Последовательности (SEQUENCE)

Аналогия: последовательность — отдельный автоматический нумератор в гардеробе: каждый новый посетитель получает следующий номерок, и номератор сам помнит, до какого числа уже досчитал.

CREATE SEQUENCE seq_promo_code START 1;

ALTER TABLE promo_code
    ALTER COLUMN id SET DEFAULT nextval('seq_promo_code');

nextval('seq_...') возвращает следующее число и запоминает его как текущее состояние счётчика — при следующем вызове вернётся уже на единицу больше, даже если два запроса вызвали его почти одновременно (это безопасно для параллельных вставок, в отличие от ручного MAX(id) + 1). В новых таблицах обычно пишут короче — id bigint GENERATED ALWAYS AS IDENTITY: последовательность создаётся и привязывается к столбцу автоматически.

// шаг 16/25 · теория · ~1 мин

Документирование схемы: COMMENT ON

Аналогия: комментарий к таблице и столбцам — как табличка с пояснением рядом с музейным экспонатом: сама таблица не изменится, но новому человеку станет понятнее, что здесь и зачем.

COMMENT ON TABLE promo_code IS 'Промокоды магазинов для покупателей';
COMMENT ON COLUMN promo_code.discount IS 'Размер скидки в процентах, от 0 до 100';

Эти комментарии видны через \d+ promo_code в psql или в интерфейсе IDE — стандартная практика документирования схемы прямо в самой базе данных (Data Governance), а не только в отдельном текстовом файле.

// шаг 17/25 · теория · ~2 мин

Порядок столбцов в составном индексе

Аналогия: телефонный справочник отсортирован сначала по фамилии, потом по имени. Найти всех Ивановых — легко. Найти всех Петров, не зная фамилии, — придётся читать справочник целиком, хотя имена в нём тоже отсортированы.

В §10 составной индекс упоминался, но не сказано главное: порядок столбцов в нём решает всё.

CREATE INDEX idx ON orders (customer_id, status, created_at);

Этот индекс годится для запросов, использующих столбцы слева направо без пропусков:

Запрос Индекс работает
WHERE customer_id = 5 да, первый столбец
WHERE customer_id = 5 AND status = 'new' да, 1 + 2
WHERE customer_id = 5 AND status = 'new' AND created_at > ... да, целиком
WHERE status = 'new' нет — пропущен первый
WHERE created_at > '2026-01-01' нет — пропущены первые два

Это называется правилом левого префикса. Из него следуют два практических вывода. Первый: индекс (a, b) делает ненужным отдельный индекс по a, но не заменяет индекс по b. Второй: столбцы, по которым идёт диапазон (>, <, BETWEEN), ставят в конец — после диапазона остальные столбцы индекса уже не сужают поиск, потому что внутри диапазона порядок по следующему столбцу не гарантирован.

Порядок выбирают так: первым — столбец с самым частым точным сравнением и наибольшей избирательностью (то есть тот, что отсекает больше всего строк), последним — диапазоны и сортировка.

// шаг 18/25 · теория · ~2 мин

Почему индекс есть, а Seq Scan остался

Аналогия: указатель в книге есть, но искать по нему бессмысленно, если ты ищешь не по тому признаку, по которому он составлен.

Пять причин покрывают почти все случаи, и проверять их стоит именно в этом порядке.

1. Функция над столбцом. Самая частая:

WHERE date(created_at) = '2026-01-01'          -- ✘ индекс по created_at не сработает
WHERE created_at >= '2026-01-01'
  AND created_at <  '2026-01-02'               -- ✔ сработает

Индекс хранит значения столбца, а не результат функции над ними. Либо переписывают условие диапазоном, либо создают функциональный индекс (§9) — но диапазон почти всегда лучше.

2. Нет левого префикса — разобрано в §16.

3. Запрос выбирает слишком много строк. Если условию удовлетворяет треть таблицы, последовательное чтение действительно быстрее прыжков по индексу и обратно к строкам. Здесь планировщик прав, и это не проблема.

4. Устаревшая статистика. Планировщик решает на основе накопленных данных о распределении значений. Если таблица резко выросла, оценки врут. Лечится:

ANALYZE orders;

Признак: в EXPLAIN ANALYZE сильно расходятся rows= (оценка) и actual rows= (факт).

5. Таблица маленькая. На сотне строк индекс не даёт выигрыша, и база это знает. Проверять работу индексов имеет смысл только на объёмах, близких к боевым.

// шаг 19/25 · теория · ~3 мин

Цена индексов и их обслуживание

Аналогия: каждый дополнительный указатель в книге надо обновлять при каждой правке текста. Один-два полезны, двадцать превращают редактирование в мучение.

В §7 сказано, что индекс «немного замедляет запись». На практике это не мелочь: каждый индекс на таблице обновляется при каждом INSERT, UPDATE и DELETE. Таблица с восемью индексами пишется в разы медленнее, чем с двумя, и занимает заметно больше места — индексы нередко весят больше самих данных.

Найти бесполезные индексы — регулярная задача эксплуатации:

SELECT schemaname, relname AS table, indexrelname AS index,
       idx_scan AS times_used,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

Индексы с idx_scan = 0 не использовались ни разу с момента сброса статистики — они только замедляют запись и занимают место. Оговорка: свежесозданный индекс и индекс, поддерживающий ограничение уникальности, удалять не надо.

🛑CREATE INDEX блокирует запись в таблицу

Обычная команда создания индекса берёт блокировку, при которой никто не может писать в таблицу, пока индекс строится. На таблице в десятки миллионов строк это десятки минут полного простоя записи — на проде выглядит как «приложение легло», и виноватым оказывается тот, кто выполнил команду.

CREATE INDEX CONCURRENTLY idx_orders_customer ON orders (customer_id);

Вариант CONCURRENTLY строит индекс, не блокируя запись. Он медленнее, требует двух проходов по таблице и не может выполняться внутри транзакции. Если такое построение прервётся, останется нерабочий индекс с пометкой INVALID — его надо удалить (тоже CONCURRENTLY) и повторить.

Правило простое: на боевой базе — только CONCURRENTLY. Это один из тех вопросов, по которым сразу видно, работал человек с production-базой или только с учебной.

Раздувание (bloat). При интенсивных обновлениях индексы накапливают мёртвые записи и разрастаются. Лечится перестроением, и здесь та же оговорка:

REINDEX INDEX CONCURRENTLY idx_orders_customer;
// шаг 20/25 · теория · ~1 мин

Другие типы индексов

B-tree, который используется по умолчанию, покрывает подавляющее большинство случаев — сравнения, диапазоны, сортировку. Но стоит знать, что он не единственный.

Тип Для чего
B-tree по умолчанию: =, <, >, BETWEEN, сортировка
GIN поиск внутри составных значений: JSONB, массивы, полнотекстовый поиск
GiST геоданные, диапазоны, поиск по близости
BRIN огромные таблицы, где данные физически упорядочены — например, логи по времени
Hash только точное равенство; на практике почти всегда проигрывает B-tree

Практически чаще всего за пределами B-tree встречается GIN — он решает задачу, с которой B-tree не справляется в принципе: поиск по содержимому JSON-поля или по слову внутри текста. Это же ответ на вопрос из 2.6 SQL-запросы, §12, почему LIKE '%текст%' медленный: для полноценного поиска по подстроке нужен не B-tree, а полнотекстовый индекс или расширение pg_trgm.

BRIN стоит запомнить отдельно как приём для таблиц с логами: он в сотни раз меньше B-tree и отлично работает там, где строки физически лежат в порядке возрастания времени.

// шаг 21/25 · итоги · ~1 мин

Если запомнить только главное

  • VIEW не хранит данные — это просто сохранённый запрос; материализованное представление хранит данные до следующего REFRESH.
  • Индекс превращает линейный поиск в логарифмический — но требует места на диске и немного замедляет запись (INSERT/UPDATE).
  • EXPLAIN ANALYZE — единственный надёжный способ узнать, использует ли запрос индекс на самом деле.
  • Уникальный индекс одновременно и ускоряет поиск, и защищает от дублей; частичный уникальный индекс ограничивает уникальность условием.
  • CHECK/NOT NULL/DEFAULT — защита данных на уровне самой базы, а не только на уровне приложения.
  • SEQUENCE — безопасный способ генерировать уникальные id при параллельных вставках, в отличие от ручного MAX(id) + 1.
  • Правило левого префикса: индекс (a, b, c) работает для запросов по a, a+b, a+b+c — но не по b или c отдельно. Диапазоны ставь последними.
  • Индекс не используется чаще всего из-за функции над столбцом (date(created_at) = ...), отсутствия левого префикса или устаревшей статистики (ANALYZE).
  • Каждый индекс замедляет запись и занимает место. Неиспользуемые ищут через pg_stat_user_indexes по idx_scan = 0.
  • На боевой базе индексы создают только через CREATE INDEX CONCURRENTLY — обычная команда блокирует запись в таблицу на всё время построения.
  • Кроме B-tree есть GIN (JSONB, полнотекст), GiST (геоданные, диапазоны) и BRIN (огромные таблицы с упорядоченными данными, например логи).

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

💡В портфолио
  • Индексы и EXPLAIN ANALYZE из заданий 1–2 — материал для раздела README «Решения» в P1: какой запрос был медленным и что помогло.

Задание 1 — индекс и EXPLAIN

Заполни таблицу заказов миллионом строк через generate_series. Выполни запрос по дате с EXPLAIN ANALYZE, создай индекс, повтори.
Проверка: план сменился с Seq Scan на Index Scan, время выполнения уменьшилось в разы; записаны оба плана.

Задание 2 — составной индекс

Создай индекс (customer_id, purchase_date). Проверь запросы по customer_id, по customer_id AND purchase_date и только по purchase_date.
Проверка: объясняешь, почему третий запрос индекс не использует.

Задание 3 — материализованное представление

Сделай материализованное представление «выручка по магазинам за день» и обновляй его REFRESH MATERIALIZED VIEW CONCURRENTLY.
Проверка: во время обновления запросы к представлению не блокируются (для этого нужен уникальный индекс на нём).

Задание 4 — ограничения

Создай таблицы promo_code (код, магазин, скидка, срок действия) и cart (покупатель, статус). Добавь CHECK на диапазон скидки, NOT NULL на обязательные поля, уникальный частичный индекс «одна активная корзина на покупателя».
Проверка: некорректные вставки отклоняются с понятной ошибкой.

Задание 5 — неиспользуемые индексы

Найди индексы, которые ни разу не использовались, через pg_stat_user_indexes.
Проверка: запрос выводит имя индекса, таблицу, размер и число сканирований.
