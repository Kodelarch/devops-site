О чём урок

ℹ️Зачем это нужно

До сих пор мы запускали один контейнер за раз. Реальные приложения почти всегда состоят из нескольких сервисов, работающих вместе, а сами сервисы — распределены по разным машинам. Этот урок — мост от «одного контейнера на одном компьютере» к «кластеру машин, слаженно запускающих множество связанных сервисов».

📘Словарик на будущее
  • Микросервис — маленький независимый сервис, отвечающий ровно за одну зону ответственности приложения.
  • Узел (node) — отдельная машина (реальная или виртуальная), включённая в кластер.
  • Кластер — объединение узлов в единую сеть с распределённой между ними нагрузкой.
  • Оркестратор — программа, которая запускает и управляет контейнерами на множестве узлов кластера как единым целым (например, Docker Swarm).
  • Оверлейная сеть (overlay network) — виртуальная сеть, объединяющая контейнеры на разных физических узлах так, будто они в одной локальной сети.
// шаг 2/20 · теория · ~1 мин

Правило «1 микросервис — 1 контейнер»

Аналогия: можно засунуть всех сотрудников компании в один огромный кабинет, но по факту это разрушает всю пользу от разделения на отделы — они просто физически смешаются, и уволить/заменить одного станет так же сложно, как всю компанию.

Формально ничего не мешает засунуть все сервисы приложения в один контейнер — но это разрушает принципы SOLID и чистой архитектуры: становится практически невозможно развернуть новую версию одного отдельного микросервиса, не трогая остальные. Основное правило контейнеризации микросервисных приложений: один контейнер — один микросервис, ни больше, ни меньше.

// шаг 3/20 · теория · ~1 мин

Docker Compose для нескольких сервисов

Аналогия: Docker Compose — дирижёр маленького оркестра: он не играет сам, но знает, кто, когда и в каком порядке должен вступить, и как инструменты должны звучать вместе.

services:
  proxy:
    image: nginx:1.27-alpine
    ports:
      - "8080:80"
  api:
    build: ./api                 # API магазина из урока 2.5
  worker:
    build: ./worker              # фоновые задачи: письма о заказах, пересчёт отчётов
  db:
    image: postgres:17
    # ни у кого, кроме proxy, нет ports — снаружи сервисы недоступны

Сервисы, объявленные в одном compose.yaml, автоматически попадают в общую сеть и видят друг друга по имени сервиса (proxy обращается к api по адресу http://api:8000, api — к базе по адресу db:5432). Наружу (на локальную машину) пробрасывают порты только тех сервисов, к которым реально должен обращаться внешний клиент (здесь — только proxy), а внутренние сервисы вроде api, worker и db остаются недоступны напрямую. Полная версия этого файла с томами и переменными — в 3.1 Docker, §11.

// шаг 4/20 · теория · ~2 мин

Vagrant: виртуальные машины из кода

Аналогия: Vagrant — как рецепт для 3D-принтера: вместо того чтобы вручную настраивать виртуальную машину через графический интерфейс, ты один раз описываешь её параметры в файле, и дальше она печатается (создаётся) по команде за секунды, одинаково, сколько угодно раз.

Vagrant.configure("2") do |config|
  config.vm.box = "ubuntu/jammy64"
  config.vm.hostname = "node01"
  config.vm.network "private_network", ip: "192.168.56.10"
  config.vm.synced_folder "./src", "/home/vagrant/app"
end

vagrant up       # создать и запустить виртуальную машину по конфигурации
vagrant ssh      # зайти внутрь по SSH
vagrant halt     # остановить
vagrant destroy  # полностью уничтожить машину

synced_folder автоматически «пробрасывает» папку с хоста внутрь виртуальной машины — исходный код оказывается доступен внутри VM без ручного копирования. Одним и тем же Vagrantfile можно поднять хоть одну машину, хоть десяток одинаковых — Vagrant создаёт их по описанию, а не вручную через интерфейс гипервизора.

// шаг 5/20 · теория · ~1 мин

Кластер и узлы

Аналогия: если один компьютер — это один работник, то кластер — это целый цех работников, которые вместе выполняют один большой заказ, а не соревнуются друг с другом.

Узел (node) — это отдельная машина (виртуальная или реальная), включённая в кластер. Узлы делятся на роли:

  • manager — управляет кластером, решает, какой узел получит какую задачу;
  • worker — исполняет задачи (запускает контейнеры), но сам не принимает решений об их распределении.

Кластер как таковой не привязан к тому, находятся ли все узлы физически на одной машине — реальные распределённые системы почти всегда работают на узлах, разбросанных по разным серверам или даже дата-центрам.

// шаг 6/20 · теория · ~1 мин

Docker Swarm: инициализация и присоединение узлов

Аналогия: Docker Swarm — простой прораб на стройке: собирает бригаду (worker-узлы) вокруг одного руководителя (manager), и дальше просто раздаёт задания, не требуя от рабочих знать полный план стройки целиком.

# на будущем manager-узле:
docker swarm init --advertise-addr 192.168.56.10
# команда выведет токен присоединения для worker-узлов

# на каждом worker-узле:
docker swarm join --token <TOKEN> 192.168.56.10:2377

docker swarm init превращает обычный Docker-хост в manager нового кластера и генерирует токен, необходимый другим узлам, чтобы присоединиться именно к этому кластеру (а не к случайному). Docker Swarm — один из самых простых оркестраторов «из коробки», не требующий отдельной установки поверх Docker.

// шаг 7/20 · теория · ~1 мин

Docker Hub: публикация и переиспользование образов

Аналогия: Docker Hub — как общедоступная библиотека: вместо того чтобы возить с собой физическую копию книги (образа) на каждый узел кластера, ты кладёшь её в библиотеку один раз, а каждый узел сам берёт нужную копию оттуда, когда она понадобится.

docker tag shop-api:latest username/shop-api:1.0
docker push username/shop-api:1.0

services:
  api:
    image: username/shop-api:1.0    # вместо build: ./api — тянем готовый образ из реестра

В контексте кластера образы обычно не собираются заново на каждом узле (это было бы медленно и неудобно) — их один раз собирают, публикуют в реестр (Docker Hub или приватный аналог), а docker-compose.yml для кластера ссылается на image:, а не на build:.

// шаг 8/20 · теория · ~1 мин

Стек в Docker Swarm: docker stack deploy

Аналогия: если обычный docker compose up — это запустить оркестр в одном зале, то docker stack deploy — это запустить тот же оркестр, но распределённый по нескольким залам сразу, с одним и тем же дирижёрским планом (тем же файлом).

docker stack deploy -c compose.yaml shop
docker stack services shop      # список сервисов стека
docker service ps shop_api      # на каком узле выполняется конкретный сервис

Формат compose.yaml для Swarm практически идентичен обычному Compose-файлу (с некоторыми ограничениями и дополнениями вроде deploy:) — это осознанное решение: тот же самый навык описания сервисов работает что на одной машине, что на целом кластере.

// шаг 9/20 · теория · ~1 мин

Оверлейная сеть: скрываем внутренние сервисы

Аналогия: оверлейная сеть — это отдельная защищённая линия связи между филиалами компании, разбросанными по разным городам: физически они далеко, но по этой линии общаются так, будто сидят в соседних кабинетах одного здания.

services:
  proxy:
    image: nginx:1.27
    ports:
      - "80:80"
    networks:
      - app-net
  api:
    image: username/shop-api:1.0
    networks:
      - app-net
    # без ports — доступен только proxy внутри той же оверлейной сети

networks:
  app-net:
    driver: overlay

Оверлейная сеть (driver: overlay) работает поверх нескольких физических узлов кластера так же прозрачно, как обычная docker-сеть работает в пределах одной машины. Реверс-прокси (например, nginx) — единственная точка входа снаружи; сервисы вроде api, worker и db, к которым не должно быть прямого доступа, просто не публикуют ports наружу вообще.

// шаг 10/20 · теория · ~1 мин

Распределение задач по узлам

Аналогия: manager кластера — как диспетчер такси: сам не знает заранее, какая именно машина возьмёт конкретный заказ, но распределяет заказы по доступным машинам равномерно и следит, чтобы никто не простаивал зря.

docker node ls                  # список узлов кластера и их ролей
docker service ps shop_api      # где сейчас выполняется конкретный сервис

Задача (task) — это конкретный запущенный экземпляр сервиса на конкретном узле. Manager сам решает, на каком узле разместить каждую задачу (с учётом доступных ресурсов) — оператору не нужно вручную указывать «этот контейнер — на этой машине».

// шаг 11/20 · теория · ~1 мин

Portainer: визуализация кластера

Аналогия: Portainer — как диспетчерская панель с картой всего цеха: вместо того чтобы вычитывать текстовый вывод десятка команд docker service ps, ты просто смотришь на графическую схему, кто где выполняется прямо сейчас.

docker stack deploy -c portainer-agent-stack.yml portainer

Portainer разворачивается как отдельный стек внутри того же Swarm-кластера и подключается к Docker API, показывая веб-интерфейс с визуализацией узлов, сервисов и того, какие задачи на каком узле сейчас выполняются — удобно для отладки распределения нагрузки без запоминания десятков CLI-команд.

⚠️Portainer имеет полный доступ к Docker

Он подключается к сокету Docker API, а доступ к этому сокету равносилен правам root на хосте: через него можно запустить контейнер, смонтировавший корневую файловую систему. Поэтому Portainer не публикуют в интернет без ограничений, закрывают отдельной аутентификацией и по возможности держат в приватной сети. То же относится к любому инструменту, которому дают /var/run/docker.sock.

// шаг 12/20 · теория · ~2 мин

Ограничение ресурсов


Аналогия: если в общей квартире один жилец может занять все розетки, остальные останутся без электричества — независимо от того, насколько аккуратно они себя ведут.

По умолчанию контейнер видит всю память и все процессоры хоста. Это значит, что утечка памяти в одном сервисе выключает все остальные на той же машине — и OOM killer (1.1 Linux, §6) выберет жертвой самый прожорливый процесс, которым вполне может оказаться база данных, а не виновник.

services:
  app:
    image: myapp:1.0
    deploy:
      resources:
        limits:
          cpus: "1.5"
          memory: 512M
        reservations:
          cpus: "0.5"
          memory: 256M

limits — жёсткий потолок. Превысил по памяти — контейнер убивают и перезапускают. Превысил по процессору — просто замедляют, ничего не падает. reservations — гарантированный минимум, который планировщик учитывает, размещая задачи по узлам.

В обычном Compose (не Swarm) секция deploy игнорируется, и лимиты задают напрямую:

    mem_limit: 512m
    cpus: 1.5
💡Как подобрать значения

Не угадыванием. Запусти под реальной нагрузкой, посмотри docker stats и метрики из 1.4 Метрики и логи, возьми пиковое потребление и добавь запас процентов тридцать. Слишком низкий лимит по памяти приводит к перезапускам под нагрузкой, слишком высокий — не защищает ни от чего. И обязательно поставь restart: unless-stopped, чтобы убитый по лимиту контейнер поднимался сам.

// шаг 13/20 · теория · ~1 мин

Порядок запуска: depends_on и healthcheck

Аналогия: «база запущена» и «база готова принимать соединения» — разные события, между которыми проходит десяток секунд. Приложение, стартовавшее в промежутке, падает.

Обычный depends_on гарантирует только порядок запуска контейнеров, но не их готовность. Контейнер с базой создан за секунду, а сама база инициализируется полминуты — приложение всё это время будет получать отказ в соединении.

services:
  db:
    image: postgres:17-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 30s

  app:
    image: myapp:1.0
    depends_on:
      db:
        condition: service_healthy      # ждать не запуска, а готовности
    restart: unless-stopped

condition: service_healthy заставляет Compose дождаться, пока healthcheck базы начнёт проходить. start_period даёт время на первичную инициализацию, не считая ранние неудачи за отказ.

⚠️Но полагаться на это нельзя

Даже с healthcheck приложение обязано переживать временную недоступность базы: она может уйти в перезапуск позже, уже во время работы. В Kubernetes (5.1 Kubernetes) аналога depends_on нет вовсе — контейнеры стартуют в произвольном порядке, и приложение просто обязано уметь ждать и переподключаться. Здоровая привычка: повторы с экспоненциальной задержкой при подключении к зависимостям (2.3 Параллельность, §11).

// шаг 14/20 · теория · ~2 мин

Одна конфигурация на все окружения


Аналогия: один чертёж здания и отдельные листы правок под конкретную площадку — а не пять полных чертежей, которые начинают расходиться между собой с первого же изменения.

Копировать compose.yaml в compose.prod.yaml — прямой путь к тому, что через месяц окружения будут отличаться неизвестно чем. Compose умеет накладывать файлы друг на друга.

docker compose up -d
# автоматически читает compose.yaml + compose.override.yaml (разработка)

docker compose -f compose.yaml -f compose.prod.yaml up -d
# явно указанный набор для прода

Файл compose.override.yaml подхватывается автоматически (старые имена docker-compose.yml и docker-compose.override.yml тоже работают, но их не смешивают с новыми) и содержит то, что нужно только при разработке: монтирование кода внутрь контейнера, проброшенный наружу порт базы, подробные логи. В репозиторий он кладётся, а вот .env с реальными значениями — нет (2.5 Бэкенд-сервис, §9).

Профили решают смежную задачу — необязательные сервисы:

  pgadmin:
    image: dpage/pgadmin4
    profiles: ["debug"]        # поднимется только с --profile debug

Пара мелочей, о которых стоит знать. Ключ version: в начале файла устарел — современный Compose его игнорирует и выдаёт предупреждение. И логи: без настройки драйвера файл лога контейнера растёт неограниченно, пока не кончится диск:

    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

Ровно та же проблема, что решает logrotate для обычных сервисов (1.1 Linux, §17).

// шаг 15/20 · теория · ~1 мин

Swarm или Kubernetes

Аналогия: Swarm — это надёжный велосипед, а Kubernetes — грузовик. Велосипед проще, дешевле и для поездки за хлебом лучше во всех отношениях. Но работу возят на грузовике, и вакансии открывают на водителей грузовиков.

Честная картина на 2026 год: Docker Swarm фактически проиграл Kubernetes. Он не заброшен и продолжает работать, но новых крупных внедрений почти нет, экосистема инструментов вокруг него не развивается, а в вакансиях он упоминается редко — обычно как «плюсом будет».

Зачем тогда изучать его здесь:

  • Понятия одинаковы: узлы, менеджеры и воркеры, сервисы, задачи, реплики, оверлейная сеть, декларативное описание желаемого состояния. Всё это перейдёт в 5.1 Kubernetes почти без изменений в смысле — поменяются только названия и объём YAML.
  • Swarm показывает те же идеи на порядок проще: кластер поднимается двумя командами, а не полудневной установкой.
  • Для маленьких проектов он до сих пор разумный выбор: если нужно три сервиса на двух машинах, Kubernetes здесь избыточен по сложности эксплуатации.

Что делать в вакансиях: если требуют оркестрацию — это почти наверняка Kubernetes. Опыт со Swarm стоит упоминать как понимание принципов, а не как замену.

Из промежуточных вариантов сейчас встречается Docker Compose на одной машине плюс systemd — для небольших сервисов этого хватает, и это честнее, чем разворачивать кластер ради трёх контейнеров.

// шаг 16/20 · итоги · ~1 мин

Если запомнить только главное

  • Правило «1 микросервис — 1 контейнер» — иначе разваливается независимость развёртывания сервисов.
  • Vagrant создаёт виртуальные машины по декларативному описанию (Vagrantfile), а не вручную через интерфейс.
  • Docker Swarm объединяет несколько Docker-хостов в один кластер: manager решает, worker выполняет.
  • Для кластера образы обычно публикуются в реестр (Docker Hub) заранее, а не собираются заново на каждом узле.
  • docker stack deploy использует практически тот же формат файла, что и обычный docker compose — только теперь распределённо по узлам.
  • Оверлейная сеть скрывает внутренние сервисы от прямого доступа снаружи — наружу смотрит только реверс-прокси.
  • Portainer даёт визуальное представление того, что происходит в кластере, вместо чтения текстового вывода CLI. Доступ к сокету Docker равносилен правам root на хосте.
  • Без лимитов ресурсов утечка в одном сервисе кладёт всю машину, а OOM killer убьёт не виновника, а самого прожорливого. limits — потолок, reservations — гарантия.
  • depends_on без condition: service_healthy гарантирует только порядок запуска, но не готовность. И даже с ним приложение обязано уметь переподключаться.
  • Один базовый Compose-файл плюс наложения под окружения (compose.override.yml, compose.prod.yml) вместо копий, которые расходятся. Ключ version: устарел.
  • Логи контейнера растут неограниченно, пока не задан max-size — тот же класс проблемы, что решает logrotate.
  • Swarm фактически проиграл Kubernetes. Изучать его стоит ради понятий (узлы, сервисы, реплики, оверлейная сеть), которые почти без изменений перейдут в K8s.
// шаг 17/20 · практика

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

💡В портфолио
  • Задание 1 (compose.yaml с healthcheck) — файл, которым поднимается P1.
  • Задание 5 (разные окружения через дополнительные файлы) — compose.prod.yaml в P1.

Задание 1 — стек в Compose

Опиши приложение, PostgreSQL и nginx в одном compose.yaml: сети, том для базы, depends_on с condition: service_healthy, переменные из .env.
Проверка: docker compose up -d с нуля поднимает всё в правильном порядке; приложение не падает при старте из-за неготовой базы.

Задание 2 — кластер Swarm

Через Vagrant подними три машины, инициализируй Swarm (менеджер + 2 воркера).
Проверка: docker node ls показывает три узла в статусе Ready.

Задание 3 — стек в Swarm

Задеплой стек через docker stack deploy с 3 репликами приложения, оверлейной сетью, где база не доступна снаружи, и лимитами памяти.
Проверка: при остановке одного воркера реплики переезжают на оставшиеся; порт базы не отвечает с хоста.

Задание 4 — обновление без простоя

Обнови образ приложения с update_config: parallelism: 1, order: start-first.
Проверка: во время обновления цикл curl каждую секунду не получает ошибок.

Задание 5 — один compose на окружения

Вынеси различия dev и prod в compose.override.yaml и compose.prod.yaml.
Проверка: docker compose -f compose.yaml -f compose.prod.yaml config показывает итоговую конфигурацию без dev-настроек.
