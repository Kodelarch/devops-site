О чём урок

ℹ️Зачем это нужно

Контейнеризация — сегодня стандартный способ доставки и запуска приложений в индустрии. Практически любая вакансия DevOps требует уверенного владения Docker: не абстрактно «знаю, что это», а руками — собрать образ, отладить контейнер, проверить его на безопасность, поднять несколько сервисов вместе.

📘Словарик на будущее
  • Докер-образ (image) — «упаковка» приложения и всех его зависимостей, неизменяемый шаблон, из которого создаются контейнеры.
  • Контейнер (container) — запущенный экземпляр образа, «ожившая» упаковка — то, что реально работает и потребляет ресурсы.
  • Dockerfile — текстовый рецепт, по которому Docker собирает образ шаг за шагом.
  • Слой (layer) — одно изменение файловой системы, зафиксированное одной инструкцией Dockerfile; слои накладываются друг на друга поверх базового.
  • Реверс-прокси (reverse proxy) — сервер, принимающий запросы снаружи и перенаправляющий их дальше, к реальному приложению, оставаясь для клиента единственной видимой точкой входа.
// шаг 2/22 · теория · ~1 мин

Контейнер — не виртуальная машина

Аналогия: виртуальная машина — это как построить для каждого жильца отдельный дом с собственным фундаментом, стенами и коммуникациями. Контейнер — как отдельная квартира в одном большом доме: у каждого своя дверь, свои вещи, но фундамент и инженерные системы дома — общие.

Предшественниками контейнеров были именно виртуальные машины: они тоже изолируют приложение от внешней среды, но для этого эмулируют целое отдельное «железо» и запускают полноценную операционную систему поверх него. Контейнер разделяет с хостом ядро операционной системы и изолирует только то, что реально нужно приложению (файловую систему, процессы, сеть) — поэтому контейнеры:

  • потребляют кратно меньше ресурсов, чем VM;
  • запускаются за секунды, а не за минуты;
  • легко переносятся между машинами (тот же образ работает одинаково и на ноутбуке разработчика, и на сервере).
💡Почему это важно на реальной работе

Главное преимущество контейнеризации — изоляция зависимостей и единая простая точка запуска ПО: «работает у меня на машине» перестаёт быть проблемой, потому что окружение приложения — часть самого образа, а не окружения хоста.

// шаг 3/22 · теория · ~1 мин

Докер-образ и контейнер — в чём разница

Аналогия: образ — это класс в программировании, контейнер — конкретный объект, созданный из этого класса. Из одного образа можно запустить сколько угодно независимых контейнеров.

docker pull nginx           # скачать готовый образ из реестра (Docker Hub)
docker images               # посмотреть список образов на машине
docker run -d nginx         # создать и запустить контейнер на основе образа
docker ps                   # посмотреть список запущенных контейнеров

docker run создаёт новый контейнер при каждом вызове — если вызвать эту команду трижды, получится три независимых контейнера из одного и того же образа, каждый со своим состоянием и процессами.

// шаг 4/22 · теория · ~1 мин

Из чего состоит образ: слои

Аналогия: образ — это стопка прозрачных калек, наложенных друг на друга: нижняя калька — базовая операционная система, каждая следующая — одно конкретное изменение (установили пакет, скопировали файл). Итоговая картинка — сумма всех калек сразу.

FROM ubuntu:24.04
RUN apt-get update && apt-get install -y nginx
COPY ./site /var/www/html
CMD ["nginx", "-g", "daemon off;"]

Каждая инструкция Dockerfile (FROM, RUN, COPY, ...) создаёт отдельный слой. Слои кэшируются: если ничего не изменилось выше по файлу, Docker при пересборке переиспользует уже готовый слой, не выполняя его заново — поэтому Docker собирает образ быстро при мелких правках.

💡Практическое правило

Избегай множественных отдельных вызовов RUN там, где можно объединить команды через && в один вызов — каждый RUN создаёт свой слой, и лишние слои увеличивают итоговый размер образа и число промежуточных кэш-точек без реальной пользы.

// шаг 5/22 · теория · ~2 мин

Жизненный цикл контейнера

Аналогия: контейнер — как телевизор: можно включить, выключить, перезагрузить, заглянуть «внутрь» через сервисное меню — при этом сам телевизор (образ) не меняется от этих действий.

docker run -d --name web -p 8080:80 nginx:1.27   # запустить, порт 80 контейнера доступен на 8080 хоста
docker ps                                         # проверить, что контейнер работает
docker logs -f web                                # вывод контейнера в реальном времени
docker inspect web                                # подробная информация: IP, порты, тома, переменные
docker stop web                                   # остановить (SIGTERM, через 10 секунд — SIGKILL)
docker start web                                  # запустить тот же контейнер снова
docker rm web                                     # удалить контейнер (образ остаётся)

-p 8080:80 означает «порт 80 внутри контейнера доступен на порту 8080 хост-машины» — без этого проброса порт контейнера остаётся видимым только изнутри docker-сети. Под капотом это DNAT-правило из 1.2 Сети, §10. --name web даёт контейнеру имя, чтобы не копировать длинный идентификатор в каждую команду. docker inspect возвращает JSON с полным описанием контейнера — оттуда же можно узнать его внутренний IP-адрес в docker-сети и смонтированные тома.

docker stop сначала посылает главному процессу контейнера SIGTERM и ждёт, а через 10 секунд добивает SIGKILL — ровно порядок из 1.1 Linux, §5. Почему контейнер иногда не реагирует на SIGTERM, разобрано в §14.

// шаг 6/22 · теория · ~1 мин

Заглянуть внутрь и изменить контейнер на лету

Аналогия: docker exec — как зайти внутрь работающей квартиры через отдельный чёрный ход, не выселяя жильца — можно посмотреть, что там происходит, или что-то поправить, пока контейнер продолжает работать.

docker exec -it web sh                                # оболочка внутри контейнера
docker exec web cat /etc/nginx/conf.d/default.conf    # прочитать файл внутри контейнера
docker cp ./default.conf web:/etc/nginx/conf.d/        # скопировать файл с хоста внутрь
docker exec web nginx -t && docker exec web nginx -s reload   # проверить и перечитать конфиг

Флаги -it у docker exec — это сразу два флага вместе: -i (interactive) держит открытым ввод, а -t (tty) выделяет псевдотерминал, благодаря которому вывод команды внутри контейнера выглядит и ведёт себя как в обычном терминале — без них интерактивная оболочка была бы почти неюзабельна. В минимальных образах bash часто нет, поэтому запускают sh.

docker cp копирует файлы между хостом и контейнером в любом направлении, не требуя пересборки образа — удобно для быстрой отладки конфигурации, но такие изменения теряются при удалении контейнера. Всё, что должно жить дольше одного эксперимента, попадает в Dockerfile (§8) или монтируется снаружи (§9).

// шаг 7/22 · теория · ~1 мин

nginx: обратный прокси перед приложением

Аналогия: nginx — как секретарь в приёмной большого офиса: он не выполняет саму работу, а принимает посетителей (запросы) и направляет их точно в нужный кабинет (в конкретное внутреннее приложение), оставаясь единственным, кого видит посетитель снаружи.

У nginx один главный процесс (master) и несколько рабочих (worker). Master читает и проверяет конфигурацию, управляет worker-процессами; worker-ы непосредственно обрабатывают входящие запросы. Подробно nginx разбирался в 1.2 Сети, §11 — здесь он работает в контейнере перед приложением:

# nginx/default.conf
server {
    listen 80;

    location / {
        proxy_pass http://app:8000;          # имя сервиса из docker-сети (§11)
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location = /nginx_status {
        stub_status;                         # счётчики соединений самого nginx
        allow 127.0.0.1;
        deny all;
    }
}

proxy_pass — ключевая инструкция реверс-прокси: клиент обращается к nginx на порту 80, а nginx перенаправляет запрос дальше на приложение (здесь — на app:8000), полностью скрывая эту деталь от клиента. stub_status отдаёт счётчики активных соединений и запросов — их потом забирает экспортер для мониторинга (4.5 Наблюдаемость, §4). Доступ к странице статуса закрыт для всех, кроме самой машины: внутренние счётчики незачем показывать интернету.

// шаг 8/22 · теория · ~1 мин

Приложение за прокси: как nginx разговаривает с кодом

Аналогия: nginx — переводчик на входе в здание. Он отлично говорит с посетителями, но чтобы передать их просьбу во внутренний отдел, нужен язык, который понимает и отдел.

Между nginx и приложением всегда есть протокол — и от него зависит, как приложение запускается:

Протокол Кто так работает Директива nginx
HTTP Python (gunicorn, uvicorn), Node.js, Go, Java proxy_pass
FastCGI PHP (php-fpm), программы на C через libfcgi fastcgi_pass
uWSGI старые Python-проекты на uWSGI uwsgi_pass

Сегодня почти все новые сервисы говорят обычным HTTP: приложение само слушает порт, а nginx проксирует на него запросы. Python-сервис из 2.5 Бэкенд-сервис запускается через WSGI-сервер gunicorn (§10 того урока):

gunicorn --workers 4 --bind 0.0.0.0:8000 "app:create_app()"

Важно 0.0.0.0, а не 127.0.0.1: внутри контейнера 127.0.0.1 — это сам контейнер, и nginx из соседнего контейнера до такого адреса не достучится. Это самая частая причина ошибки 502 Bad Gateway при первом запуске связки.

FastCGI стоит узнавать в лицо: он встретится в любой инфраструктуре с PHP. Там nginx не проксирует HTTP, а передаёт запрос процессу php-fpm через fastcgi_pass — идея та же, меняется только язык общения.

// шаг 9/22 · теория · ~2 мин

Свой Dockerfile: собрать и запустить сервис

Аналогия: Dockerfile — рецепт: что взять за основу, что докупить, что положить внутрь и как подавать. По одному рецепту на любой кухне получается одно и то же блюдо.

FROM python:3.13-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY src/ ./src/
ENV PYTHONUNBUFFERED=1

EXPOSE 8000
CMD ["gunicorn", "--workers", "4", "--bind", "0.0.0.0:8000", "src.app:create_app()"]

Базовый образ python:3.13-slim — официальный Python на урезанном Debian: всё нужное для запуска, ничего лишнего. Сначала копируется только requirements.txt и ставятся зависимости, а код — потом: почему именно в таком порядке, разобрано в §13. --no-cache-dir не оставляет в образе кеш pip. PYTHONUNBUFFERED=1 заставляет Python писать в stdout сразу, без буферизации, — иначе логи в docker logs появляются с задержкой или теряются при падении. EXPOSE ничего не открывает сам, это пометка «приложение слушает 8000». CMD записан списком — это exec-форма, и она важна для корректной остановки контейнера (§14).

docker build -t shop-api:0.1.0 .
docker run -d --name api -p 8000:8000 -e DATABASE_URL=postgresql://... shop-api:0.1.0
curl localhost:8000/healthz

Тег 0.1.0 вместо latest — привычка с первого дня: по нему всегда понятно, какая версия запущена, и на неё можно откатиться (3.2 CI-CD, §15).

// шаг 10/22 · теория · ~1 мин

Монтирование конфигурации: volume вместо пересборки

Аналогия: если каждый раз пересобирать весь дом ради замены одной картины на стене — абсурдно; вместо этого проще держать картину «снаружи» и просто вешать её на уже готовую стену.

docker run -d --name proxy -p 8080:80 \
  -v ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro \
  nginx:1.27-alpine

-v ./nginx/default.conf:/etc/nginx/conf.d/default.conf монтирует файл с хоста внутрь контейнера — правка конфига на хосте видна в контейнере сразу, потому что физически это один и тот же файл. Чтобы nginx её подхватил, достаточно docker exec proxy nginx -s reload — без пересборки образа. Суффикс :ro (read-only) запрещает контейнеру менять файл: конфиг должен приходить снаружи, а не правиться изнутри.

Разделение простое: код — в образе, настройки — снаружи (переменные окружения и смонтированные конфиги). Тогда один и тот же образ работает в dev, staging и prod, а различаются только настройки — принцип 12-factor из 2.5 Бэкенд-сервис, §12.

// шаг 11/22 · теория · ~1 мин

Проверка Dockerfile и образа: hadolint и Dockle

Аналогия: техосмотр перед выездом на дорогу: специально ищут типичные небезопасные привычки (запуск от root, «лысые» шины в виде тега latest), а не просто проверяют, что машина вообще едет.

docker run --rm -i hadolint/hadolint < Dockerfile   # проверить сам Dockerfile
dockle shop-api:0.1.0                               # проверить собранный образ

hadolint читает Dockerfile и находит типовые ошибки ещё до сборки: FROM без версии, apt-get install без очистки кеша, CMD в shell-форме, отсутствие USER. Dockle проверяет уже собранный образ по CIS Benchmarks — набору общепринятых практик безопасности контейнеров — и подсвечивает конкретные предупреждения: «не создан отдельный непривилегированный пользователь», «в образе остались файлы с секретами», «не задан HEALTHCHECK». Задача — довести образ до состояния без предупреждений, а не просто прочитать отчёт. Сканирование на известные уязвимости (Trivy) — следующий шаг, о нём в 6.2 DevSecOps, §6.

// шаг 12/22 · теория · ~2 мин

Docker Compose: несколько контейнеров как единое целое

Аналогия: если Docker — это команда «запусти один инструмент», то Docker Compose — это целый чек-лист «запусти оркестр из нескольких инструментов в правильном порядке, и пусть они слышат друг друга».

# compose.yaml
services:
  app:
    build: .
    environment:
      DATABASE_URL: postgresql://shop:shop@db:5432/shop
    # без ports — сервис виден только внутри docker-сети

  db:
    image: postgres:17
    environment:
      POSTGRES_USER: shop
      POSTGRES_PASSWORD: shop
      POSTGRES_DB: shop
    volumes:
      - db_data:/var/lib/postgresql/data

  proxy:
    image: nginx:1.27-alpine
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    ports:
      - "8080:80"
    depends_on:
      - app

volumes:
  db_data:

docker compose up -d --build
docker compose ps
docker compose logs -f app
docker compose down          # остановить и удалить контейнеры (тома остаются)

Все сервисы, описанные в одном compose.yaml, по умолчанию оказываются в общей внутренней docker-сети и видят друг друга по имени сервиса (app, db, proxy) как по доменному имени — именно поэтому nginx проксирует на app:8000, а приложение подключается к db:5432, хотя ни один из этих портов не опубликован наружу. Снаружи доступен только proxy на 8080. Пароль прямо в файле допустим только для учебного стенда — как с этим жить по-взрослому, разобрано в 4.1 Compose и Swarm, §13 и 6.2 DevSecOps.

// шаг 13/22 · теория · ~2 мин

Multi-stage build: инструменты сборки не едут в прод


Аналогия: мебель собирают в цеху со станками и стружкой, а к заказчику привозят только готовый шкаф. Везти вместе с ним весь цех никому не приходит в голову.

Некоторым Python-библиотекам при установке нужен компилятор: например, драйвер PostgreSQL psycopg или криптографические пакеты собираются из исходников на C. Если поставить gcc прямо в итоговый образ, в нём навсегда останутся компилятор, заголовочные файлы и кеш сборки. Это плохо по трём причинам: образ весит больше необходимого, внутри лежит компилятор (готовый инструмент для того, кто получит доступ к контейнеру), и каждый лишний пакет — это потенциальные уязвимости в отчёте сканера.

Multi-stage build решает это одним приёмом: этапов сборки может быть несколько, а в итоговый образ попадает только последний.

# ---------- этап сборки ----------
FROM python:3.13-slim AS builder
RUN apt-get update && apt-get install -y --no-install-recommends gcc libpq-dev \
    && rm -rf /var/lib/apt/lists/*
RUN python -m venv /venv
COPY requirements.txt .
RUN /venv/bin/pip install --no-cache-dir -r requirements.txt

# ---------- финальный образ ----------
FROM python:3.13-slim
RUN apt-get update && apt-get install -y --no-install-recommends libpq5 \
    && rm -rf /var/lib/apt/lists/*
COPY --from=builder /venv /venv
COPY src/ /app/src/
WORKDIR /app
ENV PATH="/venv/bin:$PATH" PYTHONUNBUFFERED=1
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "src.app:create_app()"]

AS builder даёт этапу имя, а COPY --from=builder забирает из него только нужное — готовое виртуальное окружение со скомпилированными библиотеками. Компилятор, заголовочные файлы и кеш остаются в отброшенном этапе. В финальный образ ставится только libpq5 — библиотека, нужная драйверу для работы, но без инструментов сборки.

Для компилируемых языков эффект ещё заметнее: программа на Go собирается в один файл, который кладут в почти пустой образ (distroless или даже scratch) — с 800 МБ до 10–20 МБ. Образ быстрее качается на каждый узел, быстрее стартует и содержит на порядок меньше того, что нужно обновлять из-за уязвимостей.

// шаг 14/22 · теория · ~2 мин

Кеш слоёв: порядок инструкций


Аналогия: если каждый раз перед приготовлением ужина заново ходить в магазин за солью — процесс станет вдвое дольше. Продукты длительного хранения закупают редко, свежие — каждый день.

В §3 сказано, что слои кешируются. Ключевое следствие оттуда не выведено: кеш ломается на первой изменившейся инструкции и на всех, что идут после неё. Значит, порядок строк в Dockerfile напрямую определяет время пересборки.

# ✘ плохо: любая правка кода запускает переустановку зависимостей
COPY . /app
RUN pip install -r /app/requirements.txt

# ✔ хорошо: зависимости переустанавливаются, только если изменился их список
COPY requirements.txt /app/
RUN pip install --no-cache-dir -r /app/requirements.txt
COPY . /app

Разница на реальном проекте — три минуты против трёх секунд на каждую правку строчки кода. За рабочий день это десятки минут ожидания.

Правило простое: инструкции располагают от редко меняющихся к часто меняющимся. Базовый образ и системные пакеты — вверху, зависимости — в середине, код приложения — в самом низу.

.dockerignore работает на ту же цель. Без него COPY . /app тащит в образ .git, .venv, кеши, логи и локальные конфиги — и ломает кеш при любом их изменении, даже если код не менялся:

.git
.venv
__pycache__
*.pyc
.env
node_modules
tests/
README.md

Синтаксис тот же, что у .gitignore (0.1 Git, §5). Заодно это защита от случайного попадания .env с паролями внутрь образа.

// шаг 15/22 · теория · ~3 мин

CMD, ENTRYPOINT и кто такой PID 1


Аналогия: если между тобой и собеседником стоит переводчик, который не переводит, разговора не будет — сколько бы ты ни говорил.

Два вопроса, которые задают почти всегда: чем CMD отличается от ENTRYPOINT и почему приложение в контейнере не завершается корректно.

CMD против ENTRYPOINT. ENTRYPOINT задаёт саму команду, CMD — аргументы по умолчанию к ней. Аргументы, переданные в docker run, заменяют CMD, но не трогают ENTRYPOINT:

ENTRYPOINT ["python", "app.py"]
CMD ["--port", "8000"]

docker run myapp запустит python app.py --port 8000, а docker run myapp --port 9000 — с новым портом. Если написать всё в CMD, то docker run myapp bash просто заменит команду целиком — иногда это удобно для отладки, а иногда нежелательно.

Форма записи — важнее, чем кажется. Есть shell-форма (CMD python app.py) и exec-форма (CMD ["python", "app.py"]). Различие не косметическое:

При shell-форме Docker запускает /bin/sh -c "python app.py", и процессом с PID 1 становится оболочка, а приложение — её потомком. При остановке контейнера SIGTERM получает только PID 1, то есть оболочка, а она не передаёт сигнал дальше. Приложение не узнаёт, что его просят завершиться, и через несколько секунд получает SIGKILL.

Практическое следствие прямо связано с 2.5 Бэкенд-сервис, §12: обработчик SIGTERM там написан, корректное завершение реализовано — и всё это бесполезно, потому что сигнал до приложения не доходит. Каждый деплой обрывает запросы пользователей, и причину ищут в приложении, хотя она в одной строке Dockerfile.

Всегда используй exec-форму — с квадратными скобками. Если запуск действительно требует оболочки (например, скрипт с подстановкой переменных), последней командой в скрипте пишут exec:

#!/bin/sh
# ... подготовка ...
exec python app.py     # процесс заменит собой оболочку и унаследует PID 1

Обратите внимание, что CMD в §8 записан в shell-форме — как раз тот случай, который стоит исправить.

// шаг 16/22 · теория · ~3 мин

Пользователь, теги и уязвимости

Не root. По умолчанию процесс в контейнере работает от root, и на это ругается Dockle из §10. Изоляция контейнера не абсолютна: связка «root внутри» и уязвимость в среде исполнения — это уже путь к хосту.

RUN adduser -D -u 10001 appuser
USER appuser

Порядок важен: всё, что требует прав (установка пакетов), делается до USER, всё остальное — после. Если приложение слушает порт ниже 1024, порт меняют на высокий — от непривилегированного пользователя занять 80-й нельзя.

Теги. FROM nginx:latest из §8 — то, за что Dockle тоже выдаёт предупреждение. latest не фиксирует ничего: сегодня это одна версия, через месяц другая, и сборка, работавшая вчера, ломается сегодня без единого изменения в коде. Правильно указывать конкретную версию (nginx:1.27-alpine), а в критичных случаях — цифровой отпечаток (nginx@sha256:...), который не меняется никогда.

То же касается собственных образов: тег latest не даёт понять, что именно развёрнуто, и не позволяет откатиться. Обычно используют версию из тега Git (0.1 Git, §13) или короткий хеш коммита.

Два разных сканера. Dockle проверяет практики — root, отсутствие тега, секреты в переменных. Уязвимости в самих пакетах ищет другой инструмент:

trivy image myserver:1.0
trivy image --severity HIGH,CRITICAL --exit-code 1 myserver:1.0

trivy сверяет установленные пакеты с базой известных уязвимостей. Флаг --exit-code 1 делает его пригодным для пайплайна: сборка падает, если найдено что-то критичное (3.2 CI-CD). Оба инструмента нужны — они отвечают на разные вопросы.

Проверка состояния прямо в образе:

HEALTHCHECK --interval=30s --timeout=3s --start-period=5s \
  CMD wget -qO- http://localhost:8000/healthz || exit 1

Docker будет отмечать контейнер как healthy или unhealthy, а Compose — учитывать это в depends_on. Тот самый эндпоинт из 2.5 Бэкенд-сервис, §11.

// шаг 17/22 · теория · ~2 мин

Данные: тома против bind mount

Аналогия: контейнер — вагон, а данные — груз. Груз не хранят в вагоне, который в любой момент отцепят и отправят в переплавку.

Всё, что записано внутрь контейнера, исчезает вместе с ним. Это не недостаток, а свойство: контейнеры считаются одноразовыми. Данные выносят наружу, и способов два.

Bind mount (то, что в §9) подключает конкретную папку хоста:

docker run -v ./nginx:/etc/nginx/conf.d myserver

Удобен для разработки и конфигов: файл виден и правится с обеих сторон. Минусы — зависит от структуры каталогов конкретной машины и от прав доступа на хосте.

Именованный том управляется самим Docker:

docker volume create pgdata
docker run -v pgdata:/var/lib/postgresql/data postgres:16-alpine

Для данных приложений в проде используют именно его: он переносим, его удобно бэкапить и он не привязан к путям на хосте.

docker volume ls                    # список
docker volume inspect pgdata         # где физически лежит
docker volume prune                   # удалить неиспользуемые — ОСТОРОЖНО
🛑docker volume prune удаляет данные безвозвратно

Команда убирает все тома, не подключённые ни к одному контейнеру. Если база временно остановлена, её том попадает под определение «неиспользуемый». Восстановления нет. Перед любой чисткой стоит посмотреть docker volume ls и убедиться, что среди кандидатов нет ничего ценного — то же правило, что для find ... -delete в 1.4 Метрики и логи, §14.

// шаг 18/22 · итоги · ~2 мин

Если запомнить только главное

  • Контейнер делит ядро ОС с хостом и изолирует только нужное — поэтому он легче и быстрее полноценной виртуальной машины.
  • Каждая инструкция Dockerfile — отдельный кэшируемый слой; избегай лишних отдельных RUN, объединяй команды через &&.
  • docker exec/cp позволяют отлаживать контейнер на лету, но такие правки не сохраняются в образе без явного обновления Dockerfile.
  • nginx как reverse proxy перенаправляет входящие запросы дальше — proxy_pass задаёт, куда именно.
  • Volume (-v) подключает файл/папку хоста внутрь контейнера напрямую — правки применяются без пересборки образа.
  • Dockle проверяет образ на типичные небезопасные практики по CIS Benchmarks.
  • В Docker Compose сервисы видят друг друга по имени сервиса во внутренней сети — необязательно публиковать порт наружу, если сервис нужен только другим контейнерам.
  • Multi-stage build: собирать и запускать — разные задачи. COPY --from=builder берёт из этапа сборки только результат; образ уменьшается в десятки раз, компилятор и исходники в прод не едут.
  • Кеш ломается на первой изменившейся инструкции и всех последующих: зависимости ставят до копирования кода. .dockerignore не даёт лишним файлам ломать кеш и попадать в образ.
  • ENTRYPOINT — команда, CMD — аргументы по умолчанию. Всегда exec-форма с квадратными скобками: при shell-форме PID 1 становится оболочка, SIGTERM не доходит до приложения и корректное завершение не работает.
  • Не root: adduser + USER. Не latest: фиксируй версию базового образа и тегируй свои образы версией или хешем коммита.
  • Dockle проверяет практики, trivy — уязвимости в пакетах. Нужны оба; --exit-code 1 делает сканер пригодным для пайплайна.
  • Данные — только во внешних томах. Именованный том для прода, bind mount для конфигов и разработки. docker volume prune удаляет безвозвратно.

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

💡В портфолио
  • Задания 2, 4 и 5 (свой Dockerfile, тома, проверка образа) — раздел «Контейнеры» в P1.
  • Dockerfile для утилиты из M2 собирается по тем же правилам.

Задание 1 — жизненный цикл

Скачай nginx, запусти с пробросом порта, зайди внутрь через docker exec, поменяй страницу, останови, удали.
Проверка: можешь объяснить, почему после docker rm изменения пропали, и показать слои образа через docker history nginx.

Задание 2 — свой образ

Напиши Dockerfile для Python-сервиса из 2.5 Бэкенд-сервис: slim-база, сначала requirements.txt, потом код, USER не root, HEALTHCHECK, ENTRYPOINT в exec-форме.
Проверка: при изменении только кода пересборка занимает секунды (зависимости из кэша); docker run запускает сервис, docker stop завершает за 1–2 секунды.

Задание 3 — multi-stage

Собери приложение на C или Go в multi-stage: компиляция в полном образе, запуск в alpine или distroless.
Проверка: итоговый образ в десятки раз меньше сборочного (docker images).

Задание 4 — конфиг и данные

Запусти nginx с конфигом через bind mount и PostgreSQL с именованным томом.
Проверка: правка конфига + docker exec nginx nginx -s reload применяется без пересборки; удаление и повторное создание контейнера базы не теряет данные.

Задание 5 — проверка образа

Прогони свой образ через Dockle и Trivy, исправь найденное.
Проверка: нет предупреждений уровня FATAL/WARN в Dockle и критичных уязвимостей с исправлением в Trivy.
