О чём урок

ℹ️Зачем это нужно

DevOps редко пишет Python-приложения с нуля, но постоянно пишет скрипты автоматизации, парсеры логов и мелкие утилиты — и все они опираются ровно на эти базовые кирпичики: ввод-вывод, работа со строками/числами, обход структур данных.

📘Словарик на будущее
  • stdin/stdout — стандартные потоки ввода и вывода; sys.stdin и input() читают из stdin, print() пишет в stdout.
  • Рекурсия — функция, вызывающая сама себя на более простой версии задачи, пока не дойдёт до тривиального случая.
  • Кэширование результатов (мемоизация) — вместо пересчёта одного и того же несколько раз результат один раз сохраняется и переиспользуется.
  • Множество (set) — коллекция без дубликатов; быстрый способ ответить «сколько здесь разных значений».
// шаг 2/20 · теория · ~2 мин

Ввод-вывод: скрипт в конвейере

Аналогия: программа — это чёрный ящик с одной дверью на вход и одной на выход. Если дверь стандартная, ящик можно поставить в любой конвейер рядом с grep, sort и awk.

Большинство утилит DevOps читают данные из stdin и пишут в stdout — тогда их можно соединять конвейером (1.1 Linux, §9). Python-скрипт умеет то же самое:

import sys

total = 0
for line in sys.stdin:                  # читаем построчно, сколько бы строк ни было
    size_kb, path = line.split(maxsplit=1)
    total += int(size_kb)

print(f"Всего: {total / 1024 / 1024:.2f} ГБ")

du -k /var/log/* | python3 sum_sizes.py

for line in sys.stdin читает ввод строка за строкой и не держит его целиком в памяти — скрипт одинаково работает и на десяти строках, и на десяти миллионах. line.split(maxsplit=1) разбивает строку по пробелам, но не больше одного раза: путь с пробелами внутри останется целым. int(size_kb) переводит текст в число — из stdin всегда приходят строки.

:.2f в f-строке — тот же принцип, что и printf "%.2f" в bash (1.3 Bash, §6): фиксированное количество знаков после запятой. Для чтения одной строки с клавиатуры есть input(), но в скриптах автоматизации он встречается редко: скрипт, который ждёт ответа человека, нельзя запустить из cron или пайплайна.

// шаг 3/20 · теория · ~1 мин

Строки и парсинг вручную

Аналогия: int("42") где-то внутри буквально читает строку слева направо, как человек. Написать разбор самому — хорошее упражнение на то, что обычно скрыто внутри готовой функции, и регулярная рабочая задача, когда готовой функции нет.

В конфигах и выводе утилит размеры пишут по-человечески: 512M, 1.5G, 20K. Чтобы сравнить их с порогом, нужны байты:

UNITS = {"": 1, "K": 1024, "M": 1024**2, "G": 1024**3, "T": 1024**4}

def parse_size(text: str) -> int:
    text = text.strip().upper().removesuffix("B")   # '1.5gb' -> '1.5G'
    number, unit = text, ""
    if text and text[-1] in UNITS:
        number, unit = text[:-1], text[-1]
    if not number:
        raise ValueError(f"не указано число: {text!r}")
    return int(float(number) * UNITS[unit])

parse_size("1.5G")   # 1610612736
parse_size("512M")   # 536870912

text[-1] — последний символ строки, text[:-1] — всё, кроме последнего. removesuffix("B") убирает необязательную букву B, если она есть. {text!r} в f-строке печатает значение в кавычках — в сообщении об ошибке сразу видно, если строка была пустой или с лишними пробелами. Словарь UNITS вместо цепочки if/elif — привычный приём: добавить новую единицу — значит добавить одну строку.

Обход в глубину: зависимости сервисов

Аналогия: выключили базу — что ещё сломается? Чтобы ответить, идёшь от базы к сервисам, которые от неё зависят, потом к сервисам, которые зависят от них, и так далее, пока цепочка не кончится.

Зависимости удобно хранить словарём «сервис → от кого он зависит» и обходить в глубину (DFS):

DEPENDS_ON = {
    "frontend": ["api"],
    "api": ["postgres", "redis", "auth"],
    "auth": ["postgres"],
    "worker": ["redis", "postgres"],
    "postgres": [],
    "redis": [],
}

def affected_by(failed: str) -> set[str]:
    """Все сервисы, которые сломаются вслед за failed."""
    result = set()
    def visit(service):
        for name, deps in DEPENDS_ON.items():
            if service in deps and name not in result:
                result.add(name)
                visit(name)              # идём глубже: кто зависит от этого
    visit(failed)
    return result

affected_by("postgres")   # {'api', 'auth', 'worker', 'frontend'}

Функция visit вызывает сама себя для каждого найденного зависимого сервиса — так обход уходит вглубь цепочки. Проверка name not in result — защита от повторов и бесконечного цикла, если в зависимостях есть кольцо. Тот же обход используют Docker Compose (depends_on), systemd (After=) и Terraform, когда решают, в каком порядке поднимать сервисы (4.4 Terraform, §1).

Рекурсия и запоминание результатов

Аналогия: чтобы найти файл в дереве папок, открываешь папку, а в ней — каждую вложенную папку тем же способом. Одно правило, применённое к самому себе, обходит дерево любой глубины.

Конфиги в YAML и JSON — это вложенные словари. Часто их нужно «распрямить» в плоский список ключей — например, чтобы сравнить два окружения построчно:

def flatten(config: dict, prefix: str = "") -> dict:
    flat = {}
    for key, value in config.items():
        path = f"{prefix}.{key}" if prefix else key
        if isinstance(value, dict):
            flat.update(flatten(value, path))     # вложенный словарь — рекурсия
        else:
            flat[path] = value
    return flat

flatten({"db": {"host": "10.0.2.21", "port": 5432}, "debug": False})
# {'db.host': '10.0.2.21', 'db.port': 5432, 'debug': False}

У рекурсии всегда два случая: базовый (значение — не словарь, просто записываем) и рекурсивный (словарь — разбираем тем же способом). Без базового случая функция вызывала бы себя бесконечно, пока Python не остановит её ошибкой RecursionError.

Вторая идея раздела — не считать одно и то же дважды. Если функция дорогая (запрос к API, DNS, тяжёлый расчёт), а вызывают её с одними и теми же аргументами, результат запоминают:

from functools import lru_cache
import socket

@lru_cache(maxsize=1024)
def resolve(host: str) -> str:
    return socket.gethostbyname(host)     # сетевой запрос — только при первом вызове

for line in log_lines:
    ip = resolve(line.host)               # повторные имена берутся из памяти

@lru_cache — декоратор: он оборачивает функцию и хранит результаты последних 1024 разных вызовов. Этот же приём в алгоритмах называют динамическим программированием: сохранить решение подзадачи и переиспользовать, вместо того чтобы пересчитывать. Ограничение одно: так можно кэшировать только функции, результат которых зависит лишь от аргументов.

JSON и структуры данных

Аналогия: JSON — это просто вложенные словари и списки Python, только записанные текстом для передачи между программами. Почти любой API и почти любая утилита с флагом --output json говорит на нём.

import json

with open("inventory.json", encoding="utf-8") as f:
    servers = json.load(f)
# [{"name": "web-1", "zone": "a", "ram_gb": 4, "role": "web"}, ...]

big = [s for s in servers if s["ram_gb"] >= 8]
big.sort(key=lambda s: (s["zone"], -s["ram_gb"]))

print(json.dumps(big, indent=2, ensure_ascii=False))

sort(key=...) сортирует по конкретному полю словаря: параметр key принимает функцию, которая для каждого элемента вычисляет значение для сравнения. lambda s: (s["zone"], -s["ram_gb"]) — короткая безымянная функция, которая возвращает кортеж: сначала сортировка по зоне, а внутри зоны — по памяти по убыванию (минус переворачивает порядок для чисел). lambda уместна для таких коротких одноразовых функций, которые нужны только в одном месте. ensure_ascii=False — чтобы русские буквы не превращались в \uXXXX.

Запись [s for s in servers if ...] — списковое включение с условием (2.1 Python, §9): новый список только из подходящих элементов.

Множества: сравнить два сервера

Аналогия: два списка гостей сверяют не построчно, а как множества: кто есть в обоих, кто только в первом, кто только во втором.

«На staging работает, на prod нет» — часто потому, что окружения разошлись. Множества сравнивают их одной строкой:

import subprocess

def packages(host: str) -> set[str]:
    out = subprocess.run(["ssh", host, "dpkg-query", "-W", "-f=${Package}\\n"],
                         capture_output=True, text=True, check=True).stdout
    return set(out.split())

staging, prod = packages("staging-1"), packages("prod-1")

print("только на staging:", sorted(staging - prod))
print("только на prod:   ", sorted(prod - staging))
print("общих пакетов:", len(staging & prod))

- — разность множеств (что есть в первом, но нет во втором), & — пересечение, | — объединение. Перевод списка в set к тому же убирает дубликаты: len(set(items)) — самый быстрый способ узнать число уникальных значений. Как устроен вызов внешней команды через subprocess, разобрано в §14.

Перебор вариантов: itertools

Аналогия: подобрать из нескольких тарифов облака такой набор машин, чтобы хватило мощности и вышло дешевле всего, — как собрать покупку из разных упаковок товара с минимальной итоговой ценой.

Когда вариантов немного, честный перебор — нормальное решение. itertools делает его без вложенных циклов:

from itertools import combinations_with_replacement

FLAVORS = [            # (название, vCPU, рублей в месяц)
    ("s-2", 2, 1900),
    ("s-4", 4, 3500),
    ("s-8", 8, 6600),
]

def cheapest(required_cpu: int, max_machines: int = 3):
    best = None
    for n in range(1, max_machines + 1):
        for combo in combinations_with_replacement(FLAVORS, n):
            cpu = sum(f[1] for f in combo)
            cost = sum(f[2] for f in combo)
            if cpu >= required_cpu and (best is None or cost < best[0]):
                best = (cost, [f[0] for f in combo])
    return best

cheapest(10)   # (8500, ['s-2', 's-8'])

combinations_with_replacement(FLAVORS, n) перебирает все наборы из n тарифов, где один тариф может повторяться: (s-2, s-2), (s-2, s-4) и так далее, без повторения одного и того же набора в другом порядке. sum(f[1] for f in combo) — сумма по генератору (2.1 Python, §9). Рядом в модуле есть combinations (без повторов), permutations (с учётом порядка) и product (все сочетания из нескольких списков).

Обработка ошибок и валидация ввода

Аналогия: хороший скрипт не падает молча и не падает с непонятной трассировкой — он говорит человеческим языком, что именно не так со входными данными.

import sys

try:
    n = int(input())
    if n <= 0:
        raise ValueError("ожидалось натуральное число")
except ValueError as e:
    print(f"Ошибка ввода: {e}", file=sys.stderr)
    sys.exit(1)

Важно проверять именно то, что просит задача, а не ловить любое исключение молча. Две детали, отличающие рабочий скрипт от учебного: сообщение уходит в stderr (file=sys.stderr), чтобы не смешиваться с полезным выводом, и завершение идёт через sys.exit(1), а не через встроенный exit() — последний предназначен для интерактивной консоли и в скриптах его использовать не принято.

Сложность алгоритма: почему это не мелочь

Аналогия: искать нужную книгу в куче на полу (проверяя каждую по очереди) и искать её в библиотеке с алфавитным каталогом — работа с одной и той же целью, но по времени это две разные вселенные, когда книг миллион, а не десять.

Big O — это способ сказать, как время работы программы растёт с ростом объёма данных, не привязываясь к конкретному железу.

Обозначение Что значит Пример из этого урока
O(1) не зависит от размера входа взять элемент по индексу списка
O(n) растёт линейно пройти список один раз
O(n²) растёт квадратично для каждого сервиса перебрать все остальные (§3)
O(2ⁿ) взрывной рост перебор всех подмножеств тарифов (§7) при большом их числе

Обход из §3 устроен на O(n²): для каждого найденного сервиса он перебирает весь словарь. Для десятка сервисов это неважно, для тысяч — заметно, и тогда заранее строят обратный словарь «сервис → кто от него зависит», чтобы каждый шаг стоил O(1). Перебор из §7 растёт ещё быстрее: каждый новый тариф умножает число вариантов, поэтому полный перебор годится, только пока вариантов десятки, а не тысячи. Кэш из §4 существует ровно затем, чтобы не платить дважды за одинаковую работу.

💡Лайфхак

На собеседовании фраза «какая сложность у вашего решения?» — почти всегда следующий вопрос после «работает ли код». Уметь на глаз оценить, что вложенный цикл — это O(n²), а set() — O(1) на проверку присутствия элемента, — базовый навык, который ждут даже от Python-скриптов автоматизации, а не только от алгоритмических задач.

Регулярные выражения


Аналогия: регулярка — это шаблон-трафарет, который прикладывают к тексту: где совпало по форме, оттуда и вынимают содержимое.

Для DevOps это главный инструмент разбора логов: строки в них почти всегда имеют жёсткую структуру, но разбить их простым split() не выйдёт — мешают поля в кавычках с пробелами внутри.

import re

LOG = re.compile(
    r'(?P<ip>\S+) \S+ \S+ \[(?P<time>[^\]]+)\] '
    r'"(?P<method>\w+) (?P<path>\S+)[^"]*" (?P<code>\d{3}) (?P<size>\d+)'
)

line = '203.0.113.5 - - [21/Jul/2026:14:32:10 +0000] "GET /index.html HTTP/1.1" 200 512'
m = LOG.match(line)
if m:
    print(m["ip"], m["code"], m["path"])     # 203.0.113.5 200 /index.html

Кирпичики, из которых всё собирается: \d — цифра, \s — пробельный символ, \w — буква или цифра, \S — любой непробельный (заглавная буква означает «наоборот»). Дальше идут количественные: + — один или больше, * — ноль или больше, ? — ноль или один, {3} — ровно три. Квадратные скобки задают набор символов, а ^ внутри них означает «кроме»: [^\]]+ читается как «сколько угодно любых символов, кроме закрывающей скобки».

(?P<имя>...) — именованная группа: то, что попало внутрь, потом достаётся по имени через m["ip"]. Без имён пришлось бы считать группы по номерам и путаться при каждой правке шаблона.

Префикс r перед строкой (r'...') отключает обработку обратного слеша самим Python — без него \d пришлось бы писать как \\d. В регулярках его пишут всегда.

⚠️Жадность

По умолчанию .+ захватывает как можно больше: на строке с двумя парами кавычек шаблон ".+" съест всё от первой кавычки до последней. Лечится либо ленивым вариантом .+?, либо, что надёжнее, точным описанием «всё, кроме кавычки» — [^"]+. Это причина примерно половины загадок вида «регулярка вроде правильная, но вытаскивает не то».

Полезные функции: re.match проверяет с начала строки, re.search ищет в любом месте, re.findall возвращает все совпадения списком, re.sub заменяет. Скомпилированный через re.compile шаблон работает быстрее, если применяется в цикле к миллионам строк.

Дата и время

Аналогия: время в логах — это текст, а сравнивать и вычитать можно только настоящие даты. Между ними нужен переводчик.

from datetime import datetime, timedelta, timezone

# из строки лога в объект
t = datetime.strptime("21/Jul/2026:14:32:10 +0000", "%d/%b/%Y:%H:%M:%S %z")

# обратно в текст
t.strftime("%Y-%m-%d %H:%M")          # '2026-07-21 14:32'

# арифметика
now = datetime.now(timezone.utc)
hour_ago = now - timedelta(hours=1)
if t > hour_ago:
    print("свежая запись")

# сколько прошло
delta = now - t
print(delta.total_seconds())

strptime — «строку в дату» (p = parse), strftime — «дату в строку» (f = format). Порядок букв путается постоянно, мнемоника простая: parse читает, format пишет.

timedelta — промежуток времени; его можно складывать с датами и вычитать из них. Именно так фильтруют логи «за последний час», не разбирая строки вручную.

⚠️Часовые пояса — источник тихих багов

datetime.now() без аргумента возвращает «наивное» время без пояса, и сравнить его с датой из лога, где пояс указан, нельзя — Python выдаст TypeError. Правило для серверного кода: работать всегда в UTC и с осведомлёнными о поясе объектами — datetime.now(timezone.utc). Это то же соображение, из-за которого на серверах ставят UTC (1.1 Linux, §14): иначе логи с разных машин невозможно сопоставить.

collections: Counter и defaultdict

Аналогия: готовые контейнеры под задачи, которые иначе приходится собирать руками каждый раз заново.

from collections import Counter, defaultdict

codes = [200, 404, 200, 500, 200, 404]

# было
counts = {}
for c in codes:
    counts[c] = counts.get(c, 0) + 1

# стало
counts = Counter(codes)              # Counter({200: 3, 404: 2, 500: 1})
counts.most_common(2)                 # [(200, 3), (404, 2)]

# группировка без проверок «а есть ли уже такой ключ»
by_ip = defaultdict(list)
for ip, path in requests:
    by_ip[ip].append(path)            # список создаётся сам при первом обращении

Counter — словарь, который умеет считать, и его most_common(n) сразу выдаёт топ-N. Это буквально готовая замена связке sort | uniq -c | sort -rn | head из 1.4 Метрики и логи, только результат остаётся структурой данных, с которой можно работать дальше.

defaultdict(list) избавляет от вечной проверки «есть ли уже такой ключ» перед добавлением в список. Аргумент — функция, создающая значение по умолчанию: list для списков, int для счётчиков, set для множеств.

Генераторы и ленивая обработка


Аналогия: список — цистерна, которую надо целиком заполнить, прежде чем начать пить. Генератор — кран: вода идёт по мере надобности, и в трубе всегда ровно один стакан.

Разница проявляется на больших файлах, а логи в эксплуатации бывают на десятки гигабайт:

lines = [l for l in open("huge.log")]     # ✘ весь файл в память — скрипт убьёт OOM killer
lines = (l for l in open("huge.log"))      # ✔ по строке за раз, память постоянна

Одна круглая скобка вместо квадратной решает, упадёт скрипт или нет. Свой генератор пишут через yield:

def errors(path):
    """Отдаёт по одной строке с ошибкой, не загружая файл целиком."""
    with open(path, encoding="utf-8") as f:
        for line in f:
            if " 5" in line:
                yield line.rstrip()

for line in errors("/var/log/nginx/access.log"):
    print(line)

yield — как return, но функция не завершается, а «замирает» до следующего запроса значения. Такие функции удобно составлять в цепочки: один генератор читает, второй фильтрует, третий разбирает — и всё это работает потоком, ничего не накапливая.

Цена: генератор можно пройти только один раз, и у него нет длины — len() выдаст ошибку. Нужно пройти дважды или узнать количество — данные придётся материализовать в список.

subprocess — запуск команд из Python

Аналогия: мост между двумя мирами: Python хорош в логике и структурах данных, а системные утилиты — в работе с системой. subprocess позволяет пользоваться и тем и другим.

import subprocess

result = subprocess.run(
    ["systemctl", "is-active", "nginx"],
    capture_output=True, text=True, timeout=10
)
print(result.returncode)      # 0 если активен
print(result.stdout.strip())   # 'active'

# упасть, если команда вернула ошибку
subprocess.run(["nginx", "-t"], check=True)

Что здесь важно. Команда передаётся списком аргументов, а не одной строкой — так пробелы и спецсимволы в путях не ломают разбор. capture_output=True забирает вывод вместо печати на экран, text=True отдаёт его строками, а не байтами. timeout спасает от зависшей навсегда команды. check=True возбуждает исключение при ненулевом коде — аналог set -e.

🛑shell=True — дыра в безопасности
subprocess.run(f"ping -c 1 {host}", shell=True)   # ✘ никогда так не делай

С shell=True строка передаётся оболочке целиком, и если host пришёл извне, значение 8.8.8.8; rm -rf / выполнится буквально. Это классическая инъекция команд. Правильно — списком: subprocess.run(["ping", "-c", "1", host]); тогда значение попадает как один аргумент и оболочка не участвует вовсе.

Практическая граница: если задача решается штатной библиотекой Python — решай ею, а не вызовом утилиты. shutil.disk_usage() надёжнее, чем разбор вывода df, а pathlib — чем вызов find. subprocess берут там, где готового аналога нет: systemctl, docker, kubectl, git.

Если запомнить только главное

  • Скрипт читает sys.stdin построчно и пишет в stdout — тогда его можно ставить в конвейер рядом с grep и awk.
  • Рекурсия — базовый случай плюс вызов себя для вложенной части; обход в глубину находит всё, что зависит от упавшего сервиса. @lru_cache — «не пересчитывай то, что уже посчитал».
  • set() — мгновенный подсчёт уникальных значений и сравнение окружений через -, &, |.
  • Проверяй конкретные ошибки ввода и сообщай о них в stderr с кодом выхода 1, а не лови все исключения подряд.
  • Когда вариантов мало — честный перебор (itertools) проще и надёжнее, чем преждевременная оптимизация.
  • Регулярки: \d \s \w и количественные + * ? {n}; именованные группы (?P<имя>...); префикс r'...' всегда; помни про жадность .+.
  • strptime читает строку в дату, strftime пишет дату в строку. На серверах работай в UTC с поясом, иначе сравнение дат упадёт.
  • Counter — готовая замена sort | uniq -c | sort -rn, defaultdict(list) — группировка без проверок на существование ключа.
  • Круглые скобки вместо квадратных превращают список в генератор: память постоянна на файле любого размера. Цена — один проход и отсутствие len().
  • subprocess.run — только списком аргументов. shell=True с внешними данными — инъекция команд.

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

  • Регулярные выражения, subprocess и работа со временем из заданий 2–5 — всё это понадобится в M2: утилита разбирает даты сертификатов и формирует отчёт.

Задание 1 — парсинг конфигурации

Напиши функцию, которая разбирает строки KEY=value с комментариями # и пустыми строками в словарь, а некорректные строки сообщает с номером строки.
Проверка: pytest-тесты на пустой файл, комментарии, значение со знаком = внутри, строку без =.

Задание 2 — регулярные выражения по логам

Регулярным выражением с именованными группами разбери строку лога nginx на IP, дату, метод, путь, код и размер.
Проверка: выражение проверено на regex101 и в коде на 5 разных строках, включая строку с запросом - (битый запрос).

Задание 3 — генератор для большого файла

Напиши генератор, который отдаёт только строки с ошибками 5xx из лога, и посчитай через collections.Counter самые частые пути.
Проверка: обработка файла на 2 ГБ не увеличивает память процесса больше чем на несколько мегабайт (/usr/bin/time -v).

Задание 4 — subprocess

Из Python вызови df -P, разбери вывод и выведи разделы, занятые больше чем на 80%. Используй subprocess.run со списком аргументов, check=True, capture_output=True, text=True.
Проверка: при несуществующей команде скрипт ловит исключение и пишет понятную ошибку; нигде нет shell=True.

Задание 5 — время в UTC

Напиши функцию, которая принимает время из лога (10/Oct/2026:13:55:36 +0300) и возвращает его в UTC в формате ISO 8601.
Проверка: тест с тремя разными часовыми поясами даёт ожидаемые значения.
