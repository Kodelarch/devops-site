О чём урок

ℹ️Зачем это нужно

В 4.2 Облако машины, сети и базы создавались командами или кликами в консоли облака. Через месяц такой работы никто не может сказать, какие ресурсы существуют, зачем они нужны и как воссоздать окружение с нуля. Стоит потерять один аккаунт или случайно удалить сеть — и восстановление превращается в археологию.

Terraform описывает инфраструктуру в текстовых файлах: какие сети, машины, балансировщики и базы должны существовать. Инструмент сам сравнивает описание с реальностью и создаёт, меняет или удаляет ресурсы, чтобы привести облако к описанному виду. Описание лежит в git, проходит ревью и воспроизводит окружение одной командой.

Terraform — стандарт де-факто для инфраструктуры как кода: он есть почти в каждой вакансии, где упоминается облако. После смены лицензии в 2023 году сообщество выпустило совместимый открытый форк OpenTofu; команды и синтаксис у них одинаковые, и всё, что написано ниже, применимо к обоим.

📘Словарик на будущее
  • IaC (Infrastructure as Code) — описание инфраструктуры в файлах вместо ручных действий.
  • Провайдер — плагин, который знает API конкретного облака или сервиса.
  • Ресурс (resource) — объект, которым управляет Terraform: машина, сеть, запись DNS.
  • Источник данных (data source) — объект, который Terraform только читает, но не создаёт.
  • Состояние (state) — файл, где Terraform помнит, какие ресурсы он создал и с какими параметрами.
  • План (plan) — список изменений, которые Terraform собирается сделать.
  • Модуль — переиспользуемый набор ресурсов с входными переменными и выходными значениями.
  • Дрейф (drift) — расхождение реальной инфраструктуры с описанием в коде.

Декларативный подход

Аналогия: заказ в ресторане. Ты говоришь «хочу пасту карбонара», а не «поставь кастрюлю, налей воды, включи огонь». Как именно её приготовить — забота кухни.

Есть два способа описывать инфраструктуру:

  • Императивный — последовательность команд: «создай сеть, затем подсеть, затем машину». Скрипт на bash с вызовами yc или aws. Повторный запуск создаст вторую копию всего, а удалить лишнее он не умеет.
  • Декларативный — описание результата: «должна быть сеть, в ней подсеть, в подсети две машины». Инструмент сам вычисляет, какие действия нужны, чтобы реальность совпала с описанием.

Terraform декларативный. Это даёт три важных свойства:

Повторный запуск безопасен. Если всё уже создано, Terraform ничего не делает — та же идемпотентность, что в 4.3 Ansible, §6.

Удаление — тоже изменение кода. Убрал ресурс из файла — Terraform удалит его из облака. Скрипты так не умеют, и именно поэтому в облаке копятся забытые ресурсы, о которых шла речь в 4.2 Облако, §10.

Порядок вычисляется сам. Terraform строит граф зависимостей: подсеть ссылается на сеть, значит сеть создаётся первой. Независимые ресурсы создаются параллельно.

Язык HCL: блоки и ссылки

Аналогия: анкета с полями. Каждый блок — отдельная анкета, а поля одной анкеты могут ссылаться на номер другой.

Конфигурация пишется на HCL (HashiCorp Configuration Language) в файлах .tf. Terraform читает все .tf в каталоге как одно целое, поэтому их разбивают по смыслу:

infra/
  versions.tf     # версии Terraform и провайдеров
  providers.tf    # настройки провайдеров
  variables.tf    # входные переменные
  network.tf      # сеть
  compute.tf      # машины
  outputs.tf      # выходные значения
  terraform.tfvars

Минимальная конфигурация для Yandex Cloud:

# versions.tf
terraform {
  required_version = ">= 1.6"
  required_providers {
    yandex = {
      source  = "yandex-cloud/yandex"
      version = "~> 0.130"
    }
  }
}

# providers.tf
provider "yandex" {
  folder_id = var.folder_id
  zone      = "ru-central1-a"
}

# network.tf
resource "yandex_vpc_network" "main" {
  name = "main"
}

resource "yandex_vpc_subnet" "private_a" {
  name           = "private-a"
  zone           = "ru-central1-a"
  network_id     = yandex_vpc_network.main.id
  v4_cidr_blocks = ["10.0.1.0/24"]
}

Строка network_id = yandex_vpc_network.main.id — ссылка: «возьми ID той сети, которую создашь выше». По таким ссылкам Terraform и строит граф зависимостей. Формат ссылки всегда <тип_ресурса>.<имя>.<атрибут>.

Для AWS всё выглядит так же, меняются только имена типов ресурсов (aws_vpc, aws_subnet, aws_instance). Принципы из 4.2 Облако переносятся один в один.

// шаг 4/19 · теория · ~3 мин

Рабочий цикл: init, plan, apply, destroy

Аналогия: ремонт по смете. Сначала смета (plan), её согласование, потом работы (apply). Никто не начинает ломать стены без сметы.

terraform init        # скачать провайдеры, настроить бэкенд состояния
terraform fmt         # отформатировать код
terraform validate    # проверить синтаксис и ссылки
terraform plan        # показать, что будет сделано
terraform apply       # применить (снова покажет план и спросит подтверждение)
terraform destroy     # удалить всё, что описано

Вывод plan — главное, что нужно научиться читать:

  # yandex_compute_instance.web[1] will be created
  + resource "yandex_compute_instance" "web" { ... }

  # yandex_vpc_subnet.private_a will be updated in-place
  ~ resource "yandex_vpc_subnet" "private_a" { ... }

  # yandex_compute_instance.db must be replaced
-/+ resource "yandex_compute_instance" "db" { ... }

Plan: 1 to add, 1 to change, 1 to destroy.
  • + — создать.
  • ~ — изменить на месте, ресурс сохранится.
  • -/+ — пересоздать: удалить старый и создать новый. Для машины с данными это потеря данных.
  • - — удалить.
🛑Всегда читай план перед apply

Некоторые параметры нельзя изменить у существующего ресурса — например, зону размещения машины или имя базы. Terraform в таком случае тихо планирует пересоздание. Строчка must be replaced у базы данных означает удаление базы со всем содержимым. Правило: apply только после того, как прочитал план целиком, а в CI план выводится в merge request и смотрится на ревью.

Для защиты критичных ресурсов есть блок lifecycle:

resource "yandex_mdb_postgresql_cluster" "main" {
  # ...
  lifecycle {
    prevent_destroy = true   # plan упадёт с ошибкой, если ресурс решат удалить
  }
}

Состояние: память Terraform

Аналогия: инвентарная книга склада. Без неё на складе лежат вещи, но непонятно, какие из них твои, а какие соседа.

После apply Terraform записывает в файл terraform.tfstate, какие ресурсы он создал, их ID в облаке и все атрибуты. При следующем plan он сравнивает три вещи: код, состояние и реальность.

Отсюда следствия, которые важно понимать:

  • Terraform управляет только тем, что есть в состоянии. Машину, созданную руками в консоли, он не видит и не тронет.
  • Потеря состояния — катастрофа. Ресурсы в облаке останутся, но Terraform о них забудет и при следующем apply попытается создать их заново (с конфликтами имён) или оставит висеть без управления.
  • Состояние содержит секреты. Пароли баз, ключи и токены хранятся в нём открытым текстом. Поэтому terraform.tfstate никогда не коммитят в git.
# .gitignore
.terraform/
*.tfstate
*.tfstate.*
*.tfvars        # если в них есть секреты
crash.log

Но .terraform.lock.hcl коммитят обязательно: в нём зафиксированы точные версии провайдеров, как package-lock.json или requirements.txt с версиями.

// шаг 6/19 · теория · ~1 мин

Удалённое состояние и блокировки

Аналогия: общая тетрадь учёта, которая лежит в сейфе у администратора. Записать в неё может только один человек одновременно — остальные ждут.

Пока с инфраструктурой работает один человек, локальный файл состояния терпим. В команде он не работает: у каждого своя версия, и два одновременных apply портят инфраструктуру.

Решение — удалённый бэкенд: состояние хранится в объектном хранилище (4.2 Облако, §6), а для блокировки используется отдельный механизм.

terraform {
  backend "s3" {
    bucket       = "my-company-tfstate"
    key          = "prod/network/terraform.tfstate"
    region       = "ru-central1"
    endpoints    = { s3 = "https://storage.yandexcloud.net" }
    use_lockfile = true      # блокировка через объект в бакете
    skip_region_validation      = true
    skip_credentials_validation = true
    skip_requesting_account_id  = true
  }
}

Требования к бакету для состояния:

  • Версионирование включено — чтобы откатиться, если состояние испортилось.
  • Доступ закрыт — состояние содержит секреты.
  • Шифрование включено.

Блокировка гарантирует, что пока один apply идёт, второй дождётся или упадёт с понятной ошибкой. В GitLab есть встроенный HTTP-бэкенд для состояния Terraform — удобно, если инфраструктура и так живёт в GitLab (6.1 CI-CD в Kubernetes).

// шаг 7/19 · теория · ~2 мин

Переменные, локальные значения и выходы

Аналогия: функция в программировании: параметры на входе, вычисления внутри, результат на выходе.

Входные переменные делают конфигурацию настраиваемой:

# variables.tf
variable "folder_id" {
  type        = string
  description = "ID каталога в Yandex Cloud"
}

variable "web_count" {
  type    = number
  default = 2
  validation {
    condition     = var.web_count >= 1 && var.web_count <= 10
    error_message = "От 1 до 10 веб-серверов."
  }
}

variable "db_password" {
  type      = string
  sensitive = true      # не печатать в выводе plan/apply
}

Значения задаются в terraform.tfvars, флагом -var или переменными окружения TF_VAR_имя. Последний способ удобен для секретов в CI.

Локальные значения — вычисления внутри конфигурации, чтобы не повторяться:

locals {
  common_labels = {
    project = "shop"
    env     = var.env
    owner   = "devops"
  }
}

Те самые обязательные теги из 4.2 Облако, §10 — описанные один раз и проставленные на все ресурсы.

Выходы — то, что конфигурация отдаёт наружу:

# outputs.tf
output "web_ips" {
  value = yandex_compute_instance.web[*].network_interface[0].ip_address
}

После apply их показывает terraform output. Типичное использование — передать адреса созданных машин в инвентарь Ansible.

Несколько одинаковых ресурсов: count и for_each

Аналогия: печать визиток. Не рисовать каждую вручную, а задать шаблон и количество.

# count: N одинаковых ресурсов, обращение по номеру
resource "yandex_compute_instance" "web" {
  count = var.web_count
  name  = "web-${count.index + 1}"
  # ...
}

# for_each: ресурс на каждый элемент словаря, обращение по ключу
variable "subnets" {
  default = {
    a = { zone = "ru-central1-a", cidr = "10.0.1.0/24" }
    b = { zone = "ru-central1-b", cidr = "10.0.2.0/24" }
  }
}

resource "yandex_vpc_subnet" "private" {
  for_each       = var.subnets
  name           = "private-${each.key}"
  zone           = each.value.zone
  v4_cidr_blocks = [each.value.cidr]
  network_id     = yandex_vpc_network.main.id
}

Выбор между ними важнее, чем кажется:

⚠️count и удаление из середины

С count ресурсы адресуются по номеру: web[0], web[1], web[2]. Если удалить элемент из середины списка, номера сдвинутся, и Terraform решит пересоздать все ресурсы после него. С for_each адрес — ключ (private["a"]), и удаление одного элемента не трогает остальные. Правило: count — для действительно одинаковых ресурсов, где важно только количество; for_each — когда у каждого есть своё имя или параметры.

Подсети в двух зонах из примера — это ровно правило «минимум две зоны доступности» из 4.2 Облако, §2, записанное кодом.

// шаг 9/19 · теория · ~1 мин

Источники данных: читать, а не создавать

Аналогия: справочник. Ты не издаёшь его, а только смотришь нужный номер.

Не всё нужно создавать. Образ ОС, существующая сеть, созданная другой командой, текущий каталог — их нужно только прочитать:

data "yandex_compute_image" "ubuntu" {
  family = "ubuntu-2404-lts"
}

resource "yandex_compute_instance" "web" {
  boot_disk {
    initialize_params {
      image_id = data.yandex_compute_image.ubuntu.id   # всегда свежий образ семейства
    }
  }
  # ...
}

Источник данных выполняется при каждом plan и возвращает актуальное значение. С образами это палка о двух концах: при выходе нового образа Terraform захочет пересоздать машины. Для продакшена образ часто фиксируют конкретным ID.

// шаг 10/19 · теория · ~2 мин

Модули: переиспользование

Аналогия: типовой проект — тот же принцип, что и роли в 4.3 Ansible, §10.

Модуль — каталог с .tf файлами, который вызывают из другой конфигурации с параметрами:

module "network" {
  source  = "./modules/network"
  name    = "prod"
  subnets = var.subnets
}

module "web" {
  source    = "./modules/vm-group"
  count_vm  = 3
  subnet_id = module.network.subnet_ids["a"]
}

Внутри модуля — свои variables.tf (вход) и outputs.tf (выход). Модули бывают локальные, из git-репозитория (source = "git::https://...?ref=v1.2.0") или из публичного реестра.

Типичная структура проекта с несколькими окружениями:

modules/
  network/
  vm-group/
  postgres/
envs/
  dev/      main.tf  terraform.tfvars  backend.tf
  staging/  main.tf  terraform.tfvars  backend.tf
  prod/     main.tf  terraform.tfvars  backend.tf

Код ресурсов описан один раз в модулях, окружения отличаются только параметрами и отдельным файлом состояния. Отдельное состояние на окружение — принципиально: ошибка в dev не должна уметь задеть prod.

Ещё одно правило: версию модуля фиксируют. Модуль, подключённый из ветки main, однажды изменится, и следующий plan неожиданно захочет пересоздать половину инфраструктуры.

// шаг 11/19 · теория · ~1 мин

Импорт и дрейф

Аналогия: инвентаризация. Что-то на складе есть, но в книге не записано — значит, надо внести. Что-то записано, но переложено — надо вернуть на место.

Импорт. Ресурс уже существует (создан руками до появления Terraform), и его нужно взять под управление:

import {
  to = yandex_vpc_network.main
  id = "enp1234567890abcdef"
}

После terraform plan -generate-config-out=generated.tf Terraform сам напишет описание ресурса по его текущему состоянию. Сгенерированный код потом причёсывают руками.

Дрейф. Кто-то поменял ресурс в консоли облака — открыл порт в группе безопасности «на минутку». Следующий plan покажет изменение: Terraform захочет вернуть всё как в коде. Это и хорошо (дрейф виден), и опасно (если правка была аварийной и нужной, её затрут).

Для регулярной проверки дрейфа в CI запускают terraform plan -detailed-exitcode по расписанию: код выхода 2 означает, что реальность расходится с кодом.

💡Правило команды про ручные правки

Ручная правка в консоли допустима только в аварии — и сразу после неё изменение переносится в код. Иначе следующий apply от коллеги молча откатит твой фикс в самый неподходящий момент.

// шаг 12/19 · теория · ~2 мин

Terraform в CI/CD

Аналогия: двухэтапное согласование: сначала смету смотрят на совещании, подписывают — и только потом начинаются работы.

Типовой пайплайн для инфраструктуры:

stages: [validate, plan, apply]

validate:
  stage: validate
  script:
    - terraform fmt -check
    - terraform init -backend=false
    - terraform validate

plan:
  stage: plan
  script:
    - terraform init
    - terraform plan -out=tfplan
  artifacts:
    paths: [tfplan]

apply:
  stage: apply
  script:
    - terraform init
    - terraform apply tfplan     # применяется ровно тот план, что смотрели
  when: manual
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

Ключевые моменты:

  • План сохраняется в файл (-out) и применяется именно он. Иначе между ревью и apply кто-то мог поменять инфраструктуру, и применится не то, что смотрели.
  • Apply — вручную и только из основной ветки, по аналогии со стадией staging в 6.1 CI-CD в Kubernetes.
  • Учётные данные облака — у раннера через сервисный аккаунт с ограниченными правами или через защищённые переменные (3.2 CI-CD, §11). Ни в коем случае не в репозитории.
  • В merge request выводят план — ревьюер видит не только код, но и что именно изменится в облаке.

Для проверки безопасности конфигурации существуют сканеры вроде Checkov, tfsec (сейчас часть Trivy): они находят открытые наружу группы безопасности, публичные бакеты и незашифрованные диски до того, как ресурсы созданы (6.2 DevSecOps).

// шаг 13/19 · теория · ~1 мин

Terraform и Ansible вместе

Аналогия: бригада строителей сдаёт дом с ключами и планом, а отделочники по этому плану заходят в каждую квартиру.

Типовая связка из 4.3 Ansible, §13:

  1. Terraform создаёт сеть, машины, балансировщик и базу.
  2. Выходные значения (IP машин) превращаются в инвентарь Ansible.
  3. Ansible настраивает машины.

Связать можно разными способами: шаблоном инвентаря через ресурс local_file, динамическим инвентарём Ansible по тегам облака или выводом terraform output -json, который читает скрипт. Самый чистый вариант для облака — динамический инвентарь по тегам: Terraform ставит на машины теги role=web, Ansible по этим тегам их находит, и прямой связи между инструментами нет.

Начальную настройку машины (создать пользователя, положить SSH-ключ) часто делают ещё при создании через cloud-init — параметр user_data в описании машины. Остальное — Ansible.

resource "yandex_compute_instance" "web" {
  metadata = {
    user-data = templatefile("${path.module}/cloud-init.yaml", {
      ssh_key = file("~/.ssh/id_ed25519.pub")
    })
  }
}
// шаг 14/19 · теория · ~1 мин

Типичные ошибки

Аналогия: список «как не надо», собранный из чужих инцидентов.

  • Состояние в git. Вместе с паролями от баз. Удалить из истории потом очень сложно (0.1 Git).
  • Одно состояние на всё. Dev, staging и prod в одном файле — один неудачный apply задевает всё сразу.
  • apply без чтения плана. Особенно опасно с -auto-approve в скриптах.
  • Версии провайдеров не зафиксированы. Новая мажорная версия провайдера меняет поведение, и plan внезапно предлагает пересоздать половину ресурсов.
  • Ручные правки в консоли. Дрейф копится, и следующий apply либо всё откатит, либо упадёт.
  • Секреты в .tfvars в репозитории. Секреты — через переменные окружения, хранилище секретов или с sensitive = true.
  • Забытый destroy после учебного стенда. Счёт от облака придёт в любом случае (4.2 Облако, §10).
// шаг 15/19 · итоги · ~1 мин

Если запомнить только главное

  • Terraform декларативный: описываешь результат, инструмент сам вычисляет действия и порядок по ссылкам между ресурсами.
  • Цикл: init → plan → apply. План читают целиком, особенно строки must be replaced.
  • Состояние — память Terraform. Не коммитится в git, содержит секреты, хранится в удалённом бэкенде с версионированием и блокировкой.
  • .terraform.lock.hcl коммитят, версии провайдеров и модулей фиксируют.
  • Переменные — вход, locals — вычисления, outputs — результат. Секреты помечают sensitive.
  • for_each безопаснее count, когда у ресурсов есть свои имена: удаление из середины не пересоздаёт соседей.
  • Модули убирают повторы; окружения отличаются параметрами и отдельным состоянием.
  • Существующие ресурсы берут под управление через import, дрейф ловят регулярным plan.
  • В CI: план сохраняется в файл, apply применяет именно его, вручную и только из main.
  • Terraform создаёт инфраструктуру, Ansible её настраивает, cloud-init делает первичную настройку машины.
  • Защита критичных ресурсов — prevent_destroy. Учебные стенды — destroy после занятия.
// шаг 16/19 · практика

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

💡В портфолио
  • Все задания урока — Terraform-часть P2: сеть в двух зонах, машины, удалённое состояние, модули и связка с Ansible.

Задание 1 — первая сеть

Создай аккаунт в Yandex Cloud (грант на старт) и сервисный аккаунт с ролью editor на каталог. Опиши в Terraform сеть и две подсети в разных зонах через for_each.
Проверка: terraform plan показывает 3 to add; после apply повторный plan — No changes. В консоли облака видны сеть и подсети.

Задание 2 — машины и группа безопасности

Добавь две машины через count с образом Ubuntu из источника данных, группу безопасности, разрешающую 22 только с твоего IP и 80 отовсюду, и cloud-init с твоим SSH-ключом. Выведи публичные IP через output.
Проверка: terraform output web_ips показывает два адреса, ssh ubuntu@<ip> пускает по ключу, с чужого IP порт 22 недоступен.

Задание 3 — удалённое состояние

Создай бакет в Object Storage с версионированием и перенеси туда состояние (terraform init -migrate-state).
Проверка: локального terraform.tfstate больше нет, в бакете лежит объект состояния; запусти apply в двух терминалах одновременно — второй должен упереться в блокировку.

Задание 4 — модуль и два окружения

Вынеси сеть и машины в модуль modules/web-stack, создай envs/dev и envs/prod с разным числом машин и разными ключами состояния в бакете.
Проверка: apply в dev не показывает в плане ничего, что относится к prod.

Задание 5 — связка с Ansible

Сгенерируй инвентарь Ansible из terraform output -json (скриптом или ресурсом local_file) и прогони роль common из 4.3 Ansible.
Проверка: одна последовательность terraform apply && ansible-playbook ... поднимает настроенный стенд с нуля. В конце — terraform destroy и проверка в консоли, что ничего не осталось.
