О чём урок

ℹ️Зачем это нужно

Этот урок отличается от остальных: он не про конкретную технологию вроде Docker или Kubernetes, а про инструменты, которыми ты будешь пользоваться в каждом следующем уроке независимо от темы. Git — способ сохранять историю изменений так, чтобы можно было безопасно экспериментировать, откатываться назад и работать над одним проектом вместе с другими людьми. Английский — потому что подавляющее большинство документации, сообщений об ошибках и обсуждений происходит на нём, и ждать перевода на практике не вариант. Agile/Scrum — потому что почти любая команда организует работу именно в этих терминах.

Отдельно про глубину. Разработчику Git нужен, чтобы хранить код. Тебе — чтобы запускать автоматизацию: пайплайн стартует от события в Git, версия релиза берётся из тега, право деплоя в прод определяется настройками ветки. Поэтому здесь разобраны вещи, которые в курсах «git для начинающих» обычно опускают: rebase, reset, revert, теги, Conventional Commits. Ровно их и спрашивают на собеседовании.

📘Словарик на будущее
  • Репозиторий (repository, «репо») — папка проекта, за изменениями в которой следит Git; вся история лежит внутри, в скрытой папке .git.
  • Коммит (commit) — сохранённый снимок состояния файлов в конкретный момент, с сообщением, объясняющим, что изменилось.
  • Ветка (branch) — отдельная линия разработки, существующая параллельно с другими.
  • HEAD — указатель «где я сейчас нахожусь в истории»; обычно указывает на последний коммит текущей ветки.
  • Индекс (staging area) — промежуточная область, куда складываются изменения перед коммитом.
  • Хеш коммита — уникальный идентификатор вида a3f21bc, по которому на коммит можно сослаться.
  • Pull Request / Merge Request (PR/MR) — запрос «прими мои изменения в основную ветку», который команда обсуждает и проверяет.
  • Спринт (sprint) — короткий фиксированный отрезок времени, за который команда обязуется выполнить объём работы.

Зачем вообще нужна система контроля версий

Аналогия: представь, что ты пишешь курсовую и сохраняешь файл как курсовая_финал.docx, потом курсовая_финал_2.docx, потом курсовая_ФИНАЛ_точно.docx. Через неделю уже невозможно понять, чем они отличаются, а если понадобится вернуть абзац из позапрошлой версии — придётся сравнивать файлы глазами.

Git решает ровно эту проблему, но аккуратнее: вместо кучи файлов с похожими именами он хранит один проект и помнит все его прошлые состояния внутри скрытой папки .git. В любой момент можно посмотреть, что изменилось между двумя версиями, вернуться к любой прошлой, или узнать, кто и когда изменил конкретную строку. Дополнительно Git умеет то, что вручную почти невозможно: позволяет нескольким людям одновременно работать над одним проектом и потом аккуратно соединять их изменения.

// шаг 3/26 · теория · ~1 мин

Три дерева: рабочая папка, индекс, репозиторий

Это самая важная схема урока. Если её понять, перестанут быть загадкой примерно все команды Git — потому что почти каждая из них просто перекладывает изменения между тремя местами.

Рабочая папка — файлы, которые ты видишь в проводнике и редактируешь. Индекс (он же staging area) — черновик следующего коммита: список изменений, которые ты уже отобрал для сохранения, но ещё не сохранил. Репозиторий — папка .git, где коммиты лежат уже навсегда.

Новичков сбивает с толку именно средний элемент: зачем нужен индекс, если можно было бы коммитить сразу из рабочей папки? Затем, что за один заход работы ты обычно правишь несколько вещей сразу — и почти всегда хочется разложить их по разным коммитам: отдельно исправление бага, отдельно правку документации. Индекс и позволяет отобрать в коммит только часть изменений, оставив остальные на потом.

// шаг 4/26 · теория · ~1 мин

git init и git clone — начало работы

Аналогия: git init — завести новый ежедневник с нуля. git clone — получить уже заполненный ежедневник от кого-то другого, со всей историей записей с самого начала.

git init                                     # начать отслеживать историю в текущей папке
git clone https://gitlab.com/user/repo.git   # скачать существующий репозиторий целиком
git clone --depth 1 https://.../repo.git     # только последний коммит, без истории

git init превращает обычную папку в репозиторий, добавляя служебную папку .git. git clone скачивает существующий репозиторий вместе со всей историей коммитов.

Третий вариант — то, что тебе понадобится в CI/CD. Флаг --depth 1 делает так называемый shallow clone: скачивается только последнее состояние, без истории. Для сборки в пайплайне история обычно не нужна, а на большом репозитории это экономит минуты на каждом запуске. Знание этого флага — маленький, но заметный признак того, что человек работал с CI, а не только читал про Git.

// шаг 5/26 · теория · ~2 мин

git add и git commit — сохраняем снимок

git status                  # что изменилось с последнего коммита
git add file.txt            # подготовить конкретный файл
git add .                   # подготовить все изменённые файлы разом
git add -p                  # отобрать изменения по кускам, интерактивно
git commit -m "исправил падение сервера при пустом пароле"
git commit --amend          # переписать последний коммит (только не отправленный!)

Изменение файла на диске само по себе в историю не попадает. Сначала нужно явно сказать Git, какие изменения включить в следующий снимок — это git add. И только git commit создаёт постоянную запись в истории.

git add -p — недооценённая команда: Git показывает изменения по фрагментам и по каждому спрашивает, включать его или нет. Именно так разбирают «я тут наworkал всего сразу» на аккуратные коммиты.

git commit --amend заменяет последний коммит новым — удобно, когда забыл файл или опечатался в сообщении. Важно: коммит при этом получает новый хеш, то есть формально это другой коммит. Если старый уже отправлен на сервер, обычный push будет отвергнут (см. раздел 12).

💡Как писать сообщения коммитов

Хорошее сообщение объясняет зачем было сделано изменение, а не пересказывает что видно из кода. Плохо: «поправил файл». Хорошо: «исправил падение сервера при пустом пароле в форме входа». Через полгода только сообщение коммита сможет объяснить исходный мотив.

// шаг 6/26 · теория · ~2 мин

.gitignore — что не должно попасть в репозиторий

Некоторые файлы в истории не нужны никогда: результаты сборки, зависимости, логи, временные файлы редактора. И отдельная категория — то, что попадать туда опасно: пароли, ключи, токены доступа.

Файл .gitignore в корне репозитория перечисляет шаблоны имён, которые Git должен игнорировать:

node_modules/        # папка зависимостей — восстанавливается командой установки
*.log                # любые лог-файлы
.env                 # файл с паролями и токенами — НИКОГДА в репозиторий
__pycache__/         # кеш Python
.idea/               # настройки конкретной IDE, у каждого свои
!important.log       # исключение из правила: этот лог всё-таки отслеживать
⚠️Главная ошибка, которая стоит дорого

.gitignore действует только на файлы, которые Git ещё не отслеживает. Если ты один раз закоммитил .env с паролем, а потом добавил его в .gitignore — файл останется в истории, и добавление в игнор ничего не изменит. Пароль будет доступен любому, кто склонирует репозиторий, даже если из текущей версии файл удалить.

Единственно правильная реакция на «закоммитил секрет и отправил на сервер» — считать секрет скомпрометированным и немедленно его сменить. Чистка истории (git filter-repo, BFG) делается уже потом и только как уборка. На собеседовании этот вопрос задают часто, и правильный ответ — именно «сменить пароль», а не «почистить историю».

// шаг 7/26 · теория · ~1 мин

Смотрим историю: log, diff, show, blame

git log --oneline --graph --all    # компактная история со схемой ветвления
git log -5                          # последние 5 коммитов подробно
git log --author="Иванов"           # коммиты конкретного человека
git diff                            # что изменено, но ещё не подготовлено
git diff --staged                   # что подготовлено, но ещё не закоммичено
git show a3f21bc                    # что конкретно изменил вот этот коммит
git blame config.yml                # кто и когда написал каждую строку файла

git log --oneline --graph --all стоит завести привычкой — это единственный способ увидеть реальную структуру веток, а не догадываться о ней.

git blame звучит грубо («обвинить»), но используется мирно: когда видишь в конфиге странную строку, blame показывает коммит, где она появилась, а сообщение коммита объясняет зачем. На дежурстве в три часа ночи это иногда экономит час.

// шаг 8/26 · теория · ~1 мин

Ветки — параллельные линии разработки

Аналогия: пишешь книгу и хочешь попробовать альтернативную концовку, не трогая основной текст. Ветка — параллельная черновая копия: получилось хорошо — вставишь результат в основную книгу, не получилось — выбросишь черновик.

git branch                      # список веток
git switch -c feature_login     # создать ветку и перейти на неё (современный способ)
git switch main                 # вернуться на main
git checkout -b feature_login   # то же самое, старый способ — встретишь в статьях
git branch -d feature_login     # удалить влитую ветку

По умолчанию у репозитория есть основная ветка (main, в старых проектах master) — «официальная», стабильная версия. Для новой задачи создаётся отдельная ветка, изменения в ней идут независимо, пока их не решат объединить с основной.

Команды switch и restore появились, чтобы разделить обязанности перегруженного checkout: раньше он и ветки переключал, и файлы восстанавливал. В документации и статьях ты встретишь оба варианта — это одно и то же.

// шаг 9/26 · теория · ~2 мин

push, pull и SSH-ключи

Аналогия: локальный репозиторий — личный черновик, удалённый (на GitLab/GitHub) — общая папка в облаке. push загружает свои записи туда, pull забирает оттуда чужие.

git push origin feature_login    # отправить свою ветку на сервер
git push -u origin feature_login # то же + запомнить связь, дальше можно просто git push
git pull origin main             # забрать изменения из удалённой main
git pull --rebase                # забрать и переложить свои коммиты сверху (см. раздел 9)
git fetch                        # скачать изменения, но НЕ вливать их в свою ветку

origin — общепринятое короткое имя для «сервера, откуда репозиторий склонирован».

Разница между fetch и pull — типовой вопрос на собеседовании. fetch только скачивает новые данные с сервера и обновляет представление о том, что там происходит, не трогая твою рабочую копию. pull — это fetch плюс немедленное вливание изменений в текущую ветку. То есть pull = fetch + merge. Когда хочется сначала посмотреть, что там наделали коллеги, и только потом решить — используют fetch.

SSH-ключи. Вводить логин и пароль при каждом обращении к серверу невозможно, а для автоматики — тем более. Поэтому аутентификация идёт по ключам: генерируется пара из закрытого и открытого ключа, открытый загружается в профиль на GitLab/GitHub, закрытый остаётся на машине.

ssh-keygen -t ed25519 -C "почта@example.com"   # создать пару ключей
cat ~/.ssh/id_ed25519.pub                       # открытый ключ — его копируем на сервер
ssh -T git@gitlab.com                           # проверить, что связь работает

Закрытый ключ (id_ed25519, без .pub) не показывают никому и никогда не коммитят. Подробнее про SSH как таковой — в 1.1 Linux, раздел 11.

// шаг 10/26 · теория · ~2 мин

merge против rebase

Это вопрос №1 по Git на собеседованиях. Обе команды решают одну задачу — перенести изменения из одной ветки в другую — и дают одинаковый результат в файлах. Разница в том, что происходит с историей.

git switch main && git merge feature_login   # влить feature_login в main
git switch feature_login && git rebase main  # переложить свои коммиты поверх свежей main

merge создаёт новый коммит слияния, у которого два родителя. История сохраняет правду: было ответвление, в нём велась работа, потом её влили обратно. Минус — при большом количестве веток история превращается в плетёнку, в которой трудно что-то найти.

rebase делает вид, что ветвления не было: берёт твои коммиты, откладывает в сторону, подтягивает свежее состояние основной ветки и накладывает твои коммиты сверху заново. История получается линейной и читаемой. Ключевое слово — заново: это не те же самые коммиты, а новые, с другими хешами. Старые отбрасываются.

⚠️Золотое правило rebase

Никогда не делай rebase того, что уже отправлено в общую ветку. Раз коммиты пересоздаются с новыми хешами, у всех, кто уже забрал старые, история разойдётся с твоей. Разгребать это придётся всей команде.

Формулировка для собеседования: «rebase — для своих локальных веток, чтобы причесать историю перед отправкой; merge — для вливания в общие ветки».

// шаг 11/26 · теория · ~2 мин

Конфликты слияния

Аналогия: два человека редактируют один абзац бумажного документа, каждый в своей копии, а потом пытаются склеить копии воедино. Если оба поменяли одну фразу по-разному — непонятно, чей вариант оставить.

Git прекрасно объединяет изменения автоматически, если они в разных местах файла. Но если два человека изменили одну и ту же строку по-разному, угадать он не может и сообщает о конфликте слияния. Прямо в файле появляются маркеры:

<<<<<<< HEAD
твоя версия строки
=======
чужая версия строки
>>>>>>> feature_login

Нужно вручную решить, какую версию оставить (или написать третью, объединяющую обе), удалить сами маркеры <<<<<<<, =======, >>>>>>>, затем git add файл и завершить операцию:

git add config.yml
git commit              # при merge
git rebase --continue   # при rebase
git merge --abort       # передумал — откатить всё в исходное состояние

Пара --abort — это страховка, о которой почти никто не помнит: если в процессе слияния стало ясно, что всё пошло не так, необязательно героически доразруливать. Можно вернуться к состоянию «до» одной командой.

// шаг 12/26 · теория · ~1 мин

Отмена изменений: reset, revert, restore

Второй по частоте вопрос на собеседовании — «чем reset отличается от revert».

git restore file.txt              # выбросить правки файла, вернуть как в последнем коммите
git restore --staged file.txt     # убрать файл из индекса, правки оставить
git reset --soft HEAD~1           # отменить последний коммит, изменения оставить в индексе
git reset --mixed HEAD~1          # то же, но изменения станут неподготовленными
git reset --hard HEAD~1           # отменить коммит И стереть изменения (данные пропадут)
git revert a3f21bc                # создать новый коммит, отменяющий указанный

reset переписывает историю: сдвигает указатель ветки назад, и «отменённые» коммиты просто исчезают из неё. Работает только для того, что ещё не отправлено на сервер, — иначе понадобится push --force со всеми вытекающими.

revert историю не трогает: он добавляет сверху новый коммит, который содержит изменения, обратные отменяемому. Ничего не пропадает, push обычный.

Отсюда прямое практическое следствие, ради которого это и спрашивают: на общей ветке отменяют через revert, на своей локальной — можно reset. Если в проде обнаружился сломанный коммит, правильный ответ — git revert, потому что он не ломает историю остальным и сам факт отмены остаётся задокументированным.

// шаг 13/26 · теория · ~2 мин

stash, cherry-pick и force-with-lease

git stash                    # спрятать незаконченные правки, вернуть чистую папку
git stash list               # список припрятанного
git stash pop                # достать обратно последнее и удалить из списка
git cherry-pick a3f21bc      # перенести к себе один конкретный коммит из другой ветки
git push --force-with-lease  # переписать удалённую ветку, но безопасно

stash — карман. Классическая ситуация: правишь задачу, а тут срочный баг в проде. Коммитить полуготовое не хочется — git stash убирает правки в сторону, папка становится чистой, можно спокойно переключиться. Разобрался с багом — git stash pop возвращает всё назад.

cherry-pick переносит не всю ветку, а один конкретный коммит. Типичное применение как раз DevOps'ное: в main починили критичный баг, а в релизной ветке release/1.4, которая уже ушла в прод, он остался. Тащить туда всю main нельзя — там куча нового и непроверенного. Забирают ровно один коммит с исправлением.

--force-with-lease — то, что отличает аккуратного инженера от неаккуратного. Обычный --force затирает удалённую ветку безусловно, в том числе чужие коммиты, о которых ты не знал. Версия --with-lease сначала проверяет, что на сервере ровно то состояние, которое ты последний раз видел, и отказывается работать, если кто-то успел что-то отправить. Привычка всегда писать --force-with-lease вместо --force стоит ноль усилий и однажды спасёт чужой рабочий день.

// шаг 14/26 · теория · ~1 мин

Теги и версионирование

Ветка движется вперёд с каждым коммитом, а тег — неподвижная метка на конкретном коммите. Ими помечают релизы.

git tag -a v1.4.2 -m "Релиз 1.4.2"   # аннотированный тег на текущем коммите
git tag                               # список тегов
git push origin v1.4.2                # теги НЕ отправляются обычным push — только явно
git push origin --tags                # отправить все теги сразу

Номера версий обычно пишут по схеме семантического версионирования — МАЖОРНАЯ.МИНОРНАЯ.ПАТЧ, например 2.5.1:

  • патч (2.5.1 → 2.5.2) — исправление ошибки, поведение не изменилось;
  • минорная (2.5.1 → 2.6.0) — добавили новое, старое продолжает работать;
  • мажорная (2.5.1 → 3.0.0) — сломали обратную совместимость, при обновлении что-то придётся переделать.

Для тебя это не формальность: тег v1.4.2 в репозитории обычно и есть спусковой крючок сборки релиза, а его номер попадает в имя Docker-образа. Схема «увидел тег — собрал myapp:1.4.2 — выкатил» встречается в каждом втором пайплайне.

// шаг 15/26 · теория · ~1 мин

Conventional Commits — когда сообщения читает робот

Мы уже говорили, что сообщение коммита пишут для человека. Но во многих командах его читает ещё и автоматика — чтобы самой посчитать новый номер версии и собрать список изменений для релиза. Для этого сообщениям задают формат:

feat(auth): добавить вход через корпоративный SSO
fix(api): не падать при пустом теле запроса
docs(readme): описать переменные окружения
chore(deps): обновить nginx до 1.27
refactor(db): вынести подключение в отдельный модуль

Слово в начале — тип изменения. Правило простое: fix повышает патч-версию, feat — минорную, а пометка BREAKING CHANGE в тексте — мажорную. Дальше инструменты вроде semantic-release сами проставляют тег и генерируют changelog, и никто не считает версии руками.

Даже если в команде автоматики нет, формат полезен: git log --oneline становится осмысленным списком, где сразу видно, где новая функциональность, а где починка.

// шаг 16/26 · теория · ~1 мин

Модели ветвления: git flow и trunk-based

Аналогия: стройка, где одновременно работают бригады над фундаментом, электрикой и отделкой. Модель ветвления — договорённость о том, кто где работает, чтобы бригады не мешали друг другу.

Git flow — классическая схема: main со стабильным кодом, develop с готовым, но не выпущенным, плюс ветки feature/*, release/*, hotfix/*. Придумана в эпоху, когда релизы выпускали раз в квартал коробками. Работает, но у неё есть системная проблема: ветка живёт неделями, за это время main уходит далеко вперёд, и слияние в конце превращается в отдельный проект.

Trunk-based development — современная альтернатива и то, что подразумевают под CI/CD. Одна долгоживущая ветка (main), ветки под задачи живут часы или день-два и вливаются мелкими порциями. Конфликты просто не успевают вырасти. Незаконченную функциональность прячут не в долгой ветке, а за фиче-флагом — условием в коде, которое включает её только там, где нужно.

ℹ️Почему это важно именно для DevOps

Непрерывная интеграция буквально означает «интегрировать непрерывно». Если ветка живёт две недели, никакой непрерывности нет, сколько бы пайплайнов ни было настроено. Поэтому в вакансиях 2026 года всё чаще упоминают именно trunk-based, а на собеседовании могут спросить, почему git flow плохо сочетается с CI/CD. Ответ: он поощряет долгие ветки, а долгие ветки — это отложенная интеграция и большие конфликты.

// шаг 17/26 · теория · ~1 мин

Merge Request и code review

Аналогия: вписать свои правки прямо в общую официальную рукопись без чьего-либо ведома — рискованно: вдруг закралась ошибка, а никто не заметил.

Технической разницы между Pull Request (GitHub) и Merge Request (GitLab) нет — два названия одной идеи. Процесс: разработчик заканчивает работу в ветке, отправляет её push, создаёт MR с указанием «влить эту ветку в main». Коллеги видят diff, оставляют комментарии, просят поправить или одобряют — и только после одобрения ветка вливается.

Со стороны инфраструктуры MR подкрепляют защитой веток (protected branches) — настройкой на стороне GitLab/GitHub, а не Git. Типичный набор для main: прямой push запрещён, изменения только через MR; нужно хотя бы одно одобрение; пайплайн должен быть зелёным; push --force запрещён. Именно эти настройки обычно и делает DevOps-инженер, а не разработчик.

При вливании MR предлагают выбрать стратегию: обычный merge (сохраняет все коммиты ветки плюс коммит слияния), squash (склеивает всю ветку в один коммит — удобно, когда в ветке двадцать коммитов вида «фикс», «ещё фикс») и rebase/fast-forward (линейная история без коммита слияния).

// шаг 18/26 · теория · ~1 мин

Git как источник событий для CI/CD

Здесь Git перестаёт быть «хранилищем кода» и становится тем, вокруг чего построена вся автоматизация. Пайплайн не запускается сам по себе — его запускает событие в репозитории, и от типа события зависит, что именно произойдёт:

  • push в любую ветку → быстрые проверки: линтер, юнит-тесты;
  • открыт MR → полный прогон тестов, сборка образа, сканер уязвимостей;
  • merge в main → автоматический деплой на тестовый стенд;
  • поставлен тег v1.4.2 → сборка релиза и деплой в прод.

Отсюда следует то, что стоит осознать заранее: имя ветки, текст коммита и тег — это входные данные для автоматики, а не украшение. Правило в пайплайне может звучать как «ветки feature/* собирать, но не деплоить», а версия образа — браться прямо из тега. Поэтому договорённости об именовании в командах жёсткие: их нарушение ломает не эстетику, а сборку.

// шаг 19/26 · теория · ~1 мин

Когда всё сломалось: reflog

Существует убеждение, что неудачным git reset --hard можно безвозвратно потерять работу. Почти всегда это не так — и знание, почему, отличает уверенного пользователя от боящегося.

git reflog                        # журнал всех перемещений HEAD за последние ~90 дней
git reset --hard HEAD@{2}         # вернуться к состоянию, которое было два шага назад

reflog — локальный журнал, куда Git записывает каждое перемещение указателя: коммиты, переключения веток, ресеты, ребейзы. Даже если коммит больше не принадлежит ни одной ветке, он физически лежит в репозитории (Git удалит его лишь при сборке мусора, по умолчанию месяца через три). Поэтому «потерянные» после reset --hard или неудачного rebase коммиты в подавляющем большинстве случаев восстанавливаются.

Важная оговорка: reflog знает только про то, что было закоммичено. Изменения, которые лежали в рабочей папке и не попали ни в один коммит, git reset --hard уничтожает без следа. Отсюда практическое правило: перед рискованной операцией сделай коммит, пусть даже мусорный, — тогда откатиться можно всегда.

// шаг 20/26 · теория · ~1 мин

Английский для IT

Большая часть документации, сообщений об ошибках и обсуждений на Stack Overflow написана на английском, и ждать перевода означает узнавать решение позже всех. Для удалённой работы на зарубежную компанию язык вообще входит в требования наравне с Linux.

Хорошая новость: техническая документация использует ограниченный, предсказуемый набор конструкций — гораздо более простой, чем художественный текст. Слова, которые встречаются почти в любой документации:

Слово Значение
deprecated устаревшее, скоро уберут — использовать не стоит
flag / option флаг, опция команды
default значение по умолчанию
required / optional обязательный / необязательный параметр
to override переопределить, задать своё вместо стандартного
to deploy развернуть, выложить в рабочее окружение
to troubleshoot диагностировать и устранить проблему
known issue известная задокументированная проблема
workaround обходной путь, временное решение
breaking change изменение, ломающее совместимость
rollback откат к предыдущей версии
downtime время простоя сервиса
root cause первопричина проблемы
to reproduce воспроизвести проблему

Отдельно — навык, который нужен именно на удалёнке: писать. Комментарии в MR, описания задач, сообщения в чате, постмортемы после инцидентов — всё это письменный английский, и его достаточно освоить на уровне коротких ясных предложений. Говорить нужно меньше, чем кажется: типичный дейли-стендап — это три фразы про вчера, сегодня и блокеры.

💡Лайфхак

Не обязательно понимать каждое слово, чтобы пользоваться документацией — важнее быстро находить нужный раздел и читать примеры кода, которые часто говорят больше окружающего текста. Автоперевод годится как костыль на первое время, но переведённые термины иногда искажаются и сбивают сильнее, чем помогают: увидев «толчок» вместо «push», ты потеряешь больше времени, чем сэкономил.

// шаг 21/26 · теория · ~2 мин

Agile, Scrum, Kanban и дежурства

Аналогия: Agile — не набор строгих правил, а философия: лучше делать работу маленькими проверяемыми кусочками и часто получать обратную связь, чем полгода писать в одиночестве и узнать, что нужно было другое.

Scrum — самый известный набор практик:

  • Спринт — фиксированный отрезок (обычно 1–2 недели), за который команда обязуется выполнить согласованный объём работы.
  • Беклог — общий список задач, отсортированный по важности; из него на спринт берётся часть.
  • Стендап (daily) — короткая ежедневная встреча: что сделал вчера, что планирую сегодня, что мешает.
  • Ретроспектива — встреча в конце спринта про то, что стоит улучшить в самом процессе работы.

Kanban — вторая модель, и для инфраструктурных команд она встречается даже чаще Scrum. Спринтов нет, есть доска с колонками («в очереди», «в работе», «на проверке», «готово») и ограничение на количество задач в работе одновременно. Причина проста: работа DevOps-команды плохо планируется на две недели вперёд — прилетают инциденты, запросы от разработчиков, срочные обновления безопасности. Kanban с этим живёт органично, Scrum — с трудом.

Термины, которые встретятся именно в эксплуатации:

  • Дежурство (on-call) — график, по которому кто-то из команды отвечает на ночные срабатывания алертов.
  • Инцидент — незапланированное нарушение работы сервиса; у него есть severity — уровень критичности.
  • Постмортем (postmortem) — разбор после инцидента: что случилось, почему, что делаем, чтобы не повторилось. Ключевой принцип — blameless, без поиска виноватого: ищут дефект процесса, а не человека. Смысл прагматичный: если за ошибки наказывают, о них перестают рассказывать, и организация теряет способность учиться.
  • SLA / SLO — договорённости об уровне обслуживания: например, доступность 99.9% в месяц (это, кстати, ~43 минуты простоя). Подробнее — в 4.5 Наблюдаемость и 1.4 Метрики и логи.
// шаг 22/26 · итоги · ~1 мин

Если запомнить только главное

  • Три дерева — рабочая папка, индекс, репозиторий; почти любая команда Git просто двигает изменения между ними.
  • git add готовит изменения, git commit создаёт запись в истории; add -p позволяет разложить работу по осмысленным коммитам.
  • .gitignore не действует задним числом: закоммиченный пароль считается скомпрометированным и подлежит смене, а не чистке.
  • merge сохраняет ветвление, rebase делает историю линейной, пересоздавая коммиты. Не делай rebase того, что уже отправлено в общую ветку.
  • reset переписывает историю (только своё, неотправленное), revert дописывает отменяющий коммит (безопасно для общих веток).
  • fetch только скачивает, pull = fetch + merge.
  • stash прячет незаконченное, cherry-pick переносит один коммит, --force-with-lease вместо --force всегда.
  • Теги помечают релизы и обычно запускают сборку; версии — по схеме мажорная.минорная.патч.
  • Trunk-based даёт настоящий CI; долгие ветки git flow означают отложенную интеграцию.
  • Событие в Git запускает пайплайн — имя ветки, текст коммита и тег читает автоматика.
  • reflog возвращает почти всё потерянное, но только то, что было закоммичено.
  • На удалёнке важнее письменный английский, чем разговорный; в эксплуатации Kanban встречается чаще Scrum.

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

💡В портфолио
  • Задания 1–2 — это репозиторий, в котором будут жить все твои проекты, начиная с P1. Привычка к Conventional Commits из задания 1 сразу видна в истории каждого проекта.
  • Задание 6 (merge request с описанием) — формат, в котором стоит вести изменения во всех проектах, даже если работаешь одна.

Задание 1 — репозиторий с нуля

Создай репозиторий для своих конфигов и скриптов, настрой user.name, user.email, .gitignore (исключи .env, *.log, __pycache__/). Сделай три коммита в формате Conventional Commits.
Проверка: git log --oneline показывает три осмысленных сообщения вида feat: ..., git status чистый, .env не попал в историю (git log --all -- .env пуст).

Задание 2 — SSH-ключ и удалённый репозиторий

Сгенерируй ключ ed25519, добавь его в GitLab или GitHub, создай удалённый репозиторий и запушь.
Проверка: ssh -T git@gitlab.com приветствует тебя по имени, git push работает без пароля.

Задание 3 — конфликт руками

Создай ветку feature/a, измени строку в файле. Вернись в main, измени ту же строку иначе и закоммить. Слей ветку.
Проверка: получен конфликт, разрешён вручную, в истории есть merge-коммит. Повтори через rebase и сравни историю в git log --graph.

Задание 4 — отмена изменений

Сделай коммит с ошибкой и запушь его. Отмени через git revert. Затем локально сделай два коммита и убери их через git reset --soft HEAD~2, собрав в один.
Проверка: в удалённой истории ошибочный коммит и его отмена видны оба; локально вместо двух коммитов один.

Задание 5 — спасение через reflog

Сделай git reset --hard HEAD~3 и «потеряй» три коммита.
Проверка: находишь их в git reflog и возвращаешь ветку на нужный коммит.

Задание 6 — Merge Request

Открой MR из фичеветки в main с описанием на английском: что сделано, зачем, как проверить.
Проверка: описание читается без контекста человеком, который не видел задачу; в MR есть хотя бы один комментарий-ревью и ответ на него.
