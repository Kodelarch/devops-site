О чём урок

ℹ️Зачем это нужно

До сих пор мы работали с одной таблицей за раз. Реальные данные почти всегда разбросаны по нескольким таблицам — покупки отдельно от покупателей, товары отдельно от магазинов. JOIN — это то, как SQL «сшивает» связанные таблицы обратно в один осмысленный результат, а операции над множествами (UNION/INTERSECT/EXCEPT) — как сравнивать и комбинировать целые наборы строк.

📘Словарик на будущее
  • Множество (в контексте SQL) — результат запроса как набор строк, с которым можно работать через UNION/INTERSECT/EXCEPT, как с математическими множествами.
  • JOIN — операция соединения строк из двух таблиц по условию совпадения значений.
  • Декартово произведение — соединение «каждая строка одной таблицы с каждой строкой другой», без всякого условия — самый первичный, «сырой» вид JOIN.
  • CTE (Common Table Expression) — именованный временный результат запроса, объявленный через WITH, на который можно ссылаться дальше в основном запросе.
// шаг 2/21 · теория · ~1 мин

UNION и UNION ALL — объединение списков

Аналогия: объединить два списка (например, все товары и всех покупателей) в один общий список имён — как сложить два списка в один документ, один под другим.

SELECT id AS object_id, title AS object_name FROM product
UNION
SELECT id AS object_id, name AS object_name FROM customer;

Имена итоговых столбцов берутся из первого запроса — во втором SELECT названия колонок могут быть любыми, они всё равно не используются в выводе. UNION по умолчанию убирает дубликаты строк (как DISTINCT); UNION ALL сохраняет все строки, включая повторы.

💡Обязательное правило

Количество столбцов и их типы данных должны совпадать между всеми частями UNION — нельзя объединить запрос с 2 столбцами и запрос с 3 столбцами.

// шаг 3/21 · теория · ~1 мин

INTERSECT — пересечение множеств

Аналогия: пересечение — это «и то, и другое одновременно»: покупатели, которые в один и тот же день и открывали витрину, и что-то купили (хотя это разные, не связанные напрямую таблицы).

SELECT purchase_date AS action_date, customer_id
FROM purchase
INTERSECT
SELECT visit_date AS action_date, customer_id
FROM store_visit;

Результат — только те пары (дата, customer_id), которые встречаются в обоих запросах одновременно. Без ALL дубликаты внутри результата убираются; INTERSECT ALL сохраняет их (с учётом того, сколько раз пара встретилась в обеих частях).

// шаг 4/21 · теория · ~1 мин

EXCEPT (разница множеств)

Аналогия: «то, что есть в первом списке, но отсутствует во втором» — как сверить список гостей, которые должны были прийти, со списком тех, кто реально расписался у входа, и найти, кто не пришёл.

SELECT customer_id FROM purchase WHERE purchase_date = '2026-03-10'
EXCEPT ALL
SELECT customer_id FROM store_visit WHERE visit_date = '2026-03-10'

Запрос находит покупателей, которые 10 марта что-то купили, но в этот день не открывали ни одной витрины, — например, перешли по ссылке из рассылки. EXCEPT (в некоторых базах называется MINUS) вычитает вторую таблицу из первой. Порядок частей важен: A EXCEPT B почти всегда не равно B EXCEPT A.

// шаг 5/21 · теория · ~1 мин

CROSS JOIN — декартово произведение

Аналогия: если сопоставить каждого покупателя с каждым магазином без всякого условия — получится «все возможные пары», как таблица результатов турнира «каждый с каждым».

SELECT c.id, c.name, s.id, s.name
FROM customer c
CROSS JOIN store s;

В учебной базе 12 покупателей и 8 магазинов — результат CROSS JOIN содержит 12 × 8 = 96 строк. Это самый «сырой» вид соединения — по сути, именно из него логически выводятся все остальные типы JOIN, если добавить условие фильтрации по совпадению столбцов.

// шаг 6/21 · теория · ~1 мин

INNER JOIN — соединение по условию

Аналогия: INNER JOIN — это CROSS JOIN, из которого оставили только «осмысленные» пары — те, где значения связанных столбцов действительно совпадают, как совмещение пазла только по правильным стыкам.

SELECT pu.purchase_date, c.name, c.age
FROM purchase pu
JOIN customer c ON pu.customer_id = c.id
ORDER BY pu.purchase_date, c.name;

JOIN без уточнения — то же самое, что INNER JOIN. ON pu.customer_id = c.id — условие, по которому строки двух таблиц считаются «парой». Строка purchase, для которой не нашлось совпадения в customer, в результат INNER JOIN не попадёт вообще.

// шаг 7/21 · теория · ~1 мин

NATURAL JOIN — тот же JOIN, но по имени столбца

Аналогия: NATURAL JOIN — ленивый вариант INNER JOIN: вместо того чтобы явно писать условие, база сама ищет столбцы с одинаковыми именами в обеих таблицах и соединяет по ним.

SELECT pu.purchase_date, c.name, c.age
FROM purchase pu
NATURAL JOIN customer c
ORDER BY pu.purchase_date, c.name;

Работает только если у обеих таблиц есть столбец с одинаковым именем, по которому и должно идти соединение (здесь это не сработает «из коробки» буквально, так как purchase.customer_id и customer.id называются по-разному — NATURAL JOIN уместен только там, где имена столбцов действительно совпадают).

💡Почему NATURAL JOIN редко используют в реальных проектах

Он неявный: если в обеих таблицах случайно совпадёт имя ещё одного столбца (не того, что задумывалось), соединение молча пойдёт не так, как ожидалось. Явный JOIN ... ON считается более безопасной практикой.

// шаг 8/21 · теория · ~1 мин

LEFT, RIGHT и FULL JOIN — сохраняем «непарные» строки

Аналогия: если INNER JOIN — это только пары, то LEFT JOIN — это «все из левой таблицы, даже если пары не нашлось» (для непарных строк правая часть заполняется NULL), как список всех сотрудников с их премиями, включая тех, кому премию в этом месяце не начислили (там будет пусто, а не пропущенная строка).

SELECT s.name AS store_name, s.rating
FROM store s
LEFT JOIN store_visit sv ON s.id = sv.store_id
WHERE sv.id IS NULL;

Этот конкретный запрос находит магазины, витрину которых никто не открывал: LEFT JOIN подставляет NULL вместо данных из store_visit там, где совпадений нет, а WHERE sv.id IS NULL оставляет только такие строки. RIGHT JOIN — то же самое, но приоритет отдаётся правой таблице. FULL JOIN сохраняет непарные строки из обеих таблиц одновременно.

// шаг 9/21 · теория · ~1 мин

Восполняем пропуски: generate_series

Аналогия: чтобы найти пропущенные дни (когда покупатель ни разу не заходил на площадку), сначала нужен полный список всех дней периода — как сплошной календарь, с которым потом сравнивают реальные отметки о посещениях.

SELECT gs::date AS missing_date
FROM generate_series('2026-03-01'::date, '2026-03-10'::date, '1 day') AS gs
LEFT JOIN store_visit sv ON sv.visit_date = gs::date AND sv.customer_id IN (1, 2)
WHERE sv.id IS NULL
ORDER BY missing_date;

generate_series(start, stop, step) генерирует последовательность значений — здесь дат с шагом в один день. Двойное двоеточие :: в PostgreSQL (например, gs::date или '2026-03-01'::date) — оператор явного приведения типа: он говорит базе «обращайся с этим значением именно как со значением такого-то типа», даже если само значение записано в виде обычного текста в кавычках. Запрос выводит дни с 1 по 10 марта, в которые ни Анна, ни Борис не открывали ни одной витрины. Комбинация «сгенерировать полный диапазон + LEFT JOIN + проверка на NULL» — стандартный SQL-паттерн поиска пропусков в данных: дни без продаж, часы без записей в логе, пропуски в метриках.

// шаг 10/21 · теория · ~1 мин

CTE — именованные подзапросы через WITH

Аналогия: CTE — как черновик, который сначала выносишь отдельным пунктом плана, а потом ссылаешься на него по названию в основном тексте, вместо того чтобы каждый раз пересказывать его целиком.

WITH generated_dates AS (
    SELECT gs::date AS the_date
    FROM generate_series('2026-03-01'::date, '2026-03-10'::date, '1 day') AS gs
)
SELECT the_date AS missing_date
FROM generated_dates gd
LEFT JOIN store_visit sv ON sv.visit_date = gd.the_date AND sv.customer_id IN (1, 2)
WHERE sv.id IS NULL
ORDER BY missing_date;

Тот же результат, что и в разделе 8, но generate_series вынесен в блок WITH ... AS (...) — именованное временное представление generated_dates, на которое основной запрос ссылается по имени. При росте сложности запроса CTE сильно улучшает читаемость по сравнению с подзапросом прямо внутри FROM.

// шаг 11/21 · теория · ~1 мин

IN и EXISTS — два способа проверить принадлежность

Аналогия: IN — «есть ли моё значение в этом готовом списке?», EXISTS — «а найдётся ли вообще хоть одна подходящая строка, если поискать?». Разные способы задать один и тот же по смыслу вопрос.

-- через IN
SELECT name FROM store
WHERE id NOT IN (SELECT store_id FROM store_visit);

-- через EXISTS
SELECT name FROM store s
WHERE NOT EXISTS (
    SELECT 1 FROM store_visit sv WHERE sv.store_id = s.id
);

Оба запроса находят магазины, витрину которых никто не открывал. EXISTS проверяет сам факт существования хотя бы одной строки и не заботится о том, что конкретно та строка возвращает (SELECT 1 — условная «заглушка»); EXISTS часто работает быстрее на больших таблицах, потому что база может прекратить поиск, как только нашла первое совпадение.

// шаг 12/21 · теория · ~1 мин

Соединяем несколько таблиц подряд

Аналогия: если нужно узнать не просто «кто купил», а «кто что купил и в каком магазине» — приходится пройти по цепочке связей через несколько JOIN подряд, как передавать посылку по цепочке людей, каждый из которых знает только следующего.

SELECT c.name AS customer_name, pr.title, s.name AS store_name
FROM purchase pu
JOIN customer c ON pu.customer_id = c.id
JOIN product pr ON pu.product_id = pr.id
JOIN store s ON pr.store_id = s.id
ORDER BY c.name, pr.title, s.name;

Порядок JOIN'ов в запросе почти никогда не важен для правильности результата (важна только логика условий ON) — база сама выбирает наиболее эффективный порядок выполнения внутри себя.

// шаг 13/21 · теория · ~1 мин

Самосоединение (self-join)

Аналогия: self-join — это соединение таблицы саму с собой, как сравнение каждого покупателя с каждым другим покупателем из того же списка, чтобы найти пары из одного города.

SELECT c1.name AS customer_1, c2.name AS customer_2, c1.city AS common_city
FROM customer c1
JOIN customer c2 ON c1.city = c2.city AND c1.id < c2.id
ORDER BY c1.name, c2.name, c1.city;

Таблица customer подключается дважды с разными алиасами (p1, p2) — для базы данных это просто две независимые копии таблицы. Условие c1.id < c2.id — стандартный трюк, чтобы не получить пару дважды в обоих порядках и не сравнивать покупателя самого с собой.

// шаг 14/21 · теория · ~2 мин

ON или WHERE — где ставить условие

Аналогия: фильтровать гостей на входе или уже внутри зала — казалось бы, разница невелика. Но если задача была «составить список всех приглашённых, отметив пришедших», то фильтр внутри зала оставит только пришедших, и весь смысл списка потеряется.

Одна из самых частых ошибок с LEFT JOIN и почти обязательный вопрос на собеседовании. Два похожих запроса дают принципиально разный результат:

-- ✔ остаётся LEFT JOIN: все магазины, у непосещённых — NULL
SELECT s.name, sv.visit_date
FROM store s
LEFT JOIN store_visit sv
       ON sv.store_id = s.id
      AND sv.visit_date = '2026-03-04';

-- ✘ фактически стал INNER JOIN: магазины без посещений исчезли
SELECT s.name, sv.visit_date
FROM store s
LEFT JOIN store_visit sv ON sv.store_id = s.id
WHERE sv.visit_date = '2026-03-04';

Механика ровно та, что разбиралась в 2.6 SQL-запросы, §11. LEFT JOIN честно подставил NULL во все столбцы правой таблицы для магазинов без посещений. Затем WHERE sv.visit_date = '2026-03-04' сравнил NULL с датой, получил unknown — и выбросил именно те строки, ради которых LEFT JOIN и брали.

Правило: условие, относящееся к правой таблице, ставится в ON. Условие про левую таблицу можно ставить в WHERE — там NULL не появляется. Единственное осмысленное исключение — WHERE sv.id IS NULL: это не фильтр, а как раз поиск «того, чего нет» (см. §7).

Быстрая самопроверка при отладке: если LEFT JOIN вернул столько же строк, сколько INNER JOIN, — почти наверняка условие уехало в WHERE.

// шаг 15/21 · теория · ~2 мин

Размножение строк: почему сумма завышена

Аналогия: к каждой карточке товара подшили по три накладные — и при подсчёте стоимости склада каждый товар посчитали трижды.

Ошибка без сообщения об ошибке, из-за которой отчёты годами показывают завышенные числа. Возникает при соединении «один ко многим» сразу с двумя таблицами: если покупатель трижды открывал витрину магазина и дважды там купил, то после соединения с обеими таблицами получится 3 × 2 = 6 строк, и каждая покупка будет посчитана трижды.

-- ✘ выручка магазина, умноженная на число просмотров витрины
SELECT s.name, SUM(pr.price) AS revenue
FROM store s
JOIN product pr      ON pr.store_id = s.id
JOIN purchase pu     ON pu.product_id = pr.id
JOIN store_visit sv  ON sv.store_id = s.id
GROUP BY s.name;

Запрос синтаксически безупречен и работает без единого предупреждения — он просто суммирует ровно то, что получилось после соединения. Заметить можно только зная, что искать.

Как чинить. Самый надёжный способ — агрегировать до соединения, а потом соединять уже готовые числа:

WITH revenue AS (
    SELECT pr.store_id, SUM(pr.price) AS revenue
    FROM purchase pu
    JOIN product pr ON pr.id = pu.product_id
    GROUP BY pr.store_id
),
visits AS (
    SELECT store_id, COUNT(*) AS visits
    FROM store_visit
    GROUP BY store_id
)
SELECT s.name, r.revenue, v.visits
FROM store s
LEFT JOIN revenue r ON r.store_id = s.id
LEFT JOIN visits  v ON v.store_id = s.id;

Здесь revenue и visits содержат по одной строке на магазин, поэтому соединение уже не размножает ничего. COUNT(DISTINCT ...) тоже иногда выручает, но только для подсчёта — для суммы денег он бесполезен.

💡Привычка на пять секунд

Перед JOIN и после него сравни COUNT(*). Выросло — значит соединение размножило строки, и любые агрегаты поверх него уже врут. Эта проверка занимает несколько секунд и экономит часы разбирательств с расхождениями в отчётах.

// шаг 16/21 · теория · ~2 мин

Как база выполняет JOIN

Аналогия: соединить два списка можно по-разному: пробежать по первому и для каждой записи искать пару во втором, заранее разложить второй по ящикам, или отсортировать оба и идти навстречу. База выбирает способ сама — но полезно понимать, из чего она выбирает.

EXPLAIN ANALYZE
SELECT c.name, pu.purchase_date
FROM purchase pu
JOIN customer c ON pu.customer_id = c.id;

EXPLAIN показывает план, EXPLAIN ANALYZE — ещё и реально выполняет запрос, показывая фактическое время. В выводе встретится один из трёх способов соединения:

  • Nested Loop — для каждой строки левой таблицы ищется совпадение в правой. Хорошо, когда левая часть маленькая, а справа есть индекс. Плохо, когда обе большие: получается перебор.
  • Hash Join — правая таблица раскладывается в хеш-таблицу в памяти, левая проходится один раз. Обычный выбор для больших таблиц без подходящего индекса.
  • Merge Join — обе стороны сортируются и проходятся навстречу друг другу. Выгоден, когда данные уже отсортированы нужным образом.

Чего в выводе видеть не хочется: Seq Scan по большой таблице (полный просмотр вместо использования индекса) и сильное расхождение между rows= в плане и actual rows= в результате — это значит, что планировщик ошибся в оценке и, скорее всего, выбрал не тот способ. Причина обычно в устаревшей статистике, лечится командой ANALYZE имя_таблицы.

Подробно про индексы и чтение планов — в 2.8 Индексы. Здесь достаточно запомнить два практических следствия:

Порядок JOIN в запросе не влияет на результат и почти не влияет на скорость — планировщик сам решает, в каком порядке соединять. А вот забытое условие ON влияет катастрофически: соединение без условия превращается в декартово произведение (§4), и запрос по двум таблицам на миллион строк каждая попытается построить триллион строк. На проде это выглядит как «база внезапно встала», и находится через pg_stat_activity из 2.6 SQL-запросы, §14.

⚠️NULL не соединяется ни с чем

Строки, где столбец соединения содержит NULL, не попадут в результат INNER JOIN никогда — по той же причине, по которой NULL = NULL не истинно. Если данные пришли из внешнего источника и в ключевом столбце возможны пропуски, это надо учитывать явно: либо через LEFT JOIN, либо заполняя пропуски заранее.

// шаг 17/21 · итоги · ~1 мин

Если запомнить только главное

  • UNION/INTERSECT/EXCEPT требуют одинакового числа и типов столбцов; имена итоговых столбцов берутся из первого запроса.
  • CROSS JOIN — «все со всеми» без условия; INNER JOIN — то же самое, но только «осмысленные» совпадающие пары.
  • LEFT/RIGHT/FULL JOIN сохраняют непарные строки, заполняя недостающие значения NULL — классический способ найти «то, чего нет» (... WHERE ... IS NULL).
  • generate_series + LEFT JOIN + IS NULL — стандартный паттерн поиска пропусков в датах.
  • CTE (WITH ... AS (...)) делает сложные запросы читаемыми, вынося части в именованные блоки.
  • IN и EXISTS часто взаимозаменяемы по смыслу; EXISTS обычно эффективнее на больших данных.
  • self-join — обычный JOIN таблицы саму с собой через разные алиасы.
  • Условие про правую таблицу — в ON, иначе LEFT JOIN молча превращается в INNER JOIN. Проверка: сравни число строк с INNER JOIN.
  • Соединение «один ко многим» размножает строки — SUM после такого JOIN завышен. Агрегируй в CTE до соединения и сверяй COUNT(*) до и после.
  • Забытое условие ON даёт декартово произведение — на больших таблицах это выглядит как «база встала».
  • NULL в столбце соединения не даёт совпадений никогда.
  • EXPLAIN ANALYZE показывает, каким способом база соединяет: Nested Loop, Hash Join или Merge Join.

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

💡В портфолио
  • Запросы из заданий 1 и 5 можно добавить в shop-api как отчётные эндпоинты (выручка по магазинам, покупатели без покупок) — это делает приложение в P1 живее.

Задание 1 — все виды JOIN

Выведи пары «покупатель — магазин» по просмотрам витрин через INNER JOIN; покупателей без единой покупки через LEFT JOIN; магазины, где никто ничего не купил, через NOT EXISTS.
Проверка: число строк в каждом запросе объяснимо; вариант через LEFT JOIN ... WHERE ... IS NULL и вариант через NOT EXISTS дают одинаковый результат.

Задание 2 — пропуски в датах

Через generate_series выведи дни марта, в которые не было ни одной покупки.
Проверка: результат совпадает с ручной проверкой по таблице покупок.

Задание 3 — операции над множествами

Найди магазины, в которых покупали и москвичи, и казанцы (INTERSECT); только москвичи (EXCEPT); объедини названия товаров и магазинов в один список с меткой типа (UNION ALL).
Проверка: объясняешь, когда UNION убрал дубликаты и сколько их было.

Задание 4 — CTE вместо вложенных подзапросов

Перепиши любой запрос с двумя вложенными подзапросами через WITH.
Проверка: результат совпадает, EXPLAIN обоих вариантов сравнён.

Задание 5 — размножение строк

Посчитай выручку по магазинам, присоединив и просмотры витрин, и покупки. Найди, почему сумма завышена, и исправь через предварительную агрегацию в подзапросах.
Проверка: итог совпадает с суммой, посчитанной только по таблице покупок.
