О чём урок

ℹ️Зачем это нужно

Почти всё в DevOps в итоге происходит на Linux-сервере: контейнеры — это процессы Linux, узлы Kubernetes — машины с Linux, раннеры CI — тоже Linux. Это первый урок, предыдущего нет, поэтому читаем так, будто раньше с Linux дела вообще не имели.

На собеседовании junior DevOps Linux проверяют всегда и подробно: права, процессы и сигналы, systemd, логи, диск, SSH. Большая часть вопросов звучит как «сервис не работает — что будешь смотреть», и последний раздел урока как раз про это.

📘Словарик на будущее
  • Терминал — окно, куда вводишь команды текстом вместо кликов мышкой.
  • Команда — одна инструкция терминалу, например ls («покажи файлы»).
  • Пакет — готовая программа, упакованная в один файл для удобной установки.
  • Демон — программа-служба, которая крутится в фоне и ждёт запросов.
  • root — главный пользователь системы, у которого есть права на абсолютно всё.
  • Ядро (kernel) — сердце ОС: программа, которая напрямую общается с железом.
  • systemd — система, которая запускает службы при старте и следит за ними.
  • PID — номер процесса.

Виртуальные машины


Аналогия: виртуальная машина — компьютер внутри файла. Реального железа не появляется, но система думает, что у неё есть свой процессор, память и диск — всё это «одолжено» у настоящего компьютера.

Так проще всего попробовать Linux, не переустанавливая Windows. Варианты:

  • WSL — встроенный в Windows способ запустить настоящую Ubuntu без отдельного виртуализатора. Удобно для повседневной работы с командами.
  • VirtualBox или Hyper-V — полноценная машина со своей сетью. Нужна, когда изучаешь сеть, systemd и загрузку системы.
  • Vagrant — машины из файла описания, поднимаются одной командой (4.1 Compose и Swarm, §3).

Серверы ставят без графического интерфейса — управление только через терминал. Для практики берут Ubuntu Server LTS: её чаще всего встречаешь в вакансиях и в облаках.

cat /etc/os-release   # какой дистрибутив и версия
uname -r              # версия ядра
hostnamectl           # имя машины, ОС, ядро, виртуализация

Файловая система


Аналогия: один большой шкаф с папками. В Windows таких шкафов несколько (C:, D:), а в Linux — всегда один, называется «корень», обозначается /.

Всё растёт из этого корня, и у каждой верхней папки есть смысл:

Путь Назначение
/etc конфиги системы и сервисов
/var, /var/log изменяемые данные, логи
/home/<user> домашняя папка пользователя
/root домашняя папка root
/usr/bin, /bin сами программы
/tmp временные файлы, чистятся сами
/proc, /sys виртуальные ФС — живое состояние ядра и процессов
/dev файлы устройств (диски, терминалы)
/opt сторонний софт вне пакетного менеджера
/mnt, /media точки монтирования внешних дисков

Путь бывает абсолютный (начинается с /, работает откуда угодно) и относительный — от текущего места (. — тут же, .. — на уровень выше, ~ — домашняя папка).

pwd                         # где я сейчас нахожусь
cd /var/log                 # перейти
ls -la                      # список файлов, включая скрытые, с правами
find /etc -name "*.conf"    # найти файлы по имени
mkdir -p a/b/c              # создать сразу все вложенные папки
cp -r src/ dst/             # скопировать папку целиком
mv old new                  # переместить или переименовать
rm -rf dir/                 # удалить папку рекурсивно — опасно, сначала проверь путь

Звёздочка * — подстановочный символ («любое количество любых символов»), поэтому find находит любой файл, имя которого заканчивается на .conf. У rm -rf два флага: -r — удалить вместе со всем содержимым, -f — не спрашивать подтверждения. Сочетание делает команду опасной: она молча удаляет всё по указанному пути. Корзины в терминале нет.

Симлинк (ln -s) — ярлык: отдельный файл с путём к другому файлу; сломается, если оригинал удалить. Жёсткая ссылка (ln) — второе имя для тех же данных на диске; данные живы, пока жива хоть одна ссылка.

«Всё есть файл». В Linux файлами представлены не только документы, но и устройства (/dev/sda), состояние процессов (/proc/1234/status) и параметры ядра (/proc/sys/...). Поэтому многие диагностические вещи читаются обычным cat.

Права доступа


Аналогия: замок на двери. У каждого файла есть хозяин, его «семья» (группа) и «все остальные» — и для каждого отдельно решается, можно ли читать, писать или запускать.

ls -la показывает строку вроде -rw-r--r--: тип файла, потом три раза по три буквы — права хозяина, группы, всех остальных. r — читать, w — изменять, x — запускать как программу (для папки — входить в неё). Цифра — сумма r=4, w=2, x=1 на каждую тройку:

  • 644 = rw-r--r-- — типично для конфигов.
  • 755 = rwxr-xr-x — скрипты, программы, папки.
  • 600 = rw------- — приватные файлы, например SSH-ключ.
chmod 755 script.sh        # выдать права числом
chmod u+x script.sh        # или символьно: добавить хозяину право на выполнение
chmod g-w,o-rwx file       # убрать запись у группы, всё у остальных
chown user:group file      # сменить хозяина и группу разом
umask                      # маска прав по умолчанию для новых файлов
⚠️chmod 777 — не решение

Когда «не хватает прав», соблазн написать chmod -R 777 велик: ошибка пропадает. Вместе с ней пропадает и защита — любой процесс на машине может переписать файл. Правильный путь — понять, от какого пользователя работает процесс, и выдать права именно ему: сменить владельца или добавить пользователя в группу.

⚠️Спецбиты, если хочешь глубже
  • SUID (chmod u+s) — программа выполняется с правами её владельца, а не того, кто запустил (пример: /usr/bin/passwd).
  • SGID (chmod g+s) на директории — новые файлы наследуют группу директории.
  • Sticky bit (chmod +t, пример /tmp) — удалить файл может только его владелец, даже если у остальных есть право записи в саму директорию.

Пользователи и sudo


Аналогия: один аккаунт-администратор на всех — как один ключ от офиса на всю компанию. Отдельные пользователи — именные пропуска.

sudo adduser newuser
sudo usermod -aG sudo newuser   # разрешить пользоваться sudo
sudo usermod -aG adm newuser    # доступ к логам без полного root
id newuser                      # в каких группах состоит
getent passwd newuser           # запись в /etc/passwd

Группа — набор пользователей, которым разом выдали одинаковый доступ. У usermod флаг -a (append) обязательно идёт вместе с -G: без -a команда заменит все группы пользователя на указанную и легко лишит его прав, которые уже были.

sudo — не «волшебное слово», а «выполни это от имени root, но запиши в журнал, что это сделал я». Безопаснее, чем постоянно работать под root: там одна опечатка ломает систему без предупреждения, и непонятно, кто что сделал. Права на sudo настраиваются в /etc/sudoers — редактируют его только через sudo visudo, который проверяет синтаксис: сломанный sudoers оставляет систему без администратора.

Сервисные пользователи. Каждая служба работает от своего пользователя без права входа: nginx — от www-data, PostgreSQL — от postgres. Взлом одной службы не даёт доступ к файлам другой. Свои приложения запускают так же:

sudo useradd --system --no-create-home --shell /usr/sbin/nologin app

Процессы и сигналы


Аналогия: процесс — запущенная программа. У каждой есть номер (PID), родитель, владелец, и с ней можно взаимодействовать: посмотреть, что она делает, или попросить остановиться.

ps aux                  # все процессы: a — все, u — с владельцем, x — и без терминала
ps aux --sort=-%mem | head    # самые прожорливые по памяти
pgrep -a nginx          # найти процессы по имени
top                     # живой список: load average, CPU, память
htop                    # то же удобнее: F6 сортировка, F4 фильтр, F9 сигнал

Load average в top — три числа: средняя очередь на процессор за 1, 5 и 15 минут. Сравнивают с числом ядер (nproc): на 4 ядрах load 4 — полная загрузка, 8 — процессы ждут в очереди.

Сигналы — способ сообщить процессу о событии:

Сигнал Номер Что значит
SIGTERM 15 Вежливая просьба завершиться: сохранить данные, закрыть соединения
SIGKILL 9 Убить немедленно. Процесс не может его перехватить
SIGINT 2 То, что посылает Ctrl+C
SIGHUP 1 Исторически «терминал закрылся»; многие демоны по нему перечитывают конфиг 
kill 1234          # по умолчанию SIGTERM
kill -9 1234       # SIGKILL — только если SIGTERM не помог
pkill -HUP nginx   # отправить сигнал по имени

Порядок важен: сначала SIGTERM и несколько секунд ожидания, SIGKILL — только если процесс не отреагировал. kill -9 сразу лишает приложение шанса завершить запись в базу или дослать ответы. Ровно так же ведут себя Docker и Kubernetes при остановке контейнера: сначала SIGTERM, через период ожидания — SIGKILL (2.5 Бэкенд-сервис).

Фоновые задачи:

long_command &          # запустить в фоне
jobs                    # фоновые задачи текущего терминала
fg %1                   # вернуть задачу 1 на передний план
nohup long_command &    # переживёт закрытие терминала

%1 — номер задачи в списке jobs, а не PID. Обычная фоновая задача завершится при закрытии терминала, nohup от этого защищает. Для долгой работы по SSH удобнее tmux: сессия продолжает жить после отключения, и к ней можно вернуться.

Зомби — процесс, который завершился, но родитель ещё не забрал его код выхода. Ресурсов почти не ест, но много зомби — признак ошибки в родительском процессе.

Память, swap и OOM killer

Аналогия: память — рабочий стол. Swap — тумбочка рядом: туда можно убрать бумаги, но доставать их долго. Когда стол завален и тумбочка полна, приходит уборщик и выбрасывает самую большую стопку, не спрашивая.

free -h
#               total   used   free   shared  buff/cache  available
# Mem:          7.7Gi  2.1Gi  0.4Gi   0.1Gi       5.2Gi      5.3Gi
# Swap:         2.0Gi     0B  2.0Gi

Самая частая ошибка новичка — смотреть на free и паниковать, что свободно 0.4 ГБ. Linux специально занимает свободную память под кэш диска (buff/cache): это ускоряет чтение файлов, а при нехватке кэш мгновенно освобождается. Смотреть нужно на available — сколько реально можно отдать программам.

Swap — место на диске, куда ядро выгружает редко используемые страницы памяти. Немного swap полезно. Активная работа со swap (видно в vmstat 1, колонки si/so) означает, что памяти не хватает, и всё становится очень медленным.

OOM killer (Out Of Memory) — механизм ядра на крайний случай: если памяти не осталось совсем, ядро выбирает процесс и убивает его SIGKILL. Выбирает в основном по размеру — поэтому жертвой часто становится самый важный и прожорливый процесс, например база данных.

sudo dmesg -T | grep -i -E "killed process|out of memory"
journalctl -k | grep -i oom

Признаки того, что процесс убил OOM killer: сервис внезапно перезапустился без ошибок в собственном логе, а в журнале ядра есть Killed process 1234 (postgres). В контейнерах то же самое выглядит как статус OOMKilled (5.1 Kubernetes, §12): там лимит задаёт сам контейнер.

Защищаются лимитами памяти для служб и контейнеров (4.1 Compose и Swarm, §11) и мониторингом available с алертом заранее (4.5 Наблюдаемость).

systemd: службы

Аналогия: systemd — управляющий зданием. Знает, какие службы должны работать, запускает их утром в правильном порядке, перезапускает упавшие и ведёт журнал.

Почти во всех современных дистрибутивах службами управляет systemd. Основная команда — systemctl:

systemctl status nginx          # состояние, PID, последние строки лога
sudo systemctl start nginx      # запустить
sudo systemctl stop nginx       # остановить
sudo systemctl restart nginx    # остановить и запустить заново
sudo systemctl reload nginx     # перечитать конфиг без остановки
sudo systemctl enable nginx     # запускать при загрузке системы
sudo systemctl enable --now nginx   # включить и сразу запустить
systemctl list-units --type=service --state=failed   # все упавшие службы

restart и reload — разные вещи. restart останавливает процесс и запускает заново: все текущие соединения рвутся. reload просит процесс перечитать конфигурацию на ходу (обычно сигналом SIGHUP, §5) — соединения сохраняются. Для nginx и большинства веб-серверов после правки конфига делают reload. Не все службы его поддерживают; тогда systemctl сообщит об ошибке.

start и enable — тоже разные. start запускает сейчас, но после перезагрузки служба не поднимется. enable включает автозапуск, но сейчас ничего не запускает. Частая ошибка — поставить сервис, запустить через start, а после первой перезагрузки сервера обнаружить, что он не работает.

Свой сервис. Любую программу можно оформить службой — это правильнее, чем nohup или screen:

# /etc/systemd/system/myapp.service
[Unit]
Description=My application
After=network-online.target
Wants=network-online.target

[Service]
User=app
WorkingDirectory=/opt/myapp
ExecStart=/opt/myapp/venv/bin/python app.py
Restart=on-failure
RestartSec=5
Environment=PORT=8000
MemoryMax=512M

[Install]
WantedBy=multi-user.target

sudo systemctl daemon-reload        # после любого изменения unit-файлов
sudo systemctl enable --now myapp

Что даёт такой unit: запуск при загрузке, автоматический перезапуск при падении (Restart=on-failure), работа от отдельного пользователя (§4), лимит памяти (MemoryMax, §6) и весь вывод программы в journald (§8). Забытый daemon-reload после правки unit-файла — классическая причина «я поменял, а ничего не изменилось».

journald: журнал служб

Аналогия: единый журнал дежурного, куда пишут все службы здания, вместо стопки тетрадей в каждом кабинете.

Всё, что службы systemd пишут в stdout и stderr, попадает в journald. Читается через journalctl:

journalctl -u nginx                     # лог конкретной службы
journalctl -u nginx -f                  # следить в реальном времени, как tail -f
journalctl -u nginx --since "1 hour ago"
journalctl -u nginx -n 50 --no-pager    # последние 50 строк
journalctl -p err -b                    # только ошибки с момента загрузки
journalctl -k                           # сообщения ядра
journalctl --disk-usage                 # сколько места занимает журнал

Флаг -u (unit) — главный: показывает только нужную службу, а не весь системный шум. Скрипт, оформленный unit-ом из §7, автоматически пишет в journald — именно так логи из 1.3 Bash оказываются в одном месте с системными.

Журнал по умолчанию может не переживать перезагрузку. Чтобы хранить его на диске, создают каталог /var/log/journal или ставят Storage=persistent в /etc/systemd/journald.conf. Размер ограничивают там же (SystemMaxUse=500M), иначе журнал однажды займёт весь диск.

Bash


Аналогия: bash — язык, на котором отдаёшь команды текстом вместо кликов мышкой. Со временем это оказывается быстрее и куда легче автоматизировать.

Переменные и условия:

NAME="value"            # без пробелов вокруг =
echo "$NAME"            # переменные — всегда в кавычках

if [ -f file.txt ]; then
  echo "есть"
else
  echo "нет"
fi

for f in /var/log/*.log; do
  echo "$f"
done

Пробелы вокруг = недопустимы: bash воспримет NAME = value как вызов команды NAME. В [ -f file.txt ] флаг -f проверяет, что файл существует; -d — что это папка, -z — что строка пустая, -n — что не пустая.

Конвейер | передаёт вывод одной команды на вход следующей, перенаправления пишут в файлы:

grep ERROR app.log | wc -l     # сколько строк с ERROR
command > out.log              # вывод в файл (перезапись)
command >> out.log             # дописать в конец
command 2> err.log             # только ошибки (поток stderr)
command > all.log 2>&1         # и вывод, и ошибки в один файл

У каждой программы два выходных потока: stdout (1) для обычного вывода и stderr (2) для ошибок. 2>&1 означает «отправь ошибки туда же, куда идёт обычный вывод».

Текстовые утилиты, без которых редкий скрипт обходится:

grep -v "debug" file.log         # исключить совпадения
grep -r "listen" /etc/nginx/     # искать по всем файлам в папке
cut -d',' -f2 file.csv           # 2-е поле по разделителю
sort file.txt | uniq -c          # отсортировать и посчитать повторы
awk '{print $1, $3}' file.log    # 1-я и 3-я колонки
sed 's/old/new/g' file.txt       # заменить текст
tail -f /var/log/syslog          # следить за концом файла
find . -name "*.tmp" | xargs rm  # передать результат как аргументы

sort перед uniq обязателен: uniq убирает только соседние повторы. sed 's/old/new/g': s — заменить, g — все вхождения в строке, а не только первое.

Скрипт — файл с командами, начинается с shebang и строгого режима:

#!/usr/bin/env bash
set -euo pipefail     # упасть при ошибке, на необъявленной переменной и в конвейере

chmod +x deploy.sh
./deploy.sh

Подробно о скриптах — параметры, функции, кавычки, trap, shellcheck — в 1.3 Bash.

Пакетные менеджеры


Аналогия: как магазин приложений, только для Linux — устанавливает, обновляет и полностью удаляет программы без мусора, а заодно подтягивает всё, что им нужно для работы.

sudo apt update                 # обновить список доступных пакетов
sudo apt install -y nginx       # установить
sudo apt remove nginx           # удалить (конфиги остаются)
sudo apt purge nginx            # удалить вместе с конфигами
apt search nginx                # найти пакет
apt show nginx                  # описание и версия
dpkg -L nginx                   # какие файлы принёс пакет
apt list --installed | grep nginx

apt update не обновляет программы, а только скачивает свежий список пакетов. Без него apt install может пытаться поставить версию, которой уже нет в репозитории.

Сторонние репозитории. Docker, PostgreSQL новых версий, Grafana ставят из репозиториев производителя: добавляется ключ подписи и строка с адресом репозитория, потом обычный apt install. Подпись гарантирует, что пакет не подменили по дороге.

На RHEL, Rocky, Fedora вместо apt — dnf (dnf install, dnf remove). В Alpine, которую часто используют в контейнерах, — apk add.

SSH


Аналогия: sshd — дежурный вахтёр: слушает свою дверь (порт 22) и пускает только тех, у кого подходящий ключ.

SSH — способ управлять удалённым сервером через зашифрованное соединение. На сервере работает служба sshd, на твоей машине — клиент ssh.

sudo apt install -y openssh-server
sudo systemctl enable --now ssh
ss -tlnp | grep :22            # слушает ли порт: -t TCP, -l слушающие, -n числа, -p процесс

Вход по ключу вместо пароля — стандарт. Создаётся пара: приватный ключ остаётся у тебя и никому не показывается, публичный кладётся на сервер.

ssh-keygen -t ed25519 -C "me@laptop"     # создать пару ключей
ssh-copy-id user@server                  # положить публичный ключ на сервер
ssh user@server                          # войти

Публичный ключ попадает в ~/.ssh/authorized_keys на сервере. Права важны: каталог ~/.ssh — 700, файл authorized_keys и приватный ключ — 600. Если права шире, sshd из соображений безопасности молча откажется принимать ключ.

Удобные записи для частых подключений — в ~/.ssh/config на своей машине:

Host web1
    HostName 10.0.1.11
    User deploy
    IdentityFile ~/.ssh/id_ed25519

После этого достаточно ssh web1.

Минимальная защита сервера в /etc/ssh/sshd_config:

PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes

sudo sshd -t && sudo systemctl reload ssh    # проверить конфиг и применить

Боты перебирают пароли на порту 22 любого сервера с публичным адресом круглосуточно — в /var/log/auth.log это видно через несколько минут после создания машины. Вход только по ключу делает перебор бессмысленным.

🛑Не потеряй доступ

Меняя настройки SSH или включая файрвол (1.2 Сети), не закрывай текущую сессию. Открой вторую и проверь, что вход работает. Если настройки сломали доступ, первая сессия — единственный способ всё вернуть, иначе спасать сервер придётся через консоль облака или физически.

Сеть: DHCP и статика


Аналогия: DHCP — стойка регистрации на конференции: выдаёт «бейджик» (IP) на время визита. Статика — именной пропуск, всегда один и тот же.

ip a            # интерфейсы и адреса; lo — «сеть с самим собой», 127.0.0.1
ip r            # таблица маршрутов, default — шлюз по умолчанию
resolvectl status   # какие DNS-серверы используются

DHCP — служба, которая автоматически выдаёт машине IP-адрес, шлюз и DNS при подключении к сети. Серверам обычно нужен постоянный адрес — его задают статически. В Ubuntu это делается через netplan:

# /etc/netplan/00-installer-config.yaml
network:
  version: 2
  ethernets:
    eth0:
      addresses: [192.168.1.50/24]
      routes:
        - to: default
          via: 192.168.1.1
      nameservers:
        addresses: [1.1.1.1, 8.8.8.8]

addresses — IP с маской подсети, routes — куда отправлять трафик, если адрес не в локальной сети, nameservers — DNS-серверы. YAML чувствителен к отступам: лишний пробел — и конфиг не применится.

sudo netplan try        # применить с автоматическим откатом через 120 секунд, если не подтвердить
sudo netplan apply
ping -c 4 1.1.1.1       # цель: "0% packet loss"

netplan try — правильный способ менять сеть на удалённой машине: если новая настройка отрезала тебя от сервера, через две минуты всё вернётся само. Подробно о сетях — в 1.2 Сети.

Текстовые редакторы

Аналогия: vim — не блокнот, а отдельный язык жестов: сначала бессмысленный набор клавиш, потом быстрее мыши.

vim test.txt
i            — режим вставки текста; Esc — обратно в режим команд
:wq          — сохранить и выйти; :q! — выйти без сохранения
/слово       — поиск; n — следующее совпадение
dd           — удалить строку; u — отменить
:%s/старое/новое/g — заменить по всему файлу

Главное, что сбивает с толку: vim модальный. В режиме по умолчанию буквы на клавиатуре — это команды, а не текст. i переключает в режим вставки, Esc возвращает обратно. :q! выходит без сохранения — восклицательный знак значит «точно, без предупреждений».

nano проще: подсказки внизу экрана (Ctrl+O сохранить, Ctrl+X выйти), никаких режимов.

⚠️Почему это не мелочь

На реальном сервере графического редактора не будет никогда — только vim или nano. В контейнерах часто нет даже их. Без минимального владения vim не починишь конфиг в 3 часа ночи.

Обновления и время

Аналогия: обновления — как прививки: неприятно, но без них рано или поздно «продует» через давно известную дыру.

sudo apt update && sudo apt upgrade -y
cat /var/run/reboot-required 2>/dev/null   # нужна ли перезагрузка (например, после обновления ядра)

Обновления безопасности на Ubuntu может ставить сам unattended-upgrades — его стоит включить на любом сервере. Крупные обновления на продакшене делают осознанно: сначала на тестовой машине.

Время. Точное время критично: по нему проверяются сертификаты, сопоставляются логи с разных машин, работает cron, а Kerberos и многие базы при расхождении часов отказываются работать. Часы синхронизирует NTP:

timedatectl                          # время, часовой пояс, синхронизация
timedatectl show -p NTPSynchronized  # цель: NTPSynchronized=yes
sudo timedatectl set-timezone UTC

Серверы живут в UTC. Местное время на сервере — постоянный источник ошибок: переход на летнее время ломает расписание cron, а логи серверов из разных часовых поясов невозможно сопоставить. Местное время показывают пользователю в интерфейсе, а на сервере и в базе всё хранится в UTC (2.2 Python для автоматизации).

Дисковое пространство


Аналогия: df — счётчик на бензоколонке: сколько всего и сколько осталось. du — чек с расшифровкой, куда именно ушло топливо.

df -Th                       # размер, занято, свободно, % и тип ФС по разделам
du -sh /var/log/*            # размер каждой папки отдельно
du -xh / --max-depth=1 2>/dev/null | sort -h   # что самое большое в корне
ncdu /                       # то же интерактивным деревом
lsblk                        # дерево дисков и разделов
mount | column -t            # что и куда смонтировано

Типичные пожиратели места на сервере: логи (/var/log), журнал systemd (§8), образы и тома Docker (/var/lib/docker, чистится docker system prune), старые ядра и кэш пакетов (apt autoremove, apt clean).

Две ловушки, о которых спрашивают на собеседованиях:

Файл удалили, а место не освободилось. Если процесс держит файл открытым, удаление через rm убирает только имя, а данные остаются на диске, пока процесс не закроет файл. df показывает полный диск, а du не находит, куда делось место.

sudo lsof +L1                # открытые, но удалённые файлы

Решение — перезапустить процесс, который держит файл, или очистить файл, не удаляя его: : > /var/log/big.log (или truncate -s 0). Именно так логи «чистят» на живом сервере. Это та самая утечка дескрипторов из 2.1 Python.

Место есть, а файлы не создаются. Кончились иноды — записи о файлах. Миллионы мелких файлов (сессии, кэш) исчерпывают их раньше, чем место.

df -i                        # использование инодов

Логи и cron


Аналогия: системные логи — чёрный ящик самолёта: когда что-то падает, смотрят туда, а не гадают.

Кроме journald (§8), многие службы пишут классические текстовые логи в /var/log:

less /var/log/syslog         # общий системный журнал (Ubuntu)
less /var/log/auth.log       # входы, sudo, SSH
less /var/log/nginx/error.log
tail -f /var/log/nginx/access.log

cron — планировщик: запускает команды по расписанию без участия человека.

crontab -e      # редактировать свои задачи
crontab -l      # список задач

# минута  час  день_месяца  месяц  день_недели  команда
*/2       *    *            *      *            uptime >> /tmp/uptime.log
0         3    *            *      1            /opt/backup.sh >> /var/log/backup.log 2>&1

Первая строка — каждые 2 минуты, вторая — в 3:00 по понедельникам. */2 означает «каждое второе значение». Проверять выражения удобно на crontab.guru.

Две вещи, на которых ломаются почти все первые cron-задачи:

  • Другое окружение. Cron запускает команды с минимальным PATH и без твоих переменных. Команда, работающая в терминале, в cron не находится. Решение — полные пути (/usr/bin/python3) или PATH= в начале crontab.
  • Вывод пропадает. Без перенаправления >> файл 2>&1 ошибки задачи никто не увидит.

Современная альтернатива cron — systemd timers: задача оформляется сервисом (§7), а расписание — отдельным .timer. Плюсы: лог в journald, видно время последнего и следующего запуска (systemctl list-timers), можно запустить вручную через systemctl start.

// шаг 18/24 · теория · ~2 мин

logrotate: чтобы логи не съели диск

Аналогия: архивариус, который раз в неделю убирает старые журналы в коробку, подписывает её, а совсем старые коробки выбрасывает.

Текстовые логи растут бесконечно. Без ротации один болтливый сервис за несколько недель заполняет диск, и падает всё на машине. logrotate запускается по расписанию и по правилам из /etc/logrotate.d/ переименовывает, сжимает и удаляет старые логи:

# /etc/logrotate.d/myapp
/var/log/myapp/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
  • daily и rotate 14 — ротировать каждый день, хранить 14 архивов.
  • compress и delaycompress — сжимать, но вчерашний файл оставить несжатым, чтобы его было удобно читать.
  • missingok, notifempty — не ругаться на отсутствующий файл и не ротировать пустой.
  • copytruncate — скопировать лог и очистить оригинал, не удаляя его. Нужно для программ, которые держат файл открытым и не умеют переоткрывать (ловушка из §15). Лучшая альтернатива, если программа поддерживает, — блок postrotate с сигналом на переоткрытие логов.
sudo logrotate -d /etc/logrotate.d/myapp    # проверить правила без изменений
sudo logrotate -f /etc/logrotate.d/myapp    # ротировать принудительно

Пакеты nginx, PostgreSQL и других служб приносят свои правила logrotate сами. Для собственных приложений их пишут вручную — или, что лучше, пишут логи в stdout и отдают journald или Docker, где ограничение размера настраивается централизованно (4.1 Compose и Swarm).

// шаг 19/24 · теория · ~2 мин

Сервис не работает: порядок разбора

Аналогия: врач на приёме идёт по одному и тому же списку: температура, давление, жалобы — и только потом анализы. Не гадает, а исключает.

Вопрос «сервис не отвечает — что будешь делать» задают почти на каждом собеседовании. Хороший ответ — последовательность шагов, а не случайные команды:

# 1. Запущен ли он вообще и что говорит systemd
systemctl status myapp

# 2. Что он пишет в лог перед падением
journalctl -u myapp -n 100 --no-pager

# 3. Слушает ли нужный порт и на каком адресе
ss -tlnp | grep 8000

# 4. Отвечает ли локально, в обход сети и файрвола
curl -v http://127.0.0.1:8000/health

# 5. Хватает ли ресурсов
df -h; df -i; free -h; uptime

# 6. Не убил ли его OOM killer
journalctl -k | grep -i oom

# 7. Правильный ли конфиг
nginx -t            # или аналог для конкретной программы

Типовые находки:

  • active (running), но порт не слушается — приложение слушает не тот порт или только 127.0.0.1, а обращаются снаружи.
  • Отвечает на 127.0.0.1, но не снаружи — файрвол или группа безопасности (1.2 Сети, 4.2 Облако).
  • failed с status=203/EXEC — неверный путь в ExecStart или нет прав на запуск.
  • Постоянные перезапуски — смотреть лог перед каждым падением: чаще всего нет конфига, занят порт (Address already in use) или нет доступа к файлу.
  • Permission denied — проверить, от какого пользователя работает служба (User= в unit-файле), и права на файлы (§3).

Тот же порядок потом повторяется для контейнеров (3.1 Docker) и подов (5.1 Kubernetes, §15) — меняются только команды.

// шаг 20/24 · итоги · ~1 мин

Если запомнить только главное

  • Всё растёт из одного корня /; конфиги — в /etc, логи — в /var/log. Симлинк — ярлык, жёсткая ссылка — второе имя тех же данных.
  • Права — хозяин/группа/остальные × чтение/запись/выполнение. chmod 777 — не решение.
  • sudo — повышение прав с журналом. usermod -aG: без -a пользователь теряет группы. Службы работают от своих пользователей.
  • Сначала SIGTERM, и только потом SIGKILL.
  • В free смотрят на available. OOM killer убивает процесс при полной нехватке памяти — следы в dmesg.
  • systemd: restart рвёт соединения, reload нет; start — сейчас, enable — при загрузке. После правки unit — daemon-reload.
  • Логи службы — journalctl -u имя -f.
  • Конвейер | склеивает команды; 2>&1 объединяет вывод и ошибки. В скриптах — set -euo pipefail.
  • SSH только по ключу, root и пароли запрещены, права 700/600. Меняя доступ — держи открытой вторую сессию.
  • Серверы живут в UTC, время синхронизируется по NTP.
  • df — сколько места, du — куда делось. Удалённый, но открытый файл — lsof +L1. Кончились иноды — df -i.
  • В cron другое окружение и пропадает вывод — полные пути и перенаправление в лог.
  • logrotate не даёт логам съесть диск; для открытых файлов — copytruncate.
  • Неработающий сервис разбирают по порядку: status → лог → порт → curl локально → ресурсы → OOM → конфиг.

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

💡В портфолио
  • Задания 1–2 — раздел «Сервер» в P1: статический адрес, UTC, пользователь deploy, вход только по ключу.
  • Задания 1 и 2, собранные в один идемпотентный скрипт, — это мини-проект M1.
  • Задание 3 (свой systemd-сервис) пригодится в M2: утилиту удобно запускать таймером.

Задание 1 — сервер с нуля

Поставь Ubuntu Server LTS в VirtualBox. Задай статический IP через netplan (с netplan try), часовой пояс UTC, включи unattended-upgrades.
Проверка: после перезагрузки ip a показывает твой статический адрес, timedatectl — UTC и NTPSynchronized=yes.

Задание 2 — пользователь и SSH

Создай пользователя deploy с правом sudo. Сгенерируй ключ ed25519 на своей машине, положи его на сервер, запрети в sshd_config вход root и вход по паролю.
Проверка: ssh deploy@<ip> пускает без пароля, ssh root@<ip> отклоняется, ssh -o PubkeyAuthentication=no deploy@<ip> отклоняется. Во время настройки вторая сессия оставалась открытой.

Задание 3 — свой сервис

Напиши простой HTTP-сервер (python3 -m http.server 8000 подойдёт) и оформи его systemd-юнитом с отдельным пользователем app, Restart=on-failure и MemoryMax=100M.
Проверка: сервис стартует после перезагрузки; sudo kill -9 <PID> — через 5 секунд он снова работает (systemctl status показывает новый PID); его вывод виден в journalctl -u.

Задание 4 — ловушка с диском

Запусти python3 -c "f=open('/tmp/big','w'); f.write('x'*500_000_000); input()", в другом терминале удали /tmp/big.
Проверка: df -h всё ещё показывает занятое место, sudo lsof +L1 находит удалённый файл; после завершения Python-процесса место освободилось.

Задание 5 — cron и logrotate

Сделай cron-задачу, которая каждые 5 минут дописывает в /var/log/myapp/status.log вывод uptime и df -h /. Напиши правило logrotate для этого файла.
Проверка: в логе появляются записи; logrotate -f создаёт сжатый архив; crontab -l показывает задачу с полными путями и перенаправлением 2>&1.

Задание 6 — разбор поломки

Попроси кого-нибудь (или сделай сам с закрытыми глазами) сломать сервис из задания 3 одним из способов: опечатка в ExecStart, неверные права на рабочую папку, занятый порт.
Проверка: находишь причину, следуя порядку из §18, и записываешь, на каком шаге она обнаружилась.
