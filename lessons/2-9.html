О чём урок

ℹ️Зачем это нужно

До сих пор мы возвращали строки «как есть» — одна строка на запись. Агрегация — это переход от сырых данных к выводам: не «список всех визитов», а «сколько визитов у каждого человека». Ровно так строятся дашборды, отчёты и любая бизнес-аналитика.

📘Словарик на будущее
  • Агрегатная функция — функция, сворачивающая много строк в одно значение: COUNT, SUM, AVG, MIN, MAX.
  • GROUP BY — группировка строк по значению одного или нескольких столбцов перед применением агрегатной функции.
  • HAVING — фильтр, применяемый после группировки (по результату агрегатной функции), в отличие от WHERE, который фильтрует строки до группировки.
  • OLAP (аналитическая обработка) — работа с агрегированными, «свёрнутыми» данными для анализа, в противовес OLTP (обработке отдельных транзакций).
// шаг 2/21 · теория · ~1 мин

COUNT(*) и GROUP BY — базовая агрегация

Аналогия: GROUP BY — как рассортировать колоду карт по мастям в отдельные стопки, а потом посчитать, сколько карт в каждой стопке.

SELECT customer_id, COUNT(*) AS count_of_visits
FROM store_visit
GROUP BY customer_id
ORDER BY count_of_visits DESC, customer_id ASC;

GROUP BY customer_id группирует все строки store_visit по значению customer_id, а COUNT(*) считает, сколько строк попало в каждую группу. Любой столбец в SELECT, который не под агрегатной функцией, обязан быть и в GROUP BY — иначе непонятно, какое из значений этой группы показывать.

// шаг 3/21 · теория · ~1 мин

Сортировка агрегата + LIMIT (топ-N)

Аналогия: если нужен не полный рейтинг, а «топ-4 самых активных» — сортируешь весь список и просто отрезаешь его после четвёртой позиции.

SELECT c.name, COUNT(*) AS count_of_visits
FROM store_visit sv
JOIN customer c ON sv.customer_id = c.id
GROUP BY c.name
ORDER BY count_of_visits DESC
LIMIT 4;

LIMIT n отрезает результат после сортировки — то есть сортировка обязательно должна идти раньше LIMIT по смыслу запроса, иначе «топ-4» окажутся случайными четырьмя строками.

// шаг 4/21 · теория · ~1 мин

Объединяем агрегаты с меткой источника

Аналогия: сравнить «топ по звонкам» и «топ по письмам» в одном общем списке, подписав рядом с каждой строкой, откуда она взялась.

(SELECT s.name, COUNT(*) AS count, 'purchase' AS action_type
 FROM purchase pu
 JOIN product pr ON pu.product_id = pr.id
 JOIN store s ON pr.store_id = s.id
 GROUP BY s.name
 ORDER BY count DESC
 LIMIT 3)

UNION ALL

(SELECT s.name, COUNT(*) AS count, 'visit' AS action_type
 FROM store_visit sv
 JOIN store s ON sv.store_id = s.id
 GROUP BY s.name
 ORDER BY count DESC
 LIMIT 3);

'purchase' и 'visit' — не столбцы таблицы, а строковые константы, добавленные прямо в SELECT как метка происхождения строки. Это стандартный приём, когда нужно объединить агрегаты из разных таблиц, но не потерять информацию, откуда какая строка пришла.

Скобки вокруг каждой части обязательны: без них ORDER BY и LIMIT относились бы ко всему результату UNION ALL, а не к каждому запросу отдельно, и PostgreSQL выдал бы ошибку синтаксиса.

// шаг 5/21 · теория · ~1 мин

COALESCE при неполном объединении данных

Аналогия: если один список (покупки) охватывает не все те же магазины, что и другой (просмотры витрин), при объединении по имени магазина в части строк один из показателей будет отсутствовать — COALESCE подставляет вместо пустоты ноль, чтобы можно было честно сложить оба показателя.

SELECT
    COALESCE(o.store_name, v.store_name) AS name,
    COALESCE(o.purchase_count, 0) + COALESCE(v.visit_count, 0) AS total_count
FROM
    (SELECT s.name AS store_name, COUNT(*) AS purchase_count
     FROM purchase pu JOIN product pr ON pu.product_id = pr.id JOIN store s ON pr.store_id = s.id
     GROUP BY s.name) o
FULL JOIN
    (SELECT s.name AS store_name, COUNT(*) AS visit_count
     FROM store_visit sv JOIN store s ON sv.store_id = s.id
     GROUP BY s.name) v
ON o.store_name = v.store_name
ORDER BY total_count DESC, name ASC;

COALESCE(a, b) возвращает первое не-NULL значение из списка — здесь: «имя из левой части, а если там NULL — то из правой» и «число покупок, а если NULL (в магазине ничего не купили) — то 0». Без COALESCE сложение NULL + число дало бы просто NULL.

// шаг 6/21 · теория · ~1 мин

HAVING — фильтр после группировки

Аналогия: WHERE отсеивает гостей ещё на входе в комнату; HAVING — это уже отбор внутри комнаты, после того как всех разложили по группам и посчитали итог для каждой группы.

SELECT c.name, COUNT(*) AS count_of_visits
FROM store_visit sv
JOIN customer c ON sv.customer_id = c.id
GROUP BY c.name
HAVING COUNT(*) >= 3;

WHERE COUNT(*) >= 3 здесь не сработал бы — на этапе WHERE агрегат ещё не посчитан. HAVING создан именно для условий, зависящих от результата агрегатной функции.

// шаг 7/21 · теория · ~1 мин

Уникальные значения без GROUP BY

Аналогия: не всегда для «уникального списка» нужна группировка — иногда достаточно самого простого инструмента, как в самом начале курса.

SELECT DISTINCT c.name
FROM purchase pu
JOIN customer c ON pu.customer_id = c.id
ORDER BY c.name;

Это не агрегация в строгом смысле (нет агрегатной функции), но относится к той же теме «свернуть много строк в осмысленный список» — иногда DISTINCT даже проще и понятнее, чем GROUP BY без реального счётчика.

// шаг 8/21 · теория · ~1 мин

Несколько агрегатных функций за один проход

Аналогия: вместо того чтобы отдельно спросить «сколько», «сколько в среднем», «максимум» и «минимум», можно задать все четыре вопроса разом об одной и той же группе данных.

SELECT
    s.name,
    COUNT(*) AS purchases,
    ROUND(AVG(pr.price), 2) AS average_price,
    MAX(pr.price) AS max_price,
    MIN(pr.price) AS min_price
FROM purchase pu
JOIN product pr ON pu.product_id = pr.id
JOIN store s ON pr.store_id = s.id
GROUP BY s.name
ORDER BY s.name;

ROUND(значение, знаков) округляет результат AVG до нужного количества знаков после запятой — без этого AVG часто возвращает длинную дробь.

// шаг 9/21 · теория · ~1 мин

Глобальный агрегат — вся таблица как одна группа

Аналогия: если убрать GROUP BY вообще, вся таблица становится одной большой группой — как посчитать средний балл по всей школе, а не по каждому классу отдельно.

SELECT ROUND(AVG(rating), 4) AS global_rating
FROM store;

Без GROUP BY агрегатная функция применяется сразу ко всей таблице целиком, и результат — ровно одна строка.

// шаг 10/21 · теория · ~1 мин

Группировка по двум столбцам

Аналогия: сводная таблица в Excel: строки — города, столбцы — магазины, в ячейках — число покупок. GROUP BY по двум столбцам даёт ровно такие ячейки, только в виде списка.

SELECT c.city, s.name AS store_name, COUNT(*) AS purchases
FROM purchase pu
JOIN customer c ON pu.customer_id = c.id
JOIN product pr ON pu.product_id = pr.id
JOIN store s ON pr.store_id = s.id
GROUP BY c.city, s.name
ORDER BY c.city, s.name;

GROUP BY c.city, s.name — группировка сразу по двум столбцам: результат содержит одну строку на каждую уникальную комбинацию города и магазина. Так видно, например, что казанцы покупают в «Розетка+», а москвичи — в «Пикселе». Покупатель без города попадёт в отдельную группу с NULL в столбце city (см. §12).

// шаг 11/21 · теория · ~1 мин

Явное приведение типов и сравнение с агрегатом

Аналогия: сравнить показатель каждой группы со средним по всем — как сравнить результат отдельного класса со средним баллом по школе и просто ответить «выше» или «ниже».

SELECT
    city,
    COUNT(*) AS customers,
    ROUND(COUNT(*) FILTER (WHERE premium)::numeric / COUNT(*) * 100, 1) AS premium_share,
    ROUND(AVG(age), 1) AS avg_age,
    AVG(age) > (SELECT AVG(age) FROM customer) AS older_than_average
FROM customer
GROUP BY city
ORDER BY city;

COUNT(*) FILTER (WHERE premium)::numeric — явное приведение типа: без него деление двух целых чисел (integer) отбросило бы дробную часть, и доля подписчиков в городе, где их один из трёх, получилась бы нулём. ::numeric заставляет PostgreSQL посчитать точный результат. FILTER подробно разобран в §13. Последний столбец older_than_average — обычное булево сравнение со средним по всей таблице из подзапроса, как в уроке 2.6 (раздел 7).

// шаг 12/21 · теория · ~2 мин

COUNT и NULL: три счётчика, три ответа

Аналогия: посчитать анкеты в стопке, посчитать анкеты с заполненным полем «город» и посчитать, сколько разных городов упомянуто, — три разных числа, хотя стопка одна.

Один из самых частых вопросов на собеседовании по SQL, и одновременно источник расхождений в отчётах.

SELECT
    COUNT(*)                 AS всего_строк,       -- 12
    COUNT(city)              AS с_заполненным,      -- 11, NULL пропущен
    COUNT(DISTINCT city)     AS разных_городов       -- 4, NULL пропущен и повторы схлопнуты
FROM customer;

COUNT(*) считает строки, не заглядывая в содержимое. COUNT(столбец) считает только те строки, где столбец не NULL. COUNT(DISTINCT столбец) вдобавок схлопывает повторы.

Отсюда практическое следствие: если в отчёте «число клиентов» и «число клиентов с указанным городом» расходятся, это не баг, а разные счётчики. И наоборот — использовать COUNT(столбец) там, где имелось в виду COUNT(*), значит молча занизить число.

💡Мелочь про производительность

Раньше советовали писать COUNT(1) вместо COUNT(*), считая это быстрее. В современном PostgreSQL разницы нет никакой — планировщик приводит их к одному. А вот COUNT(*) по огромной таблице всё равно дорог: он честно читает все строки. Для приблизительной оценки числа строк есть быстрый путь через системную статистику:

SELECT reltuples::bigint FROM pg_class WHERE relname = 'purchase';

Агрегаты и NULL: почему среднее «неправильное»

Аналогия: если в опросе на сто человек оценку поставили только шестьдесят, средний балл считается по шестидесяти. Формально верно — но если ждали деления на сто, число окажется неожиданным.

Все агрегатные функции игнорируют NULL. Это разумно, но приводит к результатам, которые надо уметь объяснить:

-- строк 100, значение заполнено у 60
SELECT AVG(score) FROM survey;             -- делит сумму на 60, а не на 100
SELECT SUM(score) / COUNT(*) FROM survey;   -- делит на 100 — другое число

Оба варианта корректны, но отвечают на разные вопросы: «средняя оценка среди ответивших» и «средняя оценка по всем участникам, где неответившие считаются нулём». Какой нужен — решает постановка задачи, и именно здесь чаще всего расходятся аналитик и разработчик.

Если незаполненные надо считать нулями, это делают явно:

SELECT AVG(COALESCE(score, 0)) FROM survey;
⚠️Пустой набор: COUNT даёт 0, SUM даёт NULL
SELECT COUNT(*) FROM product WHERE price < 0;     -- 0
SELECT SUM(price) FROM product WHERE price < 0;   -- NULL, а не 0

Это ломает вычисления в коде приложения: ожидали число, получили пустоту, дальше арифметика превращается в NULL. Правило — оборачивать суммы в COALESCE(SUM(price), 0), если результат идёт куда-то дальше.

Отдельно про GROUP BY: все строки с NULL в столбце группировки попадают в одну группу — в отличие от сравнения, где NULL не равен NULL. Это единственное место, где NULL ведёт себя «как значение», и об этом тоже спрашивают.

// шаг 14/21 · теория · ~2 мин

Условная агрегация: FILTER и CASE

Аналогия: вместо того чтобы трижды пересчитывать одну и ту же стопку с разными условиями, разложить её за один проход сразу по трём коробкам.

Задача возникает постоянно: нужен отчёт, где в одной строке лежат показатели по разным категориям — то, что в таблицах называют сводной таблицей.

SELECT
    s.name,
    COUNT(*)                                          AS всего,
    COUNT(*) FILTER (WHERE c.premium)                  AS от_подписчиков,
    COUNT(*) FILTER (WHERE pr.price >= 10000)          AS дорогих,
    SUM(pr.price) FILTER (WHERE c.premium)             AS выручка_подписчики
FROM purchase pu
JOIN customer c  ON pu.customer_id = c.id
JOIN product pr  ON pu.product_id = pr.id
JOIN store s     ON pr.store_id = s.id
GROUP BY s.name;

FILTER (WHERE ...) применяет условие к конкретной агрегатной функции, не трогая остальные. Один проход по данным вместо трёх отдельных запросов, и читается почти как обычная фраза.

Классический эквивалент, работающий в любой СУБД:

SUM(CASE WHEN c.premium THEN 1 ELSE 0 END) AS от_подписчиков

Он многословнее, и с ним легко ошибиться: для COUNT вместо ELSE 0 нужен ELSE NULL (иначе посчитаются все строки), а для SUM — наоборот. FILTER эту ловушку убирает целиком.

// шаг 15/21 · теория · ~2 мин

Итоги и подытоги: ROLLUP

Аналогия: отчёт по продажам, где под каждым городом стоит итог по городу, а в самом низу — итог по всей стране. Одним запросом, а не тремя.

SELECT c.city, s.name, COUNT(*) AS purchases
FROM purchase pu
JOIN customer c  ON pu.customer_id = c.id
JOIN product pr ON pu.product_id = pr.id
JOIN store s ON pr.store_id = s.id
GROUP BY ROLLUP (c.city, s.name)
ORDER BY c.city, s.name;

ROLLUP (a, b) добавляет к обычной группировке по (a, b) ещё и промежуточные итоги по a, и общий итог по всему. В строках итогов «свёрнутые» столбцы содержат NULL — отличить их от настоящих NULL в данных помогает функция GROUPING():

SELECT
    CASE WHEN GROUPING(c.city) = 1 THEN 'ИТОГО' ELSE c.city END AS city,
    COUNT(*) AS purchases
FROM ... GROUP BY ROLLUP (c.city);

Рядом стоят CUBE (все возможные комбинации группировок, а не только иерархия) и GROUPING SETS (перечислить нужные разрезы вручную). На практике ROLLUP встречается чаще всего — им закрываются почти все отчёты с подытогами.

// шаг 16/21 · теория · ~1 мин

Деньги: почему не float

Аналогия: линейка с делениями по одной десятой миллиметра не годится для ювелирных весов — не потому, что плохая, а потому что не для этого сделана.

Тип float (он же double precision) хранит числа приблизительно — это следствие двоичного представления дробей, то же самое, из-за которого в Python 0.1 + 0.2 != 0.3 (2.1 Python, §18).

SELECT 0.1::float + 0.2::float = 0.3::float;      -- false
SELECT 0.1::numeric + 0.2::numeric = 0.3::numeric;  -- true

Для денег, количеств и всего, что должно сходиться копейка в копейку, используют numeric (он же decimal): он хранит числа точно, ценой чуть меньшей скорости. Ошибка в одну копейку на миллионе строк превращается в расхождение, которое потом ищут неделями.

Отсюда же практическое дополнение к §10: приведение ::numeric нужно не только чтобы избежать целочисленного деления, но и чтобы результат был точным. И ROUND(значение, 2) в PostgreSQL с двумя аргументами работает именно для numeric — для float его придётся приводить.

// шаг 17/21 · итоги · ~1 мин

Если запомнить только главное

  • GROUP BY группирует строки перед применением агрегатной функции; любой «негрупповой» столбец в SELECT обязан быть и в GROUP BY.
  • HAVING фильтрует после группировки (по результату агрегата), WHERE — до неё (по сырым строкам).
  • Строковая константа прямо в SELECT ('order', 'visit') — стандартный способ пометить происхождение строки при объединении разных агрегатов.
  • COALESCE подставляет запасное значение вместо NULL — критично при сложении чисел из неполного объединения.
  • Без GROUP BY агрегатная функция применяется ко всей таблице как к одной группе.
  • Явное приведение типа (::numeric) нужно, чтобы избежать целочисленного деления там, где ожидается дробный результат.
  • COUNT(*) считает строки, COUNT(столбец) пропускает NULL, COUNT(DISTINCT столбец) вдобавок схлопывает повторы — три разных числа.
  • Все агрегаты игнорируют NULL: AVG делит на число заполненных значений, а не на число строк.
  • На пустом наборе COUNT вернёт 0, а SUM и AVG — NULL. Оборачивай в COALESCE, если результат идёт дальше в код.
  • В GROUP BY все NULL попадают в одну группу — единственное место, где NULL ведёт себя как значение.
  • FILTER (WHERE ...) — читаемый способ условной агрегации, без ловушек CASE с ELSE 0 против ELSE NULL.
  • ROLLUP добавляет подытоги и общий итог одним запросом; строки итогов различают через GROUPING().
  • Деньги — только numeric, никогда не float: последний хранит дробные значения приблизительно.

  • Сводные запросы из заданий 3–4 — хороший эндпоинт /reports для shop-api в P1.

Задание 1 — топ-N

Выведи три магазина с наибольшим числом просмотров витрины и три с наибольшим числом покупок, объединив их в один список с меткой visit/purchase.
Проверка: при равенстве значений порядок стабилен (дополнительная сортировка по имени).

Задание 2 — HAVING

Найди покупателей, у которых больше двух покупок, и магазины со средней ценой товара выше средней по всему каталогу.
Проверка: второй запрос сравнивает с подзапросом, а не с захардкоженным числом.

Задание 3 — условная агрегация

В одну строку на магазин выведи число покупок от москвичей, от казанцев и от всех остальных через COUNT(*) FILTER (WHERE ...).
Проверка: сумма трёх колонок равна общему числу покупок — покупатель без города попал в «остальных», а не потерялся (подсказка: city IS DISTINCT FROM 'Москва').

Задание 4 — итоги через ROLLUP

Посчитай выручку по магазину и дню с подытогами по магазину и общим итогом.
Проверка: строки итогов помечены через GROUPING(), а не выглядят как данные с NULL.

Задание 5 — деньги

Создай таблицу платежей с типами real и numeric(12,2), вставь 0.1 десять тысяч раз и сравни суммы.
Проверка: сумма по real отличается от 1000.00, по numeric — нет.
