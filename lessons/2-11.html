О чём урок

ℹ️Зачем это нужно

Это самый «программистский» урок по SQL: здесь база данных перестаёт быть просто хранилищем, которое отвечает на вопросы, и начинает сама реагировать на события (триггеры), решать задачи, где данные заранее неизвестны (рекурсия), и превращаться в основу для аналитических хранилищ данных (DWH) — то, чем реально занимаются дата-инженеры.

📘Словарик на будущее
  • Триггер (trigger) — код, который база автоматически выполняет в ответ на событие (INSERT/UPDATE/DELETE), без явного вызова.
  • PL/pgSQL — процедурный язык PostgreSQL: позволяет писать функции с переменными, циклами и условиями, а не только одним SELECT.
  • Рекурсия (в SQL) — функция или запрос, обращающийся сам к себе, пока не дойдёт до базового случая.
  • DWH (Data Warehouse) — хранилище данных, объединяющее информацию из разных источников для аналитики, в отличие от оперативных баз, обслуживающих текущие транзакции (OLTP).

Триггеры: реагируем на изменения автоматически

Аналогия: триггер — как автоматическая камера видеонаблюдения на складе: она не вмешивается в то, что происходит, но при каждом событии (кто-то занёс товар) сама делает запись в журнал, без участия человека.

Задача из жизни: в магазине кто-то поменял цену, а через неделю покупатель жалуется, что заплатил больше, чем было на витрине. Чтобы разобраться, нужна история изменений, и проще всего её ведёт сама база.

CREATE TABLE product_audit (
    changed_at  timestamptz NOT NULL DEFAULT now(),
    changed_by  text        NOT NULL DEFAULT current_user,
    event       char(1)     NOT NULL,          -- I, U или D
    product_id  bigint      NOT NULL,
    old_price   numeric(10,2),
    new_price   numeric(10,2),
    old_stock   integer,
    new_stock   integer
);

CREATE FUNCTION fnc_trg_product_insert_audit() RETURNS trigger AS $$
BEGIN
    INSERT INTO product_audit (event, product_id, new_price, new_stock)
    VALUES ('I', NEW.id, NEW.price, NEW.stock);
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_product_insert_audit
AFTER INSERT ON product
FOR EACH ROW EXECUTE FUNCTION fnc_trg_product_insert_audit();

NEW — специальная переменная внутри триггерной функции, содержащая новую вставленную строку (для DELETE-триггеров вместо неё используется OLD — версия строки до удаления). Триггер настраивается в два шага: сначала функция с логикой, потом сам TRIGGER, который говорит, когда и как эту функцию вызывать. current_user в значении по умолчанию записывает, под каким пользователем базы сделано изменение.

// шаг 3/21 · теория · ~1 мин

Обобщённый триггер на все три события

Аналогия: вместо трёх отдельных камер (на вход, на изменение полки, на вынос товара) — одна камера с логикой «распознай тип события и реагируй по-разному».

CREATE FUNCTION fnc_trg_product_audit() RETURNS trigger AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO product_audit (event, product_id, new_price, new_stock)
        VALUES ('I', NEW.id, NEW.price, NEW.stock);
    ELSIF TG_OP = 'UPDATE' THEN
        INSERT INTO product_audit (event, product_id, old_price, new_price, old_stock, new_stock)
        VALUES ('U', NEW.id, OLD.price, NEW.price, OLD.stock, NEW.stock);
    ELSIF TG_OP = 'DELETE' THEN
        INSERT INTO product_audit (event, product_id, old_price, old_stock)
        VALUES ('D', OLD.id, OLD.price, OLD.stock);
    END IF;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_product_audit
AFTER INSERT OR UPDATE OR DELETE ON product
FOR EACH ROW EXECUTE FUNCTION fnc_trg_product_audit();

TG_OP — ещё одна специальная переменная, доступная только внутри триггерных функций: строка 'INSERT', 'UPDATE' или 'DELETE', показывающая, какое именно событие вызвало срабатывание. Один триггер, привязанный сразу к INSERT OR UPDATE OR DELETE, заменяет собой три отдельных. При UPDATE доступны обе версии строки — OLD и NEW, поэтому в журнал попадает и старая цена, и новая.

VIEW или FUNCTION?

Аналогия: VIEW — это как готовый бланк с одним заранее заданным вопросом; функция — как анкета с полями, которые каждый раз можно заполнить по-своему при вызове.

CREATE FUNCTION fnc_premium_customers() RETURNS SETOF customer AS $$
    SELECT * FROM customer WHERE premium;
$$ LANGUAGE sql;

SELECT * FROM fnc_premium_customers();

RETURNS SETOF customer означает «функция возвращает набор строк той же структуры, что и таблица customer» — благодаря этому функцию можно вызывать в FROM, как обычную таблицу. Без параметров такая функция ничем не лучше VIEW. Главное отличие проявляется в следующем разделе: функция может принимать параметры.

// шаг 5/21 · теория · ~1 мин

Параметризованная функция

Аналогия: вместо отдельного бланка на каждый город — один универсальный бланк с полем «укажи город», по умолчанию уже заполненным самым частым вариантом.

CREATE FUNCTION fnc_customers_in(pcity varchar DEFAULT 'Москва') RETURNS SETOF customer AS $$
    SELECT * FROM customer WHERE city = pcity;
$$ LANGUAGE sql;

SELECT * FROM fnc_customers_in(pcity := 'Казань');
SELECT * FROM fnc_customers_in();  -- вернёт москвичей, значение по умолчанию

Параметр pcity DEFAULT 'Москва' можно не указывать при вызове — тогда подставится значение по умолчанию. Именованная передача аргумента (pcity := 'Казань') делает вызов понятнее, особенно если параметров несколько.

// шаг 6/21 · теория · ~1 мин

PL/pgSQL функция-обёртка со сложной логикой

Аналогия: если внутри функции нужно не просто выполнить один SELECT, а сначала что-то проверить, разветвить логику — обычного SQL-запроса недостаточно, нужен уже мини-язык программирования внутри базы.

CREATE FUNCTION fnc_restock_needed(pthreshold integer DEFAULT 10)
RETURNS TABLE(store_name varchar, title varchar, stock integer) AS $$
BEGIN
    IF pthreshold < 0 THEN
        RAISE EXCEPTION 'Порог не может быть отрицательным: %', pthreshold;
    END IF;

    RETURN QUERY
    SELECT s.name, pr.title, pr.stock
    FROM product pr
    JOIN store s ON pr.store_id = s.id
    WHERE pr.stock < pthreshold
    ORDER BY pr.stock;
END;
$$ LANGUAGE plpgsql;

SELECT * FROM fnc_restock_needed(8);   -- что пора дозаказать

RETURNS TABLE(...) описывает структуру результата прямо в объявлении функции. RETURN QUERY — команда PL/pgSQL «выполни этот SELECT и верни его результат как результат функции целиком», в отличие от RETURN одного значения. RAISE EXCEPTION прерывает функцию с ошибкой — так функция защищается от бессмысленных аргументов так же, как bash-скрипт из 1.3 Bash, §1. Знак % в тексте ошибки заменяется значением параметра.

// шаг 7/21 · теория · ~1 мин

VARIADIC — функция с переменным числом аргументов

Аналогия: обычная функция ждёт ровно определённое число аргументов, а VARIADIC — как касса, принимающая любое количество товаров в одном чеке, не требуя заранее знать, сколько их будет.

CREATE FUNCTION fnc_cart_total(VARIADIC ids bigint[]) RETURNS numeric AS $$
    SELECT COALESCE(SUM(price), 0) FROM product WHERE id = ANY(ids);
$$ LANGUAGE sql;

SELECT fnc_cart_total(1, 2, 12);               -- 7490 + 3990 + 1290 = 12770
SELECT fnc_cart_total(VARIADIC ARRAY[1, 2]);    -- тот же вызов, если массив уже готов

VARIADIC собирает все переданные аргументы в один массив внутри функции. id = ANY(ids) — «id совпадает с любым элементом массива», аналог IN для массивов. COALESCE(..., 0) защищает от NULL для пустой корзины (2.9 Агрегация, §12).

// шаг 8/21 · теория · ~1 мин

Рекурсивная функция

Аналогия: рекурсия — как матрёшка: чтобы открыть самую большую, сначала нужно открыть чуть меньшую внутри неё, и так далее, пока не дойдёшь до самой маленькой, которая уже не открывается (базовый случай).

Задача, знакомая любому DevOps: база занимает 120 ГБ и растёт на 8% в месяц. Когда кончится диск на 500 ГБ?

CREATE FUNCTION fnc_storage_forecast(start_gb numeric, growth_pct numeric, months integer)
RETURNS TABLE(month integer, size_gb numeric) AS $$
    WITH RECURSIVE forecast(month, size_gb) AS (
        SELECT 0, start_gb
        UNION ALL
        SELECT month + 1, ROUND(size_gb * (1 + growth_pct / 100), 1)
        FROM forecast
        WHERE month < months
    )
    SELECT month, size_gb FROM forecast;
$$ LANGUAGE sql;

SELECT * FROM fnc_storage_forecast(120, 8, 24) WHERE size_gb > 500 LIMIT 1;  -- 19-й месяц

Здесь рекурсия оформлена не как классический вызов функции самой себя, а через WITH RECURSIVE — рекурсивный CTE, о котором подробнее в следующем разделе. Каждый шаг берёт размер с предыдущего шага и умножает на коэффициент роста; WHERE month < months — условие остановки, без которого запрос не закончился бы никогда. Та же идея, что у predict_linear в мониторинге (4.5 Наблюдаемость, §8), только для сложного процента.

// шаг 9/21 · теория · ~2 мин

Рекурсивный CTE (WITH RECURSIVE)

Аналогия: обычный CTE — просто именованный подзапрос; рекурсивный CTE — подзапрос, который на каждом следующем шаге берёт результат своего же предыдущего шага и обрабатывает его дальше, пока не выполнится условие остановки.

Пусть есть таблица сетевых каналов между дата-центрами компании и задержки на каждом:

CREATE TABLE link (src text, dst text, latency_ms integer);
INSERT INTO link VALUES
 ('msk', 'spb', 9), ('spb', 'msk', 9), ('msk', 'kzn', 12), ('kzn', 'msk', 12),
 ('kzn', 'ekb', 14), ('ekb', 'kzn', 14), ('msk', 'ekb', 28), ('ekb', 'msk', 28),
 ('ekb', 'nsk', 22), ('nsk', 'ekb', 22);

WITH RECURSIVE routes AS (
    -- базовый случай: все каналы, выходящие из Москвы
    SELECT src, dst, latency_ms AS total_ms, ARRAY[src, dst] AS path
    FROM link WHERE src = 'msk'

    UNION ALL

    -- рекурсивный шаг: продолжаем маршрут ещё одним каналом
    SELECT r.src, l.dst, r.total_ms + l.latency_ms, r.path || l.dst
    FROM routes r
    JOIN link l ON r.dst = l.src
    WHERE NOT l.dst = ANY(r.path)        -- не возвращаемся туда, где уже были
)
SELECT * FROM routes;

WITH RECURSIVE состоит из двух частей, соединённых UNION ALL: «базовый случай» (откуда стартуем) и «рекурсивный шаг» (как продолжить маршрут на основе уже накопленного пути). Условие NOT l.dst = ANY(r.path) — защита от бесконечного цикла: без него алгоритм бесконечно ходил бы туда-обратно между Москвой и Петербургом.

Тот же приём применяют к любым иерархиям: дерево категорий товаров, цепочка руководителей, зависимости между сервисами.

Самый быстрый маршрут

Аналогия: навигатор перебирает все дороги и показывает самую быструю — здесь то же самое для сетевых каналов.

WITH RECURSIVE routes AS (
    SELECT dst, latency_ms AS total_ms, ARRAY['msk', dst] AS path
    FROM link WHERE src = 'msk'
    UNION ALL
    SELECT l.dst, r.total_ms + l.latency_ms, r.path || l.dst
    FROM routes r
    JOIN link l ON r.dst = l.src
    WHERE NOT l.dst = ANY(r.path)
)
SELECT total_ms, array_to_string(path, ' → ') AS route
FROM routes
WHERE dst = 'nsk'
ORDER BY total_ms
LIMIT 1;                     -- 48 мс: msk → kzn → ekb → nsk

Рекурсивный CTE строит все маршруты без повторов, а финальный SELECT оставляет только ведущие в Новосибирск и берёт самый быстрый. Прямой канал Москва — Екатеринбург (28 мс) проигрывает пути через Казань (12 + 14 = 26 мс) — такие неочевидные результаты и находят перебором.

Полный перебор растёт очень быстро с числом узлов, поэтому для больших графов используют специальные алгоритмы (Дейкстра и его родственники) или расширения вроде pgRouting. Для десятка узлов рекурсивный CTE справляется мгновенно.

Хранилище данных (DWH): ODS-слой и «неидеальные» данные

Аналогия: если данные приходят из трёх разных независимых сервисов, собранных в одно хранилище, — это как сводить три разных списка гостей от трёх разных организаторов вечеринки: где-то кто-то не указал имя, где-то гость вообще не значится ни в одном списке.

Пусть платежи пишет отдельный сервис оплаты в свою таблицу payment (customer_id, amount, method_id), а аналитик собирает их в хранилище рядом с покупателями и справочником способов оплаты:

SELECT
    COALESCE(c.name, 'удалённый покупатель') AS customer,
    COALESCE(m.name, 'неизвестный способ')   AS method,
    COUNT(*)                                 AS payments,
    SUM(p.amount)                            AS volume
FROM payment p
LEFT JOIN customer c       ON p.customer_id = c.id
LEFT JOIN payment_method m ON p.method_id = m.id
GROUP BY 1, 2
ORDER BY volume DESC;

ODS (Operational Data Store) — первый слой хранилища данных, куда «сырые» данные попадают почти без изменений из разных источников. Именно здесь чаще всего встречаются несогласованности: платёж есть, а покупателя (уже удалённого или ещё не синхронизированного) — нет. INNER JOIN молча выбросил бы такие платежи, и сумма в отчёте не сошлась бы с банковской выпиской. LEFT JOIN + COALESCE — стандартная связка для таких ситуаций (см. также 2.9, раздел 4). GROUP BY 1, 2 — короткая запись «группировать по первому и второму столбцу результата».

// шаг 12/21 · теория · ~1 мин

Временная модель данных: «ближайшее значение по времени»

Аналогия: чтобы узнать, сколько стоил товар в день покупки, нужен не «текущий ценник», а последний ценник, повешенный до этого дня.

Цены меняются, а в таблице product хранится только текущая. Если вести историю цен (её как раз наполняет триггер из §2, или отдельная таблица price_history(product_id, price, valid_from)), можно восстановить цену на любой момент:

SELECT DISTINCT ON (pu.id)
    pu.id AS purchase_id, pu.purchase_date, ph.price AS price_at_purchase
FROM purchase pu
JOIN price_history ph
  ON ph.product_id = pu.product_id AND ph.valid_from <= pu.purchase_date
ORDER BY pu.id, ph.valid_from DESC;

DISTINCT ON (столбцы) — расширение PostgreSQL: оставляет только первую строку для каждой уникальной комбинации указанных столбцов, согласно ORDER BY. Здесь это даёт «последнюю цену, установленную в день покупки или раньше» — классический паттерн временных (temporal) моделей данных, где важна не только сама величина, но и момент времени, когда она была актуальна. Те же запросы пишут для курсов валют, тарифов и версий конфигурации.

// шаг 13/21 · теория · ~4 мин

Оконные функции

Аналогия: GROUP BY — как свести отчёт по отделам, потеряв фамилии. Оконная функция — как оставить полный список сотрудников, но приписать рядом с каждым итог по его отделу и место в рейтинге.

Тема, которая на собеседованиях по SQL идёт сразу после JOIN, и главный инструмент любой аналитики. Ключевое отличие формулируется одной фразой: GROUP BY схлопывает строки, OVER — нет.

SELECT
    name,
    department,
    salary,
    SUM(salary)  OVER (PARTITION BY department)                AS отдел_итого,
    ROUND(100.0 * salary / SUM(salary) OVER (PARTITION BY department), 1) AS доля_в_отделе,
    RANK()       OVER (PARTITION BY department ORDER BY salary DESC)       AS место_в_отделе
FROM employees;

Все исходные строки остаются на месте, и к каждой добавляются вычисления по её «окну» — группе строк, к которой она относится.

Устройство окна. В скобках после OVER задают две вещи: PARTITION BY — как разбить строки на группы (аналог GROUP BY, но без схлопывания), и ORDER BY — в каком порядке нумеровать и накапливать внутри группы. Пустой OVER () означает «окно — вся выборка целиком».

Функции ранжирования — их три, и разницу спрашивают:

Функция При одинаковых значениях Пример: 100, 100, 90
ROW_NUMBER() нумерует подряд, произвольно 1, 2, 3
RANK() одинаковый ранг, дальше пропуск 1, 1, 3
DENSE_RANK() одинаковый ранг, без пропуска 1, 1, 2

Соседние строки — LAG и LEAD смотрят назад и вперёд:

SELECT
    day,
    revenue,
    LAG(revenue) OVER (ORDER BY day)                        AS вчера,
    revenue - LAG(revenue) OVER (ORDER BY day)               AS прирост,
    ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY day))
          / NULLIF(LAG(revenue) OVER (ORDER BY day), 0), 1)   AS прирост_проц
FROM daily_stats;

Это готовый ответ на постоянную задачу «сравнить с предыдущим периодом», для которой раньше приходилось соединять таблицу саму с собой по хитрому условию.

Накопительный итог — через рамку окна:

SELECT
    day,
    revenue,
    SUM(revenue) OVER (ORDER BY day
                       ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS нарастающим,
    AVG(revenue) OVER (ORDER BY day
                       ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)          AS среднее_за_7_дней
FROM daily_stats;

ROWS BETWEEN ... AND ... задаёт, какие именно строки попадают в окно относительно текущей. Скользящее среднее за неделю — типовой приём для сглаживания графиков в мониторинге.

💡Топ-N внутри каждой группы — классическая задача с собеседования

«Выбрать три самых дорогих товара в каждом магазине». Без оконных функций это неудобный запрос с коррелированным подзапросом; с ними — прямолинейно:

SELECT * FROM (
    SELECT s.name AS store, pr.title, pr.price,
           ROW_NUMBER() OVER (PARTITION BY s.id ORDER BY pr.price DESC) AS rn
    FROM product pr JOIN store s ON pr.store_id = s.id
) t
WHERE rn <= 3;

Оконную функцию нельзя использовать в WHERE того же уровня — она вычисляется на шаге SELECT, то есть после WHERE (2.6 SQL-запросы, §1). Поэтому результат оборачивают в подзапрос или CTE и фильтруют снаружи. Это же объясняет, почему WHERE rn <= 3 внутри не работает.

// шаг 14/21 · теория · ~1 мин

Триггеры: когда лучше без них

Раздел 1 показал, как триггеры устроены. Не менее важно понимать, когда их не стоит применять.

Триггер — скрытая логика: разработчик выполняет обычный INSERT и не видит, что при этом сработали три функции, изменившие ещё две таблицы. Отсюда типичные проблемы: неожиданно медленная вставка, циклические срабатывания триггеров друг от друга и трудность отладки — в коде приложения причину не найти, она в базе.

Уместно: аудит изменений (как в §1–2), поддержка денормализованных счётчиков, автозаполнение служебных полей вроде updated_at.

Неуместно: бизнес-логика (её место в приложении, где она видна, тестируема и версионируется), обращения к внешним системам, тяжёлые вычисления на каждую строку.

⚠️Практическое следствие для эксплуатации

Массовая загрузка в таблицу с триггером «на каждую строку» может идти в десятки раз дольше ожидаемого. Перед разовой заливкой больших объёмов триггеры обычно отключают (ALTER TABLE ... DISABLE TRIGGER) и включают обратно после — не забыв воспроизвести то, что они должны были сделать.

Миграции схемы без простоя

Аналогия: менять рельсы под идущим поездом можно — но только если делать это участками и в правильном порядке.

Изменения схемы в реальном проекте не выполняют руками в psql. Их оформляют миграциями — пронумерованными файлами в репозитории, которые применяются автоматически при выкате: Alembic для Python, Flyway и Liquibase в мире Java, migrate для Go. Каждая миграция версионируется вместе с кодом, и база всегда соответствует той версии приложения, которая её использует.

Ключевое, что нужно знать про сами изменения: некоторые из них блокируют таблицу.

Безопасно Опасно
ADD COLUMN без NOT NULL ALTER COLUMN ... TYPE — переписывает таблицу
ADD COLUMN ... DEFAULT (PostgreSQL 11+) SET NOT NULL — полное сканирование
CREATE INDEX CONCURRENTLY CREATE INDEX без CONCURRENTLY
DROP COLUMN ADD FOREIGN KEY — проверка всех строк
ADD CONSTRAINT ... NOT VALID RENAME COLUMN — ломает работающий код

Приём с NOT VALID стоит запомнить: ограничение добавляется мгновенно и действует для новых строк, а проверка существующих запускается отдельно командой VALIDATE CONSTRAINT, которая работает без тяжёлой блокировки.

Переименование столбца без простоя делается не одной миграцией, а четырьмя выкатами: добавить новый столбец → научить код писать в оба → перелить данные пачками → переключить чтение на новый → удалить старый. Долго, зато в любой момент можно откатиться, и обе версии кода работают одновременно.

Это и есть главное правило: во время выката старая и новая версии приложения работают параллельно, поэтому миграция обязана быть совместима с обеими. Отсюда следует, что удаление столбца и выкат кода, переставшего его использовать, — это два разных релиза, а не один.

🛑Про блокировки в миграциях

Блокировка держится до конца транзакции, а миграции обычно выполняются в транзакции целиком. Значит, одна «тяжёлая» команда блокирует таблицу на всё время миграции, включая безобидные соседние шаги. Отсюда практика: выставлять lock_timeout перед миграцией, чтобы она честно падала вместо того, чтобы копить очередь запросов, и разбивать опасные изменения на отдельные шаги.

Бэкапы и восстановление

Аналогия: бэкап, который никогда не разворачивали, — это не бэкап, а надежда.

Два принципиально разных инструмента:

# логический дамп: SQL-текст, переносимый между версиями
pg_dump -Fc -d store -f store.dump
pg_restore -d store_new store.dump

# физическая копия всего кластера, основа для восстановления на момент времени
pg_basebackup -D /backup/base -Ft -z -P

pg_dump делает логическую копию: по сути, набор команд для воссоздания данных. Работает без остановки базы, даёт согласованный снимок на момент начала, годится для переноса между версиями PostgreSQL и для выгрузки отдельной таблицы. Минус — восстановление большой базы занимает часы.

pg_basebackup копирует файлы кластера целиком. Вместе с архивом журнала предзаписи (WAL) это даёт восстановление на момент времени (PITR): можно откатить базу к состоянию за минуту до того, как кто-то выполнил DELETE без WHERE.

Три вещи, о которых спрашивают и которые важнее самих команд:

Проверка восстановления. Бэкап, который ни разу не разворачивали, с высокой вероятностью не развернётся и в нужный момент. Регулярное автоматическое восстановление на отдельный стенд с проверкой — обязательная часть, а не приятное дополнение.

RPO и RTO. Сколько данных допустимо потерять (Recovery Point Objective) и как быстро надо восстановиться (Recovery Time Objective). Ежедневный дамп означает RPO в сутки: авария в 23:00 стоит целого дня работы. Это те же соглашения об уровне сервиса, что SLO из 1.4 Метрики и логи, §9.

Репликация — не бэкап. Реплика повторяет всё, включая ошибочный DROP TABLE. Она защищает от отказа сервера, но не от ошибки человека. Нужны обе вещи, и путать их — распространённое и дорогое заблуждение.

// шаг 17/21 · итоги · ~2 мин

Если запомнить только главное

  • Триггер реагирует на события автоматически; NEW/OLD — специальные переменные с новой/старой версией строки, TG_OP — тип события в обобщённом триггере.
  • Функция отличается от VIEW тем, что принимает параметры (в том числе со значением по умолчанию и VARIADIC для переменного числа аргументов).
  • PL/pgSQL нужен, когда одного SQL-запроса недостаточно — там есть переменные, IF, RETURN QUERY.
  • WITH RECURSIVE = базовый случай + рекурсивный шаг, соединённые UNION ALL; всегда нужно условие остановки, иначе бесконечный цикл.
  • ODS-слой хранилища данных получает «сырые», часто неполные и несогласованные данные из разных источников — LEFT JOIN + COALESCE защищают от потери строк при пропусках.
  • DISTINCT ON — способ выбрать «последнюю актуальную запись на момент времени» без сложных подзапросов.
  • Оконные функции: GROUP BY схлопывает строки, OVER — нет. PARTITION BY задаёт группу, ORDER BY — порядок внутри неё.
  • ROW_NUMBER нумерует подряд, RANK пропускает после одинаковых, DENSE_RANK не пропускает. LAG/LEAD смотрят на соседние строки.
  • Оконную функцию нельзя использовать в WHERE того же уровня — она вычисляется после него; оборачивай в подзапрос или CTE.
  • Триггеры — скрытая логика: годятся для аудита и служебных полей, не годятся для бизнес-правил. Перед массовой заливкой их отключают.
  • Миграции — файлы в репозитории, а не команды руками. ALTER COLUMN TYPE, SET NOT NULL, ADD FOREIGN KEY блокируют таблицу; ADD CONSTRAINT ... NOT VALID — нет.
  • Во время выката старый и новый код работают одновременно, поэтому переименование столбца — четыре релиза, а не один.
  • pg_dump — логическая копия для переноса, pg_basebackup + WAL — восстановление на момент времени. Реплика не является бэкапом. Бэкап, который не разворачивали, не считается бэкапом.

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

💡В портфолио
  • Задание 5 (бэкап по расписанию и проверка восстановления) — раздел «Эксплуатация» в P1.
  • Задание 4 (миграции без простоя) пригодится в P3: там миграции запускаются отдельной задачей перед выкаткой.

Задание 1 — аудит через триггер

Сделай таблицу аудита и триггер, который записывает в неё INSERT, UPDATE и DELETE по таблице customer со старым и новым значением в JSONB (to_jsonb(OLD), to_jsonb(NEW)).
Проверка: после трёх операций в аудите три записи с правильным типом операции.

Задание 2 — оконные функции

Для каждой покупки выведи порядковый номер покупки этого покупателя, сумму нарастающим итогом и разницу в цене с предыдущей покупкой (ROW_NUMBER, SUM() OVER, LAG).
Проверка: результат проверен вручную для одного покупателя.

Задание 3 — рекурсивный CTE

Создай таблицу с иерархией (сотрудники и руководители или категории) и выведи всё дерево с уровнем вложенности и путём.
Проверка: при цикле в данных запрос не зависает (ограничение глубины или проверка пути).

Задание 4 — миграция без простоя

Переименуй столбец, не ломая работающее приложение: добавить новый, писать в оба, перенести данные пачками, переключить чтение, удалить старый. Миграции — через Alembic, Flyway или файлы с номерами.
Проверка: каждый шаг — отдельная миграция, которую можно применить и откатить; индекс создан через CREATE INDEX CONCURRENTLY.

Задание 5 — бэкап и восстановление

Сделай бэкап базы через pg_dump -Fc, удали таблицу и восстанови её pg_restore в отдельную базу. Настрой ежедневный бэкап по cron с хранением 7 копий.
Проверка: восстановление действительно выполнено и данные сверены; без этого бэкап не считается рабочим.
