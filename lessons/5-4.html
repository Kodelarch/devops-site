О чём урок

ℹ️Зачем это нужно

В 5.3 Helm и Kustomize релиз обновлялся командой helm upgrade — руками или из пайплайна. У этого подхода три слабых места: пайплайну нужны права администратора на кластер, никто не замечает, если кто-то поправил ресурс через kubectl edit, и на вопрос «что сейчас развёрнуто в проде» приходится лезть в кластер.

GitOps переворачивает схему: желаемое состояние кластера целиком лежит в git, а внутри кластера работает агент, который постоянно сравнивает реальность с репозиторием и выравнивает расхождения. Деплой — это merge request в репозиторий конфигурации, откат — git revert.

Argo CD — самый распространённый GitOps-инструмент для Kubernetes. В вакансиях он встречается в связке «Kubernetes, Helm, ArgoCD» настолько часто, что стал почти обязательной строкой для позиций с Kubernetes.

📘Словарик на будущее
  • GitOps — подход, где git — единственный источник правды о состоянии инфраструктуры, а изменения применяет агент в кластере.
  • Желаемое состояние (desired state) — то, что описано в git.
  • Фактическое состояние (live state) — то, что реально запущено в кластере.
  • Синхронизация (sync) — приведение кластера к описанию в git.
  • Дрейф — расхождение между git и кластером.
  • Application — объект Argo CD: «вот этот путь в этом репозитории разворачивай в этот namespace».
  • ApplicationSet — генератор множества Application по шаблону.
  • Sync wave — порядок применения ресурсов при синхронизации.

Push и pull: два способа доставки

Аналогия: push — курьер с ключами от всех квартир, который сам заносит посылки. Pull — у каждой квартиры свой консьерж, который сам забирает посылки из пункта выдачи и знает, что должно лежать в квартире.

Push-модель — то, что делалось до сих пор (3.2 CI-CD, 6.1 CI-CD в Kubernetes): пайплайн собирает образ и сам выполняет helm upgrade или kubectl apply в кластере.

Проблемы push:

  • Пайплайну нужен доступ к кластеру, обычно широкий. Скомпрометированный раннер или утёкшая переменная CI — это доступ ко всему продакшену.
  • Изменения в обход пайплайна никто не видит. Кто-то сделал kubectl scale в аварии и забыл вернуть — git говорит одно, кластер живёт другим.
  • Нет постоянной сверки. Пайплайн применил изменения один раз и забыл про них.

Pull-модель (GitOps): агент живёт внутри кластера, сам ходит в git и применяет изменения.

  • Кластеру не нужно открывать доступ наружу. Агент сам ходит в git, а пайплайн вообще не трогает кластер — он только коммитит новый тег образа в репозиторий.
  • Постоянная сверка. Агент каждые несколько минут сравнивает git с кластером и показывает дрейф, а при включённой самоисправке — откатывает ручные правки.
  • История и аудит бесплатно. Каждое изменение продакшена — коммит с автором, ревью и временем (0.1 Git, §16).
// шаг 3/19 · теория · ~1 мин

Четыре принципа GitOps

Аналогия: правила бухгалтерии: каждая операция — проводка в книге, книгу не правят задним числом, остатки на счетах сверяются с книгой.

Проект OpenGitOps сформулировал четыре принципа:

  1. Декларативность. Желаемое состояние описано декларативно — манифестами, Helm-чартами, Kustomize (5.3 Helm и Kustomize), а не скриптами с командами.
  2. Версионирование и неизменяемость. Состояние хранится в git, каждая версия неизменна, есть полная история.
  3. Автоматическое получение. Агенты сами забирают желаемое состояние из источника, никто его им не «вталкивает».
  4. Постоянная сверка. Агенты непрерывно сравнивают фактическое состояние с желаемым и устраняют расхождения.

Из этих принципов следует практическое правило: kubectl apply и kubectl edit в продакшене руками не делают. Любое изменение — коммит. Иначе агент либо откатит правку, либо будет постоянно показывать дрейф.

Установка Argo CD

Аналогия: заселяем консьержа: выделяем ему комнату, даём ключи и список квартир.

kubectl create namespace argocd
kubectl apply -n argocd \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# пароль начального администратора
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d

# доступ к интерфейсу без Ingress — для учебного стенда
kubectl -n argocd port-forward svc/argocd-server 8080:443

В продакшене Argo CD ставят Helm-чартом argo/argo-cd с параметрами в git и открывают интерфейс через Ingress с HTTPS (5.2 Kubernetes в работе, §7). После первого входа начальный пароль меняют, а секрет argocd-initial-admin-secret удаляют.

Основные компоненты:

  • argocd-server — API и веб-интерфейс.
  • repo-server — клонирует репозитории и рендерит манифесты (выполняет helm template и kustomize build).
  • application-controller — сравнивает отрендеренные манифесты с кластером и синхронизирует.

Консольная утилита argocd удобна для скриптов и отладки:

argocd login localhost:8080
argocd app list
argocd app get shop
argocd app diff shop       # что изменится
argocd app sync shop       # синхронизировать вручную
argocd app history shop

Application: что и куда разворачивать

Аналогия: карточка в картотеке консьержа: «квартира 12, содержимое — по описи из папки №5».

Главный объект Argo CD — Application. Он связывает источник в git с местом в кластере:

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: shop-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://gitlab.com/my-team/shop-deploy.git
    targetRevision: main
    path: charts/shop
    helm:
      valueFiles:
        - values-prod.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: shop-prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

Разбор:

  • source — откуда: репозиторий, ветка или тег, путь. Источник может быть каталогом с манифестами, Kustomize-оверлеем или Helm-чартом — Argo CD определяет тип сам.
  • destination — куда: кластер и namespace. kubernetes.default.svc — тот кластер, где установлен сам Argo CD.
  • syncPolicy.automated — синхронизировать автоматически при изменениях в git.
  • prune — удалять из кластера ресурсы, которые удалили из git. Без этого флага удалённый из репозитория Deployment продолжит работать.
  • selfHeal — откатывать ручные изменения в кластере к состоянию из git.

Сам Application — тоже манифест, и его тоже хранят в git. Как это организовать, разбирается в §8.

Статусы: Sync и Health

Аналогия: два разных вопроса про посылку: «доставили ли то, что заказывали?» и «работает ли то, что доставили?».

У каждого Application два независимых статуса:

Sync status — совпадает ли кластер с git:

  • Synced — совпадает.
  • OutOfSync — есть разница: в git появились изменения или в кластере кто-то поправил ресурс руками.

Health status — работает ли то, что развёрнуто:

  • Healthy — все ресурсы в порядке: у Deployment готовы все реплики, у Ingress есть адрес.
  • Progressing — идёт выкатка.
  • Degraded — что-то сломано: поды в CrashLoopBackOff, выкатка не завершилась.
  • Missing — ресурса нет в кластере.

Комбинация Synced + Degraded — частая ситуация: git применён полностью, но новая версия не стартует. Argo CD свою работу сделал, проблема в приложении или конфиге. Дальше — порядок разбора пода из 5.1 Kubernetes, §15.

💡Интерфейс Argo CD как карта приложения

Веб-интерфейс показывает дерево ресурсов: Application → Deployment → ReplicaSet → Pod, рядом Service, Ingress, ConfigMap. По цвету значков сразу видно, где проблема, а по клику — события и логи пода. Для новичка это лучший способ увидеть, как ресурсы Kubernetes связаны между собой.

Ручная и автоматическая синхронизация

Аналогия: автоплатёж или подтверждение каждого платежа вручную.

Автоматическая синхронизация — Argo CD применяет изменения сам, как только видит новый коммит (опрашивает репозиторий раз в 3 минуты или сразу по вебхуку от GitLab/GitHub). Подходит для dev и staging, а во многих командах и для продакшена — там контролем служит ревью merge request.

Ручная синхронизация — Argo CD показывает OutOfSync и дифф, а применяет человек кнопкой Sync или командой argocd app sync. Выбирают, когда нужен явный момент выкатки.

selfHeal стоит понимать отдельно: он реагирует не на изменения в git, а на изменения в кластере. Кто-то сделал kubectl scale deploy shop --replicas=10 — через несколько секунд Argo CD вернёт число реплик из git. Для продакшена это обычно правильно, но это нужно знать заранее: в аварии ручной фикс в кластере продержится секунды. Аварийное изменение делают коммитом — или временно отключают автосинхронизацию для приложения.

⚠️HPA и selfHeal

Если число реплик управляется автомасштабированием (5.2 Kubernetes в работе, §16), а в манифесте Deployment тоже указано replicas, Argo CD и HPA будут бесконечно перетягивать значение. Решение — не указывать replicas в манифесте при наличии HPA или добавить поле в ignoreDifferences.

Откат

Аналогия: отмена проводки в бухгалтерии — не стирают старую запись, а делают новую, обратную.

В GitOps правильный откат — git revert коммита, который принёс проблему. Argo CD увидит новый коммит и выкатит предыдущее состояние. История сохраняется, причина отката видна в git.

Argo CD умеет и откат из интерфейса (argocd app rollback shop <id>) на одну из предыдущих синхронизаций. Но при включённой автосинхронизации он сразу же снова применит то, что лежит в git, — поэтому для приложений с автосинхронизацией откат делают только через git.

Сравнение с 3.2 CI-CD, §15: там откат — повторный запуск старого пайплайна или helm rollback. В GitOps — обычный коммит, и в любой момент git отвечает на вопрос «что сейчас в продакшене».

// шаг 9/19 · теория · ~1 мин

Структура репозиториев

Аналогия: разделение чертежей и складской книги: инженеры правят чертежи, а книга учёта того, что где стоит, ведётся отдельно.

Принятая практика — два репозитория:

  • Репозиторий приложения — код, Dockerfile, тесты, пайплайн сборки.
  • Репозиторий конфигурации (deploy/gitops-репозиторий) — Helm-чарты или Kustomize, values для окружений, объекты Application.

Почему раздельно: изменения конфигурации не должны запускать сборку приложения, у репозиториев разные права доступа (продакшен-конфиг правят не все), а история деплоев не смешивается с историей кода.

Пример структуры репозитория конфигурации:

shop-deploy/
  apps/                      # объекты Application
    shop-dev.yaml
    shop-staging.yaml
    shop-prod.yaml
    monitoring.yaml
  charts/shop/               # чарт приложения
    Chart.yaml
    templates/
    values.yaml
    values-dev.yaml
    values-staging.yaml
    values-prod.yaml

App of Apps. Чтобы и сами Application не создавать руками, заводят одно корневое Application, которое указывает на каталог apps/. Argo CD разворачивает его — и тем самым создаёт все остальные Application. Добавил файл в apps/ — появилось новое приложение. Весь кластер описывается одним репозиторием.

ApplicationSet решает ту же задачу генератором: «для каждого каталога в envs/* создай Application» или «для каждого кластера из списка». Удобно, когда окружений или кластеров много.

Связка с CI: как новый образ попадает в кластер

Аналогия: конвейер: цех собирает деталь и кладёт на склад, а в складскую книгу вносит новую запись. Сборку на объект консьерж забирает по книге.

Полный путь изменения от коммита разработчика до продакшена:

  1. Разработчик пушит код в репозиторий приложения.
  2. CI собирает образ, прогоняет тесты, сканирует (6.2 DevSecOps) и пушит образ с тегом коммита — например registry/shop:3f9ab1e.
  3. CI коммитит новый тег в репозиторий конфигурации: меняет image.tag в values-staging.yaml.
  4. Argo CD видит коммит и выкатывает staging.
  5. Для продакшена — merge request с тем же изменением в values-prod.yaml, ревью и merge.
# фрагмент .gitlab-ci.yml в репозитории приложения
update-staging:
  stage: deploy
  image: alpine/git
  script:
    - git clone https://oauth2:${DEPLOY_REPO_TOKEN}@gitlab.com/my-team/shop-deploy.git
    - cd shop-deploy
    - 'sed -i "s/^  tag: .*/  tag: ${CI_COMMIT_SHORT_SHA}/" charts/shop/values-staging.yaml'
    - git commit -am "shop: staging -> ${CI_COMMIT_SHORT_SHA}"
    - git push
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

Ключевое отличие от push-модели: у пайплайна нет доступа к кластеру вообще. Только токен на запись в репозиторий конфигурации.

Альтернатива шагу 3 — Argo CD Image Updater: отдельный компонент сам следит за реестром образов и обновляет тег. Удобно, но изменения появляются в git от имени робота, и команды часто предпочитают явный коммит из CI.

Почему тег коммита, а не latest: с latest манифест не меняется, Argo CD не видит изменений и ничего не выкатывает, а откатиться на «предыдущий latest» невозможно. Неизменяемые теги — обязательное условие GitOps.

Секреты в GitOps

Аналогия: в общую книгу учёта нельзя вписать код от сейфа, но можно вписать запечатанный конверт, который откроет только сейф.

Если всё состояние в git, возникает очевидный вопрос: а пароли? Kubernetes Secret в base64 — это не шифрование (5.1 Kubernetes, §7), класть его в репозиторий нельзя.

Распространённые решения:

  • Sealed Secrets — секрет шифруется публичным ключом контроллера в кластере (kubeseal), в git лежит зашифрованный SealedSecret, расшифровать может только контроллер.
  • SOPS — шифрует значения в YAML-файлах ключом из облачного KMS или age; Argo CD расшифровывает через плагин.
  • External Secrets Operator — в git лежит только ссылка «возьми пароль db/prod из хранилища», а сам секрет оператор забирает из HashiCorp Vault или облачного менеджера секретов и создаёт обычный Secret в кластере.

Для учебного проекта проще всего Sealed Secrets. В компаниях чаще встречается External Secrets с Vault — подробнее в 6.2 DevSecOps.

// шаг 12/19 · теория · ~2 мин

Порядок применения: sync waves и hooks

Аналогия: в ремонте сначала проводка, потом штукатурка, потом обои. Перепутать порядок — переделывать.

По умолчанию Argo CD применяет ресурсы в разумном порядке по типам (сначала Namespace и CRD, потом ConfigMap и Secret, потом Deployment). Когда нужно тоньше — например, миграция базы до запуска новой версии приложения (6.3 Итоговый проект, §6), — используют аннотации:

# миграция выполнится до основной синхронизации
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: registry/shop:3f9ab1e
          command: ["python", "manage.py", "migrate"]

# волны: меньший номер применяется раньше
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "-1"

Если хук PreSync упал, синхронизация остановится и новая версия не будет выкачена — это ровно то поведение, которое нужно для миграций.

// шаг 13/19 · теория · ~1 мин

Права: проекты и RBAC

Аналогия: у консьержа список: какие квартиры обслуживать, из каких пунктов выдачи принимать посылки и кто из жильцов может давать ему указания.

AppProject ограничивает, что может делать группа приложений:

apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: shop
  namespace: argocd
spec:
  sourceRepos:
    - https://gitlab.com/my-team/shop-deploy.git
  destinations:
    - namespace: "shop-*"
      server: https://kubernetes.default.svc
  clusterResourceWhitelist: []      # запретить кластерные ресурсы

Приложения проекта shop могут брать манифесты только из своего репозитория и разворачивать только в namespace shop-*. Даже если в репозиторий попадёт ClusterRole с правами администратора, Argo CD откажется её применять.

Пользователей Argo CD подключают через SSO (GitLab, корпоративный каталог) и раздают роли: разработчики видят приложения и могут синхронизировать staging, а продакшен — только чтение. Это продолжение идей RBAC из 5.2 Kubernetes в работе, §14.

// шаг 14/19 · теория · ~1 мин

Argo CD и Flux

Аналогия: два производителя одного типа устройства: делают одно и то же, отличаются удобством и подходом.

Flux — второй крупный GitOps-инструмент, тоже проект CNCF. Отличия:

Argo CD Flux
Интерфейс Развитый веб-интерфейс с картой ресурсов Нет встроенного, управляется CLI и CRD
Модель Центральный сервер, может управлять многими кластерами Набор контроллеров в каждом кластере
Порог входа Ниже за счёт интерфейса Выше, но проще встраивается в автоматизацию

В российских вакансиях Argo CD встречается заметно чаще. Принципы одинаковые, и освоив один, второй понимаешь за день.

// шаг 15/19 · итоги · ~1 мин

Если запомнить только главное

  • GitOps: git — единственный источник правды, агент в кластере сам забирает изменения (pull) и постоянно сверяет состояние.
  • Pull-модель убирает доступ пайплайна к кластеру и делает видимым любой дрейф.
  • Application связывает путь в git с namespace в кластере. prune удаляет лишнее, selfHeal откатывает ручные правки.
  • Два статуса: Sync (совпадает ли с git) и Health (работает ли). Synced + Degraded — проблема в приложении, а не в Argo CD.
  • Откат — git revert, а не кнопка в интерфейсе.
  • Код приложения и конфигурация — в разных репозиториях. Все Application — тоже в git (App of Apps, ApplicationSet).
  • CI собирает образ и коммитит новый тег в репозиторий конфигурации. Теги неизменяемые, никакого latest.
  • Секреты — Sealed Secrets, SOPS или External Secrets, но не Secret в base64.
  • Миграции — через хук PreSync, порядок — через sync waves.
  • AppProject ограничивает источники и namespace, доступ к продакшену — только чтение для большинства.
  • Руками в продакшен-кластер не правят: всё через коммит.
// шаг 16/19 · практика

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

💡В портфолио
  • Все задания урока — раздел «GitOps» в P3: Argo CD, репозиторий конфигурации, CI коммитит тег, откат через git revert, Sealed Secrets.

Задание 1 — Argo CD на стенде

Подними кластер (minikube, kind или k3s из 5.2 Kubernetes в работе) и установи Argo CD. Зайди в интерфейс через port-forward, смени пароль администратора.
Проверка: argocd app list выполняется без ошибок, интерфейс открывается.

Задание 2 — первое приложение

Создай репозиторий конфигурации с чартом из 5.3 Helm и Kustomize и Application с автосинхронизацией, prune и selfHeal.
Проверка: приложение в статусе Synced + Healthy. Поменяй replicaCount коммитом — через несколько минут (или сразу по кнопке Refresh) число подов изменилось.

Задание 3 — дрейф и самоисправление

Выполни kubectl scale deploy <имя> --replicas=5 и kubectl delete svc <имя>.
Проверка: Argo CD возвращает число реплик и пересоздаёт Service. Затем удали Deployment из git — с prune: true он исчезает из кластера.

Задание 4 — CI коммитит тег

Настрой пайплайн репозитория приложения: сборка образа с тегом $CI_COMMIT_SHORT_SHA, пуш в реестр и коммит нового тега в values-staging.yaml репозитория конфигурации.
Проверка: пуш в main приложения → через несколько минут в кластере работает новая версия, а в истории репозитория конфигурации есть коммит от CI. У пайплайна нет kubeconfig.

Задание 5 — откат и секрет

Выкати заведомо сломанную версию (образ с несуществующим тегом), увидь Degraded, откати через git revert. Затем добавь пароль базы через Sealed Secrets.
Проверка: после revert приложение снова Healthy; в репозитории лежит только SealedSecret, а kubectl get secret в кластере показывает расшифрованный Secret.
