О чём урок

ℹ️Зачем это нужно

Пока за базой работает один человек, все предыдущие уроки работают безупречно. Но в реальности к одной базе одновременно обращаются сотни запросов — и тут начинаются гонки: два запроса читают и меняют одни и те же строки почти одновременно. Транзакции и уровни изоляции — это то, что не даёт данным испортиться в такой ситуации.

📘Словарик на будущее
  • Транзакция — блок операций, который выполняется как единое целое: либо применяются все изменения (COMMIT), либо ни одно (ROLLBACK).
  • ACID — четыре гарантии транзакций: атомарность, согласованность, изолированность, устойчивость.
  • Уровень изоляции — правило, определяющее, что одна транзакция может «увидеть» из изменений другой параллельной транзакции, ещё не зафиксированной или уже зафиксированной.
  • Deadlock (взаимоблокировка) — ситуация, когда две транзакции блокируют друг друга навсегда, каждая ждёт ресурс, занятый другой.
// шаг 2/21 · теория · ~1 мин

Транзакция и COMMIT

Аналогия: транзакция — как черновик письма: пока не нажал «отправить» (COMMIT), получатель ничего не видит, даже если ты уже написал весь текст. Нажал «отмена» (ROLLBACK) — письмо вообще не отправится, будто его не писали.

-- Session #1: снижаем цену видеокарты
BEGIN;
UPDATE product SET price = 49990 WHERE id = 3;
SELECT price FROM product WHERE id = 3;   -- видит 49990, изменения ещё не зафиксированы

-- Session #2 (параллельно, до COMMIT в Session #1)
SELECT price FROM product WHERE id = 3;   -- всё ещё видит старую цену 54990

-- Session #1
COMMIT;

-- Session #2 (после COMMIT)
SELECT price FROM product WHERE id = 3;   -- теперь видит 49990

Изменения внутри транзакции видны самой этой транзакции сразу, но другим параллельным сессиям — только после COMMIT. Это базовое поведение, работающее одинаково на всех уровнях изоляции.

// шаг 3/21 · теория · ~1 мин

ACID — четыре гарантии транзакций

Аналогия: ACID — как правила безопасного перевода денег в банке: либо перевод проходит целиком (деньги списаны у одного и зачислены другому), либо не проходит вообще — никогда не бывает «списали, но не зачислили».

  • Atomicity (атомарность) — транзакция выполняется целиком или не выполняется вовсе.
  • Consistency (согласованность) — транзакция переводит базу из одного корректного состояния в другое, не нарушая ограничений (CHECK, FOREIGN KEY и т.д.).
  • Isolation (изолированность) — параллельные транзакции не мешают друг другу сильнее, чем позволяет выбранный уровень изоляции.
  • Durability (устойчивость) — после COMMIT изменения сохранятся даже при сбое питания сразу после этого.
// шаг 4/21 · теория · ~1 мин

Уровни изоляции: зачем их несколько

Аналогия: уровни изоляции — как разная степень приватности переговорной комнаты: от «дверь нараспашку, всем всё слышно» до «полная звукоизоляция», и каждый вариант — компромисс между скоростью и защитой от чужого влияния.

PostgreSQL поддерживает три уровня (стандарт ANSI SQL описывает четыре, но READ UNCOMMITTED в PostgreSQL ведёт себя как READ COMMITTED):

Уровень Защищает от Non-Repeatable Read Защищает от Phantom Read
READ COMMITTED (по умолчанию) Нет Нет
REPEATABLE READ Да В основном да (за счёт MVCC)
SERIALIZABLE Да Да

Более строгий уровень изоляции даёт больше гарантий, но может привести к ошибке сериализации (транзакцию приходится повторить), если конфликт всё же произошёл.

// шаг 5/21 · теория · ~2 мин

Аномалия потери обновления (Lost Update)

Аналогия: два человека одновременно редактируют одну и ту же ячейку в старой офлайн-таблице без блокировок: оба читают исходное значение, оба вносят свою правку, и тот, кто сохранил вторым, полностью затирает правку первого — как будто её никогда и не было.

В магазине это выглядит так: на складе 5 видеокарт, два покупателя оформляют заказ одновременно. Код приложения читает остаток, вычитает единицу и записывает результат.

-- Session #1 (READ COMMITTED)            -- Session #2 (READ COMMITTED)
BEGIN;                                     BEGIN;
SELECT stock FROM product WHERE id = 3;    SELECT stock FROM product WHERE id = 3;
-- видит 5                                 -- видит 5
                                           UPDATE product SET stock = 4 WHERE id = 3;
                                           COMMIT;
UPDATE product SET stock = 4 WHERE id = 3;
COMMIT;
-- Итог: stock = 4, хотя продано две видеокарты

Обе транзакции читают одно и то же исходное значение, и более поздний COMMIT полностью перезаписывает результат более ранней транзакции — правка Session #2 теряется, хотя формально обе транзакции завершились успешно. На складе по данным базы 4 видеокарты, а на полке 3: через неделю кто-то оплатит товар, которого нет.

// шаг 6/21 · теория · ~1 мин

Может ли REPEATABLE READ решить Lost Update?

Аналогия: более строгий уровень не «магически чинит» конфликт — вместо тихой потери данных он честно говорит «извини, попробуй ещё раз».

-- Session #1 (REPEATABLE READ)           -- Session #2 (REPEATABLE READ)
BEGIN;                                     BEGIN;
SELECT stock FROM product WHERE id = 3;    SELECT stock FROM product WHERE id = 3;
                                           UPDATE product SET stock = 4 WHERE id = 3;
                                           COMMIT;
UPDATE product SET stock = 4 WHERE id = 3;
-- ERROR: could not serialize access due to concurrent update

На REPEATABLE READ PostgreSQL обнаруживает конфликт и завершает вторую транзакцию с ошибкой сериализации вместо молчаливой потери данных — приложение обязано перезапустить транзакцию заново.

// шаг 7/21 · теория · ~1 мин

Аномалия неповторяющегося чтения (Non-Repeatable Read)

Аналогия: дважды посмотреть на одно и то же табло за время одного разговора — и увидеть разные цифры, потому что кто-то другой успел его переписать между двумя твоими взглядами.

-- Session #1 (READ COMMITTED)            -- Session #2
BEGIN;
SELECT price FROM product WHERE id = 1;    -- видит 7490
                                           UPDATE product SET price = 6990 WHERE id = 1;
                                           COMMIT;
SELECT price FROM product WHERE id = 1;    -- видит уже 6990 — в той же транзакции!
COMMIT;

На READ COMMITTED каждый отдельный SELECT видит последние зафиксированные данные — даже внутри одной незавершённой транзакции повторный запрос может вернуть другое значение. Для отчёта это опасно: первая строка отчёта посчитана по одной цене, последняя — по другой.

// шаг 8/21 · теория · ~1 мин

Как SERIALIZABLE защищает от Non-Repeatable Read

Аналогия: сфотографировать табло в начале разговора — и весь разговор ссылаться только на эту фотографию, что бы ни происходило с настоящим табло за окном.

-- Session #1 (SERIALIZABLE)              -- Session #2
BEGIN;
SELECT price FROM product WHERE id = 1;    -- видит 7490
                                           UPDATE product SET price = 6490 WHERE id = 1;
                                           COMMIT;
SELECT price FROM product WHERE id = 1;    -- всё ещё видит 7490 — снимок на начало транзакции
COMMIT;

На REPEATABLE READ и SERIALIZABLE транзакция видит согласованный «снимок» данных на момент своего начала — чужие COMMIT, случившиеся после этого момента, для неё как будто не существуют, пока она не завершится.

// шаг 9/21 · теория · ~1 мин

Аномалия фантомного чтения (Phantom Read)

Аналогия: пересчитать товары на полке дважды за одну инвентаризацию и получить разное число — потому что кто-то зашёл в комнату между двумя подсчётами, хотя ни один из уже посчитанных людей не менялся.

-- Session #1 (READ COMMITTED)            -- Session #2
BEGIN;
SELECT COUNT(*) FROM product
WHERE store_id = 1;                        -- 3 товара
                                           INSERT INTO product
                                           VALUES (30, 1, 'SSD 2 ТБ', 12990, 10);
                                           COMMIT;
SELECT COUNT(*) FROM product
WHERE store_id = 1;                        -- уже 4 — появился «фантом»
COMMIT;

В отличие от Non-Repeatable Read (изменилось существующее значение), здесь появилась новая строка, которой не было при первом чтении — отсюда название «фантом».

// шаг 10/21 · теория · ~1 мин

Phantom Read на REPEATABLE READ

Аналогия: в PostgreSQL «снимок» данных на REPEATABLE READ фиксируется настолько строго, что новые строки, появившиеся после начала транзакции, для неё как будто ещё не существуют — в отличие от классического определения из стандарта SQL, где формально REPEATABLE READ не обязан защищать от фантомов.

-- Session #1 (REPEATABLE READ)           -- Session #2
BEGIN;
SELECT COUNT(*) FROM product
WHERE store_id = 1;                        -- 3 товара
                                           INSERT INTO product
                                           VALUES (31, 1, 'Блок питания', 6490, 7);
                                           COMMIT;
SELECT COUNT(*) FROM product
WHERE store_id = 1;                        -- всё ещё 3
COMMIT;

Это особенность конкретной реализации PostgreSQL (через MVCC-снимок), а не универсальное правило ANSI SQL — в других СУБД REPEATABLE READ может вести себя иначе.

// шаг 11/21 · теория · ~2 мин

Deadlock — взаимная блокировка

Аналогия: два человека в узком коридоре одновременно уступают друг другу дорогу, каждый шагает в сторону — и оба шагают в одну и ту же сторону одновременно, снова блокируя проход; в случае с базой данных это происходит с блокировками строк, а не с людьми, и без внешнего вмешательства длилось бы вечно.

-- Session #1: корзина «SSD + память»     -- Session #2: корзина «память + SSD»
BEGIN;                                     BEGIN;
UPDATE product SET stock = stock - 1       UPDATE product SET stock = stock - 1
WHERE id = 1;                              WHERE id = 2;
                                           UPDATE product SET stock = stock - 1
                                           WHERE id = 1;  -- ждёт Session #1
UPDATE product SET stock = stock - 1
WHERE id = 2;      -- ждёт Session #2 → DEADLOCK

Каждая сессия удерживает блокировку одной строки и ждёт освобождения другой строки, заблокированной противоположной сессией — круговое ожидание. PostgreSQL периодически проверяет граф ожиданий и сам прерывает одну из транзакций с ошибкой deadlock detected, чтобы разорвать цикл — это не баг, а встроенный защитный механизм.

💡Как не получать deadlock

Правило то же, что для блокировок в Python (2.3 Параллельность, §9): всегда захватывать ресурсы в одном и том же порядке. Если бы обе сессии списывали товары из корзины в порядке возрастания id, взаимной блокировки не случилось бы вовсе — вторая просто подождала бы первую. В коде это одна строка: отсортировать товары корзины перед списанием.

Второй приём — держать транзакции короткими: чем меньше времени удерживается блокировка, тем меньше шансов встретиться. И третий — приложение должно уметь повторить транзакцию, прерванную из-за deadlock, потому что полностью исключить их нельзя (см. §15).

// шаг 12/21 · теория · ~2 мин

SELECT FOR UPDATE — правильный способ избежать Lost Update

Аналогия: взять документ со стола и сразу положить на него табличку «занято», а не надеяться, что за время работы никто другой его не тронет.

В §4–5 показано, что потеря обновления либо происходит тихо (READ COMMITTED), либо превращается в ошибку (REPEATABLE READ). Есть третий путь, который используют чаще всего: заблокировать строку сразу при чтении.

BEGIN;
SELECT stock FROM product WHERE id = 3 FOR UPDATE;   -- строка заблокирована
-- вторая сессия на этой же строке будет ждать здесь
-- приложение проверяет: stock > 0? если нет — «товар закончился»
UPDATE product SET stock = stock - 1 WHERE id = 3;
COMMIT;                                              -- блокировка снята

FOR UPDATE говорит: «я собираюсь менять эту строку, никого сюда не пускать до конца транзакции». Вторая сессия на том же SELECT ... FOR UPDATE не получит старое значение — она просто подождёт, а после снятия блокировки прочитает уже новое.

Варианты, которые стоит знать:

SELECT ... FOR UPDATE NOWAIT;         -- не ждать, сразу вернуть ошибку
SELECT ... FOR UPDATE SKIP LOCKED;     -- пропустить занятые строки и взять свободные
SELECT ... FOR SHARE;                   -- запретить изменение, но разрешить такое же чтение

SKIP LOCKED — основа простых очередей задач на базе: несколько обработчиков берут по задаче, не мешая друг другу и не дожидаясь чужих.

💡Что выбрать

Есть и четвёртый способ — вообще не читать значение заранее: UPDATE product SET stock = stock - 1 WHERE id = 3 AND stock > 0 атомарен сам по себе, потому что база вычисляет новое значение в момент изменения. Если обновилась ноль строк — товар закончился. Если логика позволяет обойтись так — это надёжнее и дешевле всего. FOR UPDATE нужен, когда между чтением и записью есть решение, которое надо принять в коде.

// шаг 13/21 · теория · ~2 мин

MVCC и VACUUM: почему база растёт

Аналогия: редактор, который при каждой правке не меняет страницу, а подшивает новую версию и зачёркивает старую. Папка толстеет, даже если текст остался прежним.

То, что делает возможными «снимки» из §7, имеет обратную сторону. PostgreSQL при UPDATE не меняет строку на месте — он создаёт новую версию, а старую помечает мёртвой. При DELETE строка тоже не исчезает, а просто помечается.

Старые версии нужны транзакциям, которые начались раньше и должны видеть прежнее состояние. Это и есть MVCC — многоверсионное управление конкурентным доступом, механизм, благодаря которому читающие не блокируют пишущих и наоборот.

Убирает мусор VACUUM. Обычно этим занимается фоновый autovacuum, и вмешиваться не приходится. Полезные команды:

VACUUM ANALYZE orders;        -- убрать мусор и обновить статистику
VACUUM FULL orders;            -- перестроить таблицу целиком, вернув место системе
SELECT relname, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC;   -- где больше всего мусора
🛑VACUUM FULL блокирует таблицу целиком

Обычный VACUUM работает параллельно с нагрузкой и освобождает место внутри файлов таблицы для повторного использования. VACUUM FULL физически перестраивает таблицу и возвращает место операционной системе, но берёт исключительную блокировку: на время работы таблица недоступна ни на чтение, ни на запись. На большой таблице это часы простоя. В эксплуатации вместо него используют pg_repack, который делает то же самое без длительной блокировки.

// шаг 14/21 · теория · ~2 мин

Длинная транзакция — тихий убийца базы

Аналогия: один человек не сдал ключ от общего архива и ушёл в отпуск. Никто не может разобрать старые документы, и хранилище переполняется — хотя сам он ничего плохого не делает.

Самая недооценённая проблема из всего урока, и одна из самых частых реальных аварий.

VACUUM может убрать только те мёртвые версии, которые не нужны ни одной активной транзакции. Если где-то открыта транзакция — пусть даже она ничего не делает, — её снимок удерживает все версии, появившиеся после её начала. По всей базе, а не только по её таблицам.

Что происходит дальше: таблицы распухают мёртвыми версиями, запросы начинают читать больше данных и замедляются, диск заканчивается. Причём виновная транзакция может вообще не выполнять запросов — она просто открыта.

-- найти долгие транзакции
SELECT pid, state, now() - xact_start AS transaction_age, query
FROM pg_stat_activity
WHERE state IN ('idle in transaction', 'active')
  AND now() - xact_start > interval '5 minutes'
ORDER BY xact_start;

Состояние idle in transaction — главный подозреваемый: соединение открыло транзакцию и ничего не делает. Обычно это ошибка в приложении, где забыли COMMIT или не закрыли соединение при исключении.

Защита на стороне базы — таймауты, которые стоит выставлять всегда:

ALTER SYSTEM SET idle_in_transaction_session_timeout = '5min';
ALTER SYSTEM SET statement_timeout = '30s';

Первый обрывает соединения, забывшие закрыть транзакцию. Второй ограничивает время одного запроса, не давая случайному тяжёлому SELECT работать часами.

Отсюда же правило проектирования: не держать транзакцию открытой во время обращения к внешним системам. Схема «начали транзакцию → пошли в стороннее API → ждём ответа 30 секунд → закоммитили» превращает чужую медлительность в проблему собственной базы.

// шаг 15/21 · теория · ~2 мин

Диагностика: кто кого блокирует

Аналогия: пробка на дороге — сначала находят, где именно она начинается, и только потом разбираются почему.

Три запроса, которые стоит держать наготове.

Что выполняется прямо сейчас:

SELECT pid, state, wait_event_type, now() - query_start AS runtime, query
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY runtime DESC;

Кто кого блокирует — самый полезный из трёх:

SELECT pid, pg_blocking_pids(pid) AS blocked_by, query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

Функция pg_blocking_pids сразу выдаёт список процессов, которых ждёт данный. Раньше для этого писали громоздкие соединения с pg_locks; сейчас достаточно одной строки.

Убрать виновника:

SELECT pg_cancel_backend(12345);      -- отменить текущий запрос, соединение остаётся
SELECT pg_terminate_backend(12345);    -- оборвать соединение целиком, транзакция откатится

Сначала пробуют cancel — он мягче. terminate применяют, когда отмена не сработала или когда соединение висит в idle in transaction: там отменять нечего, запрос уже не выполняется.

Дополнение к 2.8 Индексы: именно этими запросами диагностируют ситуацию, когда кто-то запустил CREATE INDEX без CONCURRENTLY и все записи в таблицу встали.

// шаг 16/21 · теория · ~2 мин

Повторы при ошибке сериализации

Аналогия: если система честно говорит «извини, попробуй ещё раз», кто-то должен эту попытку сделать. Пользователь для этой роли не годится.

На уровнях REPEATABLE READ и SERIALIZABLE конфликт заканчивается ошибкой (§5), и это штатное поведение, а не сбой. Но оно означает, что приложение обязано уметь повторить транзакцию целиком:

from psycopg import errors

def with_retry(operation, attempts=3):
    for attempt in range(attempts):
        try:
            return operation()
        except errors.SerializationFailure:
            if attempt == attempts - 1:
                raise
            time.sleep(0.1 * (2 ** attempt) + random.uniform(0, 0.1))

Это ровно та же механика повторов с экспоненциальной задержкой и джиттером, что разбиралась в 2.3 Параллельность, §11. Отличие в том, что повторять надо всю транзакцию с начала, а не последний запрос: снимок данных был отброшен вместе с ней.

То же относится и к deadlock detected из §10 — прерванную транзакцию надо повторить.

⚠️Что нельзя делать внутри повторяемой транзакции

Если транзакция может быть перезапущена, внутри неё не должно быть необратимых побочных действий: отправки письма, списания денег во внешней системе, записи в файл. Иначе при повторе они выполнятся дважды. Такие действия выносят за пределы транзакции или делают идемпотентными — понятие, которое уже встречалось в 1.3 Bash, §14.

// шаг 17/21 · итоги · ~1 мин

Если запомнить только главное

  • Изменения видны только внутри своей транзакции, пока не случился COMMIT — другие сессии ждут его.
  • ACID — Atomicity, Consistency, Isolation, Durability: четыре гарантии, которые обеспечивает СУБД.
  • Более строгий уровень изоляции не устраняет конфликты полностью — он превращает тихую потерю данных в явную ошибку сериализации.
  • Lost Update — правка одной транзакции незаметно затирается другой; Non-Repeatable Read — одно и то же значение меняется между двумя чтениями; Phantom Read — появляется новая строка между двумя чтениями.
  • REPEATABLE READ и SERIALIZABLE в PostgreSQL используют «снимок» данных на момент начала транзакции — чужие изменения после этого момента не видны до конца транзакции.
  • Deadlock — круговое ожидание блокировок; PostgreSQL сам обнаруживает его и прерывает одну из транзакций. Профилактика — единый порядок захвата и короткие транзакции.
  • SELECT ... FOR UPDATE блокирует строку при чтении — самый практичный способ избежать потери обновления. SKIP LOCKED — основа очередей задач.
  • MVCC: UPDATE создаёт новую версию строки, старую помечает мёртвой. Убирает мусор VACUUM; VACUUM FULL блокирует таблицу целиком — в проде вместо него pg_repack.
  • Одна забытая открытая транзакция останавливает VACUUM по всей базе — таблицы распухают, запросы замедляются, диск кончается. Ищи состояние idle in transaction.
  • Всегда выставляй statement_timeout и idle_in_transaction_session_timeout. Не держи транзакцию открытой во время обращения к внешним системам.
  • Диагностика: pg_stat_activity — что выполняется, pg_blocking_pids() — кто кого блокирует, pg_cancel_backend / pg_terminate_backend — убрать.
  • Ошибка сериализации и deadlock — штатное поведение: приложение обязано повторить всю транзакцию с экспоненциальной задержкой. Внутри повторяемой транзакции не должно быть необратимых побочных действий.
