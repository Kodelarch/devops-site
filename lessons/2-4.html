О чём урок

ℹ️Зачем это нужно

Скрипт на сто строк можно писать как угодно. Утилита, которую поддерживают несколько человек и которая живёт годами, без архитектуры превращается в клубок: поправил вывод — сломалась логика, заменил библиотеку HTTP — пришлось переписывать половину. Этот урок — про разделение кода на независимые слои и про тесты, которые это разделение окупают.

Сквозной пример — небольшая утилита uptime-checker: она по расписанию проверяет сайты и порты, решает, когда пора поднимать тревогу, хранит историю и показывает сводку в терминале. Это ровно тот же принцип, по которому строятся серьёзные бэкенды (2.5 Бэкенд-сервис), — просто на примере, который целиком помещается в голове.

📘Словарик на будущее
  • Слоистая архитектура — код разбит на независимые «этажи» (интерфейс, бизнес-логика, хранение и внешние системы), где каждый этаж не обязан знать детали устройства другого.
  • Домен (domain) — сама суть программы: её понятия и правила. Для uptime-checker это «проверка», «результат», «когда поднимать тревогу».
  • Инверсия зависимостей — правило «бизнес-логика не должна зависеть от конкретной технологии»: домен ничего не знает про HTTP-библиотеку, Telegram или терминал, только про свои понятия.
  • Тестовый двойник (fake, mock) — подставной объект вместо настоящей зависимости, чтобы тест не ходил в сеть и не зависел от внешнего мира.

Три слоя вместо одной кучи кода


Аналогия: ресторан работает потому, что зал (интерфейс), кухня (домен, бизнес-логика) и склад с поставщиками (хранение и внешние системы) — разные помещения с разными обязанностями. Официант не готовит еду, повар не считает выручку и не ездит за продуктами.

Для uptime-checker слои выглядят так:

  • Interface — то, с чем работает человек: команды в терминале, таблица со статусами, цветной вывод.
  • Domain — понятия и правила: что такое проверка, чем «сайт недоступен» отличается от «сайт тормозит», после скольких неудач слать алерт.
  • Infrastructure — всё, что касается внешнего мира: HTTP-запросы, TCP-соединения, файл с историей, отправка сообщений в Telegram.

Главное правило — направление зависимостей: интерфейс и инфраструктура знают про домен, а домен не знает ни про кого. В файлах домена нет ни import requests, ни print.

💡Почему это важно на реальной работе

Точно так же устроены веб-сервисы: слой, который считает бизнес-правила (например, «можно ли списать деньги со счёта»), не должен знать, вызвали его через HTTP, консоль или очередь сообщений. Поменять интерфейс или библиотеку — не значит переписывать логику.

Модель предметной области

Аналогия: прежде чем строить дом, архитектор договаривается о словах: что такое «комната», «этаж», «несущая стена». Код начинается так же — с понятий.

Понятия домена удобно описывать dataclass'ами — классами, которые в основном хранят данные:

# domain/models.py
from dataclasses import dataclass, field
from datetime import datetime
from enum import Enum

class State(Enum):
    UP = "работает"
    SLOW = "тормозит"
    DOWN = "недоступен"

@dataclass(frozen=True)
class Target:
    name: str
    address: str
    slow_ms: int = 1000           # дольше — считаем «тормозит»

@dataclass
class Result:
    target: Target
    ok: bool
    latency_ms: float
    checked_at: datetime = field(default_factory=datetime.now)
    error: str | None = None

@dataclass сам пишет за тебя __init__, понятное текстовое представление и сравнение объектов — не нужно руками перечислять каждое поле в конструкторе, как в 2.1 Python, §12. frozen=True делает объект неизменяемым: цель проверки после создания поменять нельзя, а значит, её можно класть в множество и использовать ключом словаря. field(default_factory=datetime.now) вызывает функцию при создании каждого объекта — если написать просто = datetime.now(), время вычислилось бы один раз при загрузке модуля, и у всех результатов оно было бы одинаковым. State — перечисление из 2.3 Параллельность, §5.

Разные типы через один интерфейс

Аналогия: у врача, медсестры и лаборанта одна должностная обязанность — «проверить пациента», но делает её каждый по-своему. Главврачу не нужно знать подробностей, ему достаточно получить заключение.

Сайт проверяют HTTP-запросом, базу — попыткой открыть TCP-соединение на её порт, домен — DNS-запросом. Способы разные, а вызывающему коду нужно одно: «проверь и верни Result».

# domain/checks.py
from abc import ABC, abstractmethod

class Check(ABC):
    def __init__(self, target: Target):
        self.target = target

    @abstractmethod
    def run(self) -> Result:
        """У каждого типа проверки своя реализация."""

class HttpCheck(Check):
    def __init__(self, target, client):
        super().__init__(target)
        self.client = client                  # как ходить в сеть — передают снаружи (§7)

    def run(self) -> Result:
        status, latency = self.client.get(self.target.address)
        return Result(self.target, ok=200 <= status < 400, latency_ms=latency)

class TcpCheck(Check):
    def __init__(self, target, connector):
        super().__init__(target)
        self.connector = connector

    def run(self) -> Result:
        ok, latency = self.connector.connect(self.target.address)
        return Result(self.target, ok=ok, latency_ms=latency)

class HttpCheck(Check): — наследование: HttpCheck получает всё, что описано в Check, и дописывает своё. ABC и @abstractmethod — защита: создать объект класса, который забыл реализовать run, Python просто не даст, и ошибка вылезет сразу, а не через неделю в продакшене. super().__init__(target) вызывает конструктор родителя, чтобы не повторять его код.

Это классический полиморфизм: код, который запускает проверки, вызывает один и тот же метод run() — а что именно произойдёт, зависит от конкретного класса. Добавить проверку срока TLS-сертификата — значит написать ещё один класс, не трогая ничего остального.

Правила живут в домене

Аналогия: дежурный не звонит начальнику при первом же странном звуке. У него инструкция: «если сигнал повторился три раза подряд — звонить; если уже позвонил — не звонить каждые пять минут, а сообщить, когда всё наладится».

Самая ценная часть uptime-checker — не HTTP-запросы, а правила, когда тревожить человека. Это и есть бизнес-логика, и она живёт в домене:

# domain/alerting.py
class AlertPolicy:
    def __init__(self, fail_threshold: int = 3):
        self.fail_threshold = fail_threshold
        self.failures: dict[str, int] = {}
        self.alerting: set[str] = set()

    def decide(self, result: Result) -> str | None:
        """Вернуть 'alert', 'resolved' или None — ничего не делать."""
        name = result.target.name
        if result.ok:
            self.failures[name] = 0
            if name in self.alerting:
                self.alerting.discard(name)
                return "resolved"
            return None

        self.failures[name] = self.failures.get(name, 0) + 1
        if self.failures[name] >= self.fail_threshold and name not in self.alerting:
            self.alerting.add(name)
            return "alert"
        return None

Это та же идея, что for: 5m в правилах Prometheus и send_resolved в Alertmanager (4.5 Наблюдаемость, §8–9): одна неудача — ещё не авария, а одна авария — одно сообщение, а не сообщение каждую минуту. Класс ничего не знает ни про сеть, ни про Telegram — он получает результат и возвращает решение.

Главный цикл

Аналогия: часовой на посту: раз в N минут обойти все точки, записать, что увидел, и действовать по инструкции.

# app/runner.py
import time

def run_forever(checks, policy, notifier, storage, interval_s=30):
    while True:
        for check in checks:
            result = check.run()
            storage.append(result)
            decision = policy.decide(result)
            if decision:
                notifier.send(decision, result)
        time.sleep(interval_s)

Это слой приложения: он ничего не решает сам, а соединяет части — запускает проверки, сохраняет результат, спрашивает домен, нужно ли тревожить, и передаёт решение тому, кто умеет отправлять сообщения. Проверки здесь идут по очереди; когда целей станет сотни, их запускают параллельно через пул потоков (2.3 Параллельность, §8), и меняется только этот файл.

В реальной эксплуатации такой процесс оформляют systemd-сервисом (1.1 Linux, §7) или контейнером — тогда его перезапустят при падении, а вывод попадёт в журнал.

Сохранение состояния

Аналогия: бортовой журнал: записать текущее состояние так, чтобы после перезагрузки можно было продолжить с того же места, а через год — понять, что было.

# infra/storage.py
import json
from pathlib import Path

FORMAT_VERSION = 2

def save_state(policy: AlertPolicy, path: Path):
    data = {"version": FORMAT_VERSION,
            "failures": policy.failures,
            "alerting": sorted(policy.alerting)}
    tmp = path.with_suffix(".tmp")
    tmp.write_text(json.dumps(data, ensure_ascii=False, indent=2))
    tmp.replace(path)                      # атомарная подмена файла

def load_state(path: Path) -> AlertPolicy:
    policy = AlertPolicy()
    if not path.exists():
        return policy
    data = json.loads(path.read_text())
    if data.get("version") != FORMAT_VERSION:
        raise ValueError(f"неподдерживаемая версия файла состояния: {data.get('version')}")
    policy.failures = data["failures"]
    policy.alerting = set(data["alerting"])
    return policy

Две привычки, которые отличают рабочий код от учебного. Версия формата в файле: когда через полгода структура поменяется, программа сможет понять, что перед ней старый файл, и либо преобразовать его, либо честно отказаться — а не упасть с непонятным KeyError. Запись через временный файл: если процесс убьют посреди записи, на диске останется недописанный .tmp, а основной файл не пострадает — replace подменяет файл одной операцией. Состояние нужно, чтобы после перезапуска утилита не прислала заново все алерты, которые уже отправляла.

Зависимости передают снаружи

Аналогия: повару не нужно знать, на какой машине и с какой базы приехали продукты. Ему их приносят. Сменили поставщика — кухня этого даже не заметила.

В §3 HttpCheck не создаёт HTTP-клиент сам, а получает его в конструкторе. Это и есть внедрение зависимостей (dependency injection) — подробнее о нём в 2.5 Бэкенд-сервис, §5. Настоящий клиент живёт в инфраструктуре:

# infra/http.py
import time
import requests

class RequestsClient:
    def __init__(self, timeout_s: float = 5):
        self.timeout_s = timeout_s

    def get(self, url: str) -> tuple[int, float]:
        start = time.perf_counter()
        try:
            status = requests.get(url, timeout=self.timeout_s).status_code
        except requests.RequestException:
            status = 0
        return status, (time.perf_counter() - start) * 1000

Собирается всё в одном месте — точке входа:

# main.py
client = RequestsClient(timeout_s=5)
checks = [HttpCheck(Target("shop", "https://shop.example.com/healthz"), client)]
run_forever(checks, load_state(STATE), TelegramNotifier(TOKEN, CHAT), JsonlStorage(LOG))

Захочешь перейти с requests на httpx — поменяется один файл в infra/, а домен, правила алертов и тесты останутся как были.

// шаг 9/18 · теория · ~1 мин

Зачем это всё на практике: тесты без сети

Аналогия: рецепт супа проверяют в кастрюле на кухне, а не накрывая каждый раз стол на десять персон. Отделив правила от сети и экрана, их можно проверить за миллисекунды.

Благодаря §7 в тесте вместо настоящего клиента можно подставить тестовый двойник, который ведёт себя ровно так, как нужно для проверки:

class FakeClient:
    def __init__(self, status=200, latency=50):
        self.status, self.latency = status, latency

    def get(self, url):
        return self.status, self.latency

def test_http_check_fails_on_500():
    check = HttpCheck(Target("shop", "https://shop"), FakeClient(status=500))
    assert check.run().ok is False

def test_alert_only_after_three_failures():
    policy = AlertPolicy(fail_threshold=3)
    bad = Result(Target("shop", "x"), ok=False, latency_ms=0)
    assert [policy.decide(bad) for _ in range(4)] == [None, None, "alert", None]

Эти тесты не ходят в интернет, не зависят от того, работает ли сайт прямо сейчас, и выполняются за миллисекунды. Второй тест к тому же проверяет самое важное: алерт приходит на третьей неудаче и не повторяется на четвёртой. Именно возможность писать такие тесты — главная практическая выгода слоистой архитектуры, а не «красивый код сам по себе».

Структура проекта и импорты

Аналогия: пока файлов три, их можно держать в одной папке. Когда их тридцать и над ними работают четверо, нужна планировка — иначе каждый кладёт своё куда попало.

uptime-checker/
├── pyproject.toml          # описание проекта и зависимостей
├── README.md
├── .gitignore
├── src/
│   └── uptime_checker/
│       ├── __init__.py
│       ├── domain/         # понятия и правила — ничего не импортирует извне
│       │   ├── models.py
│       │   ├── checks.py
│       │   └── alerting.py
│       ├── app/            # главный цикл, сценарии
│       │   └── runner.py
│       ├── infra/          # HTTP, TCP, файлы, Telegram
│       │   ├── http.py
│       │   ├── storage.py
│       │   └── telegram.py
│       └── cli.py          # точка входа и вывод в терминал
└── tests/
    ├── test_checks.py
    └── test_alerting.py

Файл __init__.py превращает папку в пакет — набор модулей, который можно импортировать как единое целое (from uptime_checker.domain import alerting). В современном Python он может быть пустым, но его наличие делает структуру явной.

Раскладка с папкой src/ (так называемый src-layout) поначалу кажется лишней вложенностью, но решает конкретную проблему: без неё тесты импортируют код из рабочей папки, а не из установленного пакета — и ошибки упаковки обнаруживаются только у пользователя. С src/ тесты вынуждены работать с тем же кодом, который получат все остальные.

⚠️Циклический импорт

Модуль A импортирует B, B импортирует A — Python падает с ImportError, и сообщение обычно указывает не туда, где настоящая причина. Это почти всегда признак того, что границы слоёв нарушены: domain полез в infra. Лечится не хитрым импортом внутри функции, а исправлением зависимости — стрелка должна смотреть внутрь, к домену.

// шаг 11/18 · теория · ~3 мин

Тесты по-настоящему: pytest


Аналогия: тесты — не доказательство, что код идеален, а сигнализация: она не мешает войти, но громко сообщает, если что-то сдвинулось.

Голые функции с assert из §8 работают, но запускать десятки таких функций руками невозможно. Стандарт индустрии — pytest:

# tests/test_alerting.py
import pytest
from uptime_checker.domain.models import Target, Result
from uptime_checker.domain.alerting import AlertPolicy

@pytest.fixture
def target():
    return Target("shop", "https://shop.example.com")

@pytest.fixture
def policy():
    """Свежая политика для каждого теста."""
    return AlertPolicy(fail_threshold=3)

def make(target, ok):
    return Result(target, ok=ok, latency_ms=10)

def test_recovery_sends_resolved(policy, target):
    for _ in range(3):
        policy.decide(make(target, ok=False))
    assert policy.decide(make(target, ok=True)) == "resolved"

@pytest.mark.parametrize("threshold,failures,expected", [
    (1, 1, "alert"),
    (3, 2, None),
    (3, 3, "alert"),
])
def test_threshold_table(target, threshold, failures, expected):
    policy = AlertPolicy(fail_threshold=threshold)
    decisions = [policy.decide(make(target, ok=False)) for _ in range(failures)]
    assert decisions[-1] == expected

Три вещи, ради которых берут pytest. Автоматический поиск: он сам находит все файлы test_*.py и функции test_*, ничего регистрировать не нужно. parametrize прогоняет один тест на списке случаев — вместо трёх почти одинаковых функций получается одна с таблицей. Фикстуры готовят общее состояние и делают это заново для каждого теста, так что тесты не влияют друг на друга.

pytest                      # прогнать всё
pytest -v                    # с именами тестов
pytest tests/test_alerting.py::test_threshold_table   # один конкретный
pytest -x                     # остановиться на первом падении
pytest --cov=uptime_checker   # покрытие кода тестами
💡Про покрытие

Покрытие показывает, какая доля строк была выполнена хотя бы одним тестом. Полезная метрика, но обманчивая: сто процентов покрытия не означают, что код правильный — только что он был выполнен. Тест без единого assert тоже даёт покрытие. Требование «не ниже 80%» встречается в командах как порог в пайплайне, но гнаться за цифрой ради цифры бессмысленно; важнее покрыть тестами то, что ломается.

Детерминированность. Код, который зависит от времени, сети или случайности, плохо тестируется, пока эта зависимость неуправляема. Решение — подставлять её снаружи: фиктивный клиент вместо сети (§8), фиксированное время вместо datetime.now(), random.seed(42) вместо настоящей случайности. Тест, который иногда падает без изменений в коде (flaky test), хуже отсутствующего: ему перестают верить и в итоге отключают.

// шаг 12/18 · теория · ~3 мин

Единый стиль в команде

Аналогия: спорить о том, ставить ли пробел перед скобкой, — как спорить о шрифте служебной записки. Правильный ответ: договориться один раз и поручить машине.

pip install ruff
ruff check .          # найти проблемы
ruff check --fix .     # починить то, что чинится автоматически
ruff format .           # привести к единому стилю

ruff — линтер и форматтер в одном инструменте, к 2026 году фактически вытеснивший связку flake8 + black + isort за счёт скорости. Он ловит неиспользованные импорты, затенённые переменные, подозрительные конструкции — и заодно переформатирует код так, что вопрос стиля просто перестаёт обсуждаться на ревью.

Настройка живёт в pyproject.toml рядом с описанием проекта:

[tool.ruff]
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]   # ошибки, импорты, устаревшие конструкции, баги

Pre-commit запускает эти проверки автоматически перед каждым коммитом, чтобы в репозиторий не попадал неотформатированный код:

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.0
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format

pip install pre-commit && pre-commit install

Это тот же принцип, что shellcheck для bash (1.3 Bash, §13), и та же проверка потом дублируется в пайплайне (3.2 CI-CD): локальный хук даёт быструю обратную связь, а проверка в CI гарантирует, что её нельзя обойти.

Аннотации типов и mypy. Типы из 2.1 Python можно проверять статически:

mypy src/

mypy найдёт места, где функция, объявленная возвращающей int, возвращает None — до запуска кода. В командном проекте это заметно снижает количество глупых ошибок на стыках между чужими модулями.

// шаг 13/18 · теория · ~1 мин

Терминальный интерфейс

Утилите вроде uptime-checker нужен интерфейс, и чаще всего это терминал. Большая часть инструментов, которыми пользуется DevOps, устроена именно так: htop (1.1 Linux), ncdu, k9s для Kubernetes, lazydocker и lazygit — всё это терминальные интерфейсы с одним и тем же циклом «прочитать состояние → отрисовать → дождаться клавиши».

Причина их популярности практическая: на сервере, куда ты попал по SSH, графического интерфейса нет и не будет, а смотреть на постоянно меняющиеся данные через watch неудобно.

Стандартная библиотека Python умеет это через модуль curses, но писать на нём многословно. Из современных библиотек стоит знать rich (цветной вывод, таблицы, прогресс-бары — минимальными усилиями) и textual (полноценные интерфейсы поверх того же движка):

# cli.py
from rich.console import Console
from rich.table import Table

def show(results):
    table = Table(title="uptime-checker")
    for col in ("Цель", "Состояние", "Задержка"):
        table.add_column(col)
    for r in results:
        state = "[green]работает[/]" if r.ok else "[red]недоступен[/]"
        table.add_row(r.target.name, state, f"{r.latency_ms:.0f} мс")
    Console().print(table)

Обрати внимание, где этот код живёт: в интерфейсном слое. Захочешь вместо таблицы в терминале веб-страницу — домен и правила алертов об этом не узнают.

// шаг 14/18 · итоги · ~1 мин

Если запомнить только главное

  • Слоистая архитектура: интерфейс и инфраструктура зависят от домена, домен не знает ни про HTTP, ни про терминал, ни про Telegram.
  • Понятия домена — dataclass'ы и перечисления; разные варианты одного действия — наследники одного абстрактного класса (полиморфизм).
  • Бизнес-правила вроде «алерт после трёх неудач, без повторов» живут в домене и проверяются тестами без сети.
  • Зависимости передают снаружи (dependency injection) — тогда в тесте их можно подменить двойником.
  • Состояние в файле — с версией формата и записью через временный файл.
  • Направление зависимостей важнее числа слоёв: стрелки смотрят внутрь. Циклический импорт — сигнал, что границу нарушили.
  • pytest: автопоиск тестов, parametrize вместо копипасты, фикстуры для общего состояния. Время, сеть и случайность — под контролем теста, иначе тесты станут плавающими.
  • Покрытие показывает, что строка выполнялась, а не что она верна — не гонись за цифрой.
  • ruff заменяет связку линтера и форматтера; pre-commit не пускает неформатированный код в репозиторий, а CI не даёт обойти проверку.
  • Терминальные интерфейсы — норма для инструментов DevOps: htop, k9s, lazydocker. Для своих утилит бери rich или textual.

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

💡В портфолио
  • Структура проекта, тесты без сети и ruff в CI из заданий 1–4 — ровно то, как устроен код M2.
  • Сама утилита uptime-checker из урока тоже годится в портфолио как отдельный маленький проект, если довести её до README и зелёного пайплайна.

Задание 1 — каркас uptime-checker

Создай проект со структурой из §9, модели из §2, проверки HttpCheck и TcpCheck из §3 и правило алертов из §4. Домен не импортирует ничего из infra и cli.
Проверка: grep -rE "import (requests|rich)|print\(" src/uptime_checker/domain/ пуст; утилита проверяет два-три настоящих сайта и печатает таблицу.

Задание 2 — тесты без сети

Напиши не меньше 10 тестов на домен: проверки с двойником клиента, порог алерта, отсутствие повторных алертов, resolved после восстановления, сохранение и загрузку состояния. Используй фикстуры и parametrize.
Проверка: pytest -q зелёный при выключенном интернете; pytest --cov показывает покрытие домена выше 80%.

Задание 3 — состояние переживает перезапуск

Сохраняй состояние политики алертов в JSON с версией формата. Загрузка файла другой версии даёт понятную ошибку, битый JSON не роняет программу молча.
Проверка: останови утилиту во время «аварии» и запусти снова — повторный алерт не приходит, а resolved после восстановления приходит.

Задание 4 — единый стиль

Подключи ruff (линтер и форматтер) и pre-commit. Добавь проверку и тесты в CI.
Проверка: коммит с неотформатированным кодом отклоняется хуком; пайплайн падает на нарушении стиля и на упавшем тесте.
