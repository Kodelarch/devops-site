О чём урок

ℹ️Зачем это нужно

В 1.1 Linux и 1.2 Сети каждый сервер настраивался руками: зашёл по SSH, поставил пакеты, поправил конфиг, перезапустил сервис. Для одной машины это нормально. Для десяти — уже неделя работы и гарантированные расхождения: на одной забыли поставить ufw, на другой опечатались в конфиге nginx. Для ста — невозможно.

Ansible решает ровно эту задачу: желаемое состояние серверов описывается в YAML-файлах, а инструмент приводит машины к этому состоянию сам — сколько бы их ни было и сколько бы раз его ни запускали.

В вакансиях junior DevOps Ansible — один из самых частых пунктов после Linux, Docker и CI/CD. Его любят за низкий порог входа: на управляемых машинах не нужно ничего ставить, достаточно SSH и Python.

📘Словарик на будущее
  • Управляющая машина (control node) — откуда запускают Ansible: ноутбук или раннер CI.
  • Управляемый узел (managed node) — сервер, который настраивают. На нём нужен только SSH и Python.
  • Инвентарь (inventory) — список узлов и их групп.
  • Модуль — готовое действие: поставить пакет, скопировать файл, перезапустить сервис.
  • Задача (task) — один вызов модуля с параметрами.
  • Плейбук (playbook) — YAML-файл со списком задач для групп узлов.
  • Роль — переиспользуемый набор задач, шаблонов и переменных с фиксированной структурой папок.
  • Идемпотентность — повторный запуск не меняет то, что уже в нужном состоянии.

Зачем вообще управление конфигурацией

Аналогия: рецепт вместо устных указаний повару. По рецепту блюдо получается одинаковым у любого повара и в любой день; «ну ты знаешь, как обычно» — каждый раз по-разному.

Ручная настройка порождает три проблемы, которые рано или поздно встречает каждая команда:

Дрейф конфигурации. Серверы, настроенные «одинаково», со временем расходятся: кто-то поправил конфиг на одном, обновил пакет на другом. Через полгода ни один не похож на соседа, и ошибка «на этом сервере работает, на том нет» становится нормой.

Снежинки. Сервер, который настраивали два года вручную, невозможно воспроизвести. Когда он сломается, восстанавливать его будет нечем — никто не помнит всех правок. Это прямое противоречие принципу одноразовых машин из 4.2 Облако, §3.

Нет истории. Ручные правки не проходят ревью и не попадают в git. Через месяц на вопрос «кто и зачем поменял этот параметр» ответа нет.

Управление конфигурацией кодом снимает все три: конфигурация лежит в репозитории, проходит ревью как обычный код (0.1 Git), применяется одинаково на любом количестве машин и в любой момент возвращает их в описанное состояние.

// шаг 3/20 · теория · ~1 мин

Как устроен Ansible: агентов нет

Аналогия: Ansible — не охранник, который круглосуточно сидит в каждом здании, а инспектор, который приезжает по вызову, проверяет всё по списку, исправляет отклонения и уезжает.

Ключевое отличие от старших инструментов (Puppet, Chef, Salt): Ansible безагентный. На управляемых машинах ничего постоянно не работает. При запуске Ansible:

  1. Подключается к узлу по SSH — обычным ключом из 1.1 Linux, §11.
  2. Копирует туда маленькую программу на Python — код модуля.
  3. Запускает её, получает результат в JSON и удаляет за собой.

Отсюда практические следствия:

  • Для старта нужно только то, что и так есть: SSH-доступ и Python на узле. На большинстве дистрибутивов Python стоит из коробки.
  • Ansible работает по модели push: изменения применяются в момент запуска, а не когда узел сам решит проверить конфигурацию. Если на сервере что-то поменяли руками, Ansible узнает об этом только при следующем прогоне.
  • Скорость упирается в SSH. На сотнях узлов прогон заметно небыстрый; это лечится параллельностью (параметр forks) и SSH pipelining.
pip install ansible        # или apt install ansible
ansible --version

Инвентарь: кого настраиваем

Аналогия: список гостей с рассадкой по столам. Сначала решаешь, кто за каким столом, потом — что подавать каждому столу.

Инвентарь — список узлов, разбитый на группы. Простейший формат — INI, но в реальных проектах чаще YAML:

# inventory/hosts.yml
all:
  children:
    web:
      hosts:
        web-1: { ansible_host: 10.0.1.11 }
        web-2: { ansible_host: 10.0.1.12 }
    db:
      hosts:
        db-1:  { ansible_host: 10.0.2.21 }
  vars:
    ansible_user: deploy
    ansible_ssh_private_key_file: ~/.ssh/id_ed25519

Группы можно вкладывать друг в друга: например, группа production содержит web и db. Плейбук потом применяется к группе, а не к перечню адресов.

Проверка связи — первая команда в любом новом проекте:

ansible all -i inventory/hosts.yml -m ping
# web-1 | SUCCESS => { "ping": "pong" }

Здесь ping — не ICMP-пинг из 1.2 Сети, а проверка, что Ansible может зайти по SSH и запустить Python. Если она проходит, всё остальное заработает.

Динамический инвентарь. В облаке машины создаются и удаляются постоянно, и вести их список руками бессмысленно. Плагины инвентаря умеют сами запрашивать у облака список машин по тегам — например, «все машины с тегом role=web». Теги, о которых шла речь в 4.2 Облако, §10, тут начинают работать на автоматизацию.

Ad-hoc команды: разовые действия

Аналогия: один звонок всем сотрудникам сразу: «перезагрузите компьютеры». Удобно для разовой задачи, но регламентом это не становится.

Ad-hoc команда — вызов одного модуля на группе узлов без плейбука:

# сколько места на дисках у всех веб-серверов
ansible web -i inventory/hosts.yml -m command -a "df -h /"

# поставить htop везде (с повышением прав через sudo)
ansible all -i inventory/hosts.yml -m apt -a "name=htop state=present" --become

# перезапустить nginx на веб-серверах
ansible web -i inventory/hosts.yml -m service -a "name=nginx state=restarted" --become

Флаг --become — это sudo из 1.1 Linux, §4: задача выполняется от root.

Ad-hoc удобен для диагностики и разовых операций. Всё, что нужно повторять, оформляется в плейбук, иначе история изменений снова теряется.

// шаг 6/20 · теория · ~2 мин

Плейбук: желаемое состояние

Аналогия: чек-лист открытия кафе: «свет включён, касса работает, витрина заполнена». Не «включи свет», а «свет должен быть включён» — если уже горит, ничего делать не надо.

# playbooks/web.yml
- name: Настройка веб-серверов
  hosts: web
  become: true

  tasks:
    - name: Установить nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true
        cache_valid_time: 3600

    - name: Положить конфиг сайта
      ansible.builtin.template:
        src: templates/site.conf.j2
        dest: /etc/nginx/sites-available/site.conf
        mode: "0644"
      notify: Перезагрузить nginx

    - name: Включить сайт
      ansible.builtin.file:
        src: /etc/nginx/sites-available/site.conf
        dest: /etc/nginx/sites-enabled/site.conf
        state: link
      notify: Перезагрузить nginx

    - name: Nginx запущен и включён в автозагрузку
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: Перезагрузить nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded

ansible-playbook -i inventory/hosts.yml playbooks/web.yml

Как читать вывод:

  • ok — состояние уже было нужным, ничего не делалось.
  • changed — Ansible что-то изменил.
  • failed — ошибка, на этом узле прогон остановлен.
  • skipped — задача пропущена по условию.

В конце — сводка PLAY RECAP по каждому узлу. Здоровый повторный прогон выглядит как changed=0: всё уже в нужном состоянии.

Идемпотентность — главная идея

Аналогия: кнопка лифта. Нажмёшь один раз или десять — лифт приедет один раз.

Идемпотентность разбиралась ещё в 1.3 Bash на примере скриптов. В Ansible это свойство обеспечивает сам инструмент: модуль apt с state: present сначала проверяет, стоит ли пакет, и ставит его только если нет. Модуль template сравнивает содержимое файла и пишет только при отличии.

Из этого следует правило, которое проверяют на собеседованиях: по возможности используй специализированные модули, а не command и shell.

# плохо: выполняется при каждом прогоне, всегда "changed"
- name: Создать каталог
  ansible.builtin.command: mkdir -p /opt/app

# хорошо: проверяет состояние, меняет только при необходимости
- name: Создать каталог
  ansible.builtin.file:
    path: /opt/app
    state: directory
    owner: app
    mode: "0755"

Если без command никак — его делают идемпотентным вручную: параметром creates (не запускать, если файл уже есть) или changed_when, который говорит Ansible, когда считать задачу изменившей что-то.

- name: Инициализировать базу один раз
  ansible.builtin.command: /opt/app/bin/init-db
  args:
    creates: /opt/app/.db-initialized
⚠️«changed» при каждом прогоне — признак ошибки

Если повторный запуск плейбука показывает изменения там, где ничего не менялось, плейбук не идемпотентен. Это не косметика: такие задачи без нужды перезапускают сервисы через хендлеры и делают невозможным режим проверки (§11). Проверка простая — запустить плейбук дважды подряд, второй прогон обязан дать changed=0.

Переменные и факты

Аналогия: бланк договора с пустыми полями. Текст один, а имя, сумма и дата подставляются под конкретного клиента.

Переменные позволяют одним плейбуком настраивать разные окружения. Их можно задать в нескольких местах; самые используемые:

inventory/
  hosts.yml
  group_vars/
    all.yml         # для всех узлов
    web.yml         # только для группы web
  host_vars/
    db-1.yml        # только для конкретного узла

# group_vars/web.yml
app_port: 8000
server_name: shop.example.com
worker_processes: 4

Используются через фигурные скобки: "{{ app_port }}". Кавычки обязательны, если значение начинается со скобки, иначе YAML воспримет его как словарь.

У переменных есть приоритет: значение из host_vars перебивает group_vars, а переданное в командной строке через -e перебивает всё. Полная таблица приоритетов длинная, на практике достаточно помнить, что более конкретное побеждает более общее.

Факты — переменные, которые Ansible сам собирает с узла в начале прогона: дистрибутив, IP-адреса, объём памяти, число процессоров.

- name: Показать, что за система
  ansible.builtin.debug:
    msg: "{{ ansible_distribution }} {{ ansible_distribution_version }}, RAM {{ ansible_memtotal_mb }} MB"

Если факты не нужны, сбор отключают (gather_facts: false) — это ускоряет прогон на больших инвентарях.

Шаблоны Jinja2

Аналогия: письмо из рассылки: «Здравствуйте, {{ имя }}!» — шаблон один, писем тысячи.

Конфиги почти никогда не бывают одинаковыми для всех узлов: где-то другой порт, другое число воркеров, другой домен. Для этого модуль template берёт файл .j2 и подставляет в него переменные:

# templates/site.conf.j2
upstream app {
{% for host in groups['app'] %}
    server {{ hostvars[host].ansible_host }}:{{ app_port }};
{% endfor %}
}

server {
    listen 80;
    server_name {{ server_name }};

    location / {
        proxy_pass http://app;
    }
}

Это тот же Jinja2, что используется во Flask (2.5 Бэкенд-сервис): подстановки {{ }}, условия и циклы {% %}. Пример выше сам собирает список серверов приложения из инвентаря — добавил машину в группу app, перезапустил плейбук, и балансировщик о ней узнал.

Хорошая привычка — первой строкой шаблона ставить комментарий # Managed by Ansible, do not edit. Это предупреждение коллегам: ручная правка будет перезаписана при следующем прогоне.

// шаг 10/20 · теория · ~1 мин

Хендлеры: перезапуск только при изменениях

Аналогия: «если поменяли меню — перепечатать вывеску». Если меню не меняли, вывеску не трогают.

В плейбуке из §5 задача с конфигом содержит notify: Перезагрузить nginx. Это значит: если задача что-то изменила, в конце прогона выполнить хендлер с таким именем. Если конфиг не менялся — nginx не трогают.

Важные свойства хендлеров:

  • Выполняются один раз в конце плейбука, даже если их вызвали несколько задач.
  • Если прогон упал до конца, хендлеры не выполнятся. Принудительно запустить накопленные хендлеры можно задачей meta: flush_handlers.
  • Для nginx и большинства сервисов лучше reloaded, а не restarted: перечитывание конфига не рвёт существующие соединения (1.2 Сети и 1.1 Linux, §7).

Перед перезагрузкой стоит проверять конфиг — битый конфиг nginx не даст ему перезагрузиться. Модуль template умеет это сам через параметр validate:

- name: Положить конфиг nginx
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
    validate: nginx -t -c %s
  notify: Перезагрузить nginx

Роли: структура для переиспользования

Аналогия: типовой проект квартиры. Один раз разработали, дальше строят по нему в любом доме, меняя только отделку.

Когда плейбук разрастается до сотен строк, его раскладывают на роли. Роль — каталог с фиксированной структурой:

roles/
  nginx/
    tasks/main.yml        # задачи
    handlers/main.yml     # хендлеры
    templates/site.conf.j2
    files/                # файлы без шаблонизации
    defaults/main.yml     # значения переменных по умолчанию
    vars/main.yml         # переменные с высоким приоритетом
    meta/main.yml         # зависимости от других ролей

Плейбук становится коротким и читаемым:

- hosts: web
  become: true
  roles:
    - common       # пользователи, ssh, ufw, время
    - nginx
    - app

Каркас роли создаётся командой ansible-galaxy role init roles/nginx.

Ansible Galaxy — каталог готовых ролей и коллекций от сообщества. Например, роли для установки Docker, PostgreSQL или node_exporter. Ими пользуются, но с оглядкой: роль запускается с правами root на всех твоих серверах, поэтому стоит выбирать популярные, поддерживаемые и фиксировать версию в requirements.yml.

💡Роль common — первое, что пишут

В любом проекте есть набор, нужный каждому серверу: пользователь для деплоя с SSH-ключом, запрет входа root и по паролю (1.1 Linux, §11), файрвол (1.2 Сети), часовой пояс UTC и синхронизация времени (1.1 Linux, §14), базовые пакеты, node_exporter для мониторинга (4.5 Наблюдаемость). Это и есть роль common, и она отлично смотрится в портфолио.

Проверка перед применением

Аналогия: примерка перед покупкой. Посмотреть, как сидит, до того, как отрезать ярлыки.

Применять плейбук сразу на продакшен — рискованно. У Ansible есть встроенные способы посмотреть, что произойдёт:

# синтаксис
ansible-playbook playbooks/web.yml --syntax-check

# сухой прогон: что изменится, без изменений
ansible-playbook -i inventory/hosts.yml playbooks/web.yml --check --diff

# только на одном узле
ansible-playbook -i inventory/hosts.yml playbooks/web.yml --limit web-1

# только задачи с определённым тегом
ansible-playbook -i inventory/hosts.yml playbooks/web.yml --tags nginx

--check --diff — самая полезная пара: показывает, какие файлы поменяются и как именно, построчно. Ограничение: задачи command и shell в режиме проверки не выполняются, и то, что от них зависит, может показать неверную картину — ещё одна причина избегать их.

ansible-lint проверяет плейбуки на типовые ошибки: устаревший синтаксис, command вместо модуля, отсутствие имён у задач. Его запускают в CI так же, как линтер для кода (3.2 CI-CD).

Molecule — инструмент для тестирования ролей: поднимает контейнер, применяет роль, проверяет идемпотентность повторным прогоном и запускает проверки. Для junior достаточно знать, что такое существует и зачем.

// шаг 13/20 · теория · ~2 мин

Секреты: Ansible Vault

Аналогия: сейф внутри общей папки. Папку видят все, содержимое сейфа — только те, у кого есть ключ.

Пароли от баз, токены и ключи нельзя класть в репозиторий открытым текстом — их найдут так же быстро, как облачные ключи из 4.2 Облако, §5. Ansible Vault шифрует файлы с переменными:

ansible-vault create group_vars/db/vault.yml     # создать зашифрованный файл
ansible-vault edit group_vars/db/vault.yml       # отредактировать
ansible-playbook site.yml --ask-vault-pass       # запуск с вводом пароля
ansible-playbook site.yml --vault-password-file ~/.vault_pass  # пароль из файла

Принятая конвенция: секреты хранятся в vault.yml с префиксом vault_, а в обычном vars.yml на них ссылаются — так из открытого файла видно, какие переменные существуют, не раскрывая значений.

# group_vars/db/vars.yml
db_password: "{{ vault_db_password }}"

В CI пароль от Vault передаётся через защищённую переменную (3.2 CI-CD, §11). В больших компаниях вместо Ansible Vault часто используют HashiCorp Vault или облачный менеджер секретов — об этом в 6.2 DevSecOps.

🛑no_log для задач с секретами

Ansible печатает параметры задач в вывод, и пароль, переданный модулю, окажется в логе пайплайна. Для таких задач ставят no_log: true. Забытый no_log — один из самых частых способов утечки секретов через CI.

Ansible, Terraform и Docker: кто за что

Аналогия: строители возводят дом (Terraform), отделочники делают ремонт внутри (Ansible), а мебель приезжает собранной в коробках (Docker).

Новички часто путают зоны ответственности. Разделение, которое принято в индустрии:

Инструмент Задача Пример
Terraform (4.4 Terraform) Создать инфраструктуру VPC, машины, балансировщик, база
Ansible Настроить машины Пользователи, пакеты, конфиги, Docker
Docker / Kubernetes Запустить приложение Контейнеры с кодом

Пересечения есть: Ansible умеет создавать облачные машины, Terraform — запускать скрипты на них. Но использовать инструмент не по назначению — путь к боли: Terraform плохо справляется с настройкой внутри ОС, а Ansible плохо отслеживает состояние облачных ресурсов и их удаление.

Где Ansible остаётся незаменимым даже в мире контейнеров и Kubernetes:

  • Подготовка узлов кластера: ядро, sysctl, containerd, установка k3s (5.2 Kubernetes в работе).
  • Серверы, которые не живут в контейнерах: базы на выделенных машинах, балансировщики, бастионы.
  • Регулярные операции: ротация ключей, обновление пакетов на всём парке, сбор диагностики.
// шаг 15/20 · теория · ~1 мин

Типичные ошибки

Аналогия: грабли, которые лежат на одном и том же месте у всех.

  • Задачи без имён. Вывод превращается в нечитаемую простыню. Каждая задача получает понятное имя на любом языке.
  • shell везде. Плейбук становится набором bash-скриптов с YAML-обёрткой: не идемпотентен, не работает --check.
  • Пароли в открытом виде. Даже «временно» и «в приватном репозитории».
  • Ручные правки на серверах. Следующий прогон их перезапишет — или, хуже, не перезапишет, и сервер разойдётся с кодом. Правило команды: поменял руками в аварии — сразу перенёс в код.
  • Нет фиксации версий. Роли из Galaxy и коллекции без версий однажды обновятся и сломают прогон.
  • Прогон сразу на весь продакшен. Для изменений, затрагивающих работу сервиса, используют serial: 1 или serial: "25%" — плейбук идёт по узлам порциями, и если первая порция сломалась, остальные не тронуты.
- hosts: web
  serial: 1                  # по одному узлу
  max_fail_percentage: 0     # остановиться при первой ошибке
// шаг 16/20 · итоги · ~1 мин

Если запомнить только главное

  • Управление конфигурацией кодом убирает дрейф, снежинки и ручные правки без истории.
  • Ansible безагентный: нужен только SSH и Python на узле, модель push.
  • Инвентарь — кого настраиваем, плейбук — что должно быть, модуль — как это сделать.
  • Идемпотентность: повторный прогон даёт changed=0. Используй модули, а не command/shell.
  • Переменные — в group_vars/host_vars, более конкретное побеждает общее. Факты Ansible собирает сам.
  • Конфиги — через шаблоны Jinja2, с validate перед применением.
  • Хендлеры перезапускают сервис только если конфиг реально изменился, и один раз в конце.
  • Большие плейбуки раскладывают на роли. Первая роль в любом проекте — common.
  • Перед применением — --check --diff и --limit. В CI — ansible-lint.
  • Секреты — в Ansible Vault, задачи с ними — с no_log: true.
  • Terraform создаёт инфраструктуру, Ansible её настраивает, Docker запускает приложения.
  • Изменения на продакшене катят порциями через serial.

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

💡В портфолио
  • Задания 2–5 — роли Ansible в P2: common, nginx, postgres, Vault и линтер в CI.
  • Роль common — это M1, переписанный на Ansible: хорошая тема для README «было — стало».

Задание 1 — стенд из трёх машин

Подними три виртуалки (Vagrant + VirtualBox или облако): одну управляющую и две управляемые. Настрой SSH-доступ по ключу с управляющей на обе.
Напиши inventory/hosts.yml с группами web (одна машина) и db (вторая).
Проверка: ansible all -i inventory/hosts.yml -m ping возвращает pong от обеих машин.

Задание 2 — роль common

Напиши роль, которая на всех узлах: создаёт пользователя deploy с твоим публичным ключом и правом sudo без пароля, запрещает вход root и вход по паролю в sshd_config (с хендлером на reload sshd), ставит htop, curl, ufw, включает ufw с разрешённым портом 22, ставит часовой пояс UTC.
Проверка: первый прогон — изменения, второй прогон — changed=0. Вход ssh root@... отклоняется, ssh deploy@... работает.

Задание 3 — nginx из шаблона

Роль nginx для группы web: установка, конфиг из шаблона с переменными server_name и app_port, validate: nginx -t -c %s, хендлер reloaded.
Поменяй app_port в group_vars/web.yml и запусти с --check --diff.
Проверка: дифф показывает ровно одну изменённую строку конфига; после реального прогона nginx перезагружен, а не перезапущен (systemctl status nginx показывает старое время старта).

Задание 4 — секрет через Vault

Роль postgres для группы db: установка PostgreSQL, создание базы и пользователя с паролем из vault.yml (модули community.postgresql.postgresql_db и postgresql_user).
Проверка: git grep по репозиторию не находит пароль открытым текстом; в выводе прогона пароль не печатается.

Задание 5 — линтер в CI

Добавь в репозиторий пайплайн GitLab CI или GitHub Actions, который запускает ansible-lint и ansible-playbook --syntax-check.
Проверка: намеренно замени модуль file на command: mkdir — пайплайн должен упасть на линтере.
