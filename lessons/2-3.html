О чём урок

ℹ️Зачем это нужно

Здесь начинается настоящий DevOps-Python: не «посчитать что-то в одной функции», а «несколько процессов работают одновременно и не мешают друг другу», «скачать много файлов, не дожидаясь по очереди каждого» — ровно то, из чего состоят реальные скрипты автоматизации.

📘Словарик на будущее
  • Процесс — отдельная, полностью независимая копия программы со своей памятью (в отличие от потока/thread, который делит память с остальными).
  • Асинхронность — способ не ждать медленную операцию (сеть, диск) простаивая, а заняться тем временем чем-то ещё.
  • Race condition — ситуация, когда результат зависит от того, кто из параллельных процессов «успел первым» — источник трудноуловимых багов.
// шаг 2/17 · теория · ~1 мин

Парадигмы программирования — зачем их различать

Аналогия: ООП, процедурный и функциональный подходы — это не разные языки, а разные «стили письма» на одном языке: можно писать роман главами (процедуры), можно через диалоги персонажей (объекты), а можно как математическое доказательство без побочных эффектов (функции).

  • Процедурный — программа как последовательность шагов и вызовов функций.
  • ООП — данные и поведение объединены в объекты (класс Server, класс Deployment).
  • Функциональный — функции не меняют данные снаружи, а возвращают новые значения.
  • Мультипарадигмальный — Python не заставляет выбирать одно: обычно в одном проекте смешивают все три подхода там, где уместно.

Многопроцессность

Аналогия: если один кассир обслуживает очередь, люди ждут по одному. Если открыть несколько касс (процессов) — очередь двигается параллельно, и каждая касса вообще не знает, что происходит у соседней.

Задача: за ночь накопилось 40 логов по гигабайту, их нужно сжать перед отправкой в архив. Сжатие нагружает процессор, и на 8-ядерной машине делать его по одному файлу — значит оставить семь ядер без дела.

from multiprocessing import Process
import gzip, shutil, pathlib

def compress(path: pathlib.Path):
    with open(path, "rb") as src, gzip.open(f"{path}.gz", "wb") as dst:
        shutil.copyfileobj(src, dst)      # читаем и пишем кусками, не весь файл в память
    path.unlink()                         # исходник удаляем только после успешного сжатия

files = sorted(pathlib.Path("/var/log/myapp").glob("*.log.1"))
processes = [Process(target=compress, args=(f,)) for f in files[:8]]
for p in processes:
    p.start()
for p in processes:
    p.join()   # дождаться завершения всех процессов

Каждый процесс — полностью независимая копия программы; они не делят переменные напрямую (в отличие от потоков), поэтому для общих данных (например, общей очереди файлов) нужны специальные потокобезопасные структуры (multiprocessing.Queue, Manager). Здесь запущено ровно 8 процессов по числу ядер — как раздать 40 файлов восьми работникам без ручного учёта, показано в §8.

Случайность по распределению, а не поровну

Аналогия: нечестная монета, которая падает орлом в девяти случаях из десяти. Иногда именно такая и нужна.

Канареечный выкат (6.1 CI-CD в Kubernetes, §15): новая версия получает 10% запросов, старая — 90%. Если на 10% всё спокойно, долю увеличивают. Так же работают балансировщики с весами и нагрузочные тесты, имитирующие реальный трафик:

import random

backends = ["v1", "v2-canary"]
weights = [90, 10]                                   # веса не обязаны давать в сумме 1

sample = random.choices(backends, weights=weights, k=10_000)
print(sample.count("v2-canary"))                    # около 1000

# имитация трафика: главная страница чаще остальных
paths = ["/", "/catalog", "/cart", "/checkout"]
next_path = random.choices(paths, weights=[60, 25, 10, 5])[0]

random.choices(..., weights=..., k=...) — взвешенный случайный выбор с повторениями: варианты выпадают пропорционально весам, а k задаёт, сколько раз выбирать. Веса нормировать не нужно: [90, 10] и [0.9, 0.1] дают одно и то же. Для воспроизводимых тестов перед выбором вызывают random.seed(42) — тогда «случайная» последовательность будет одинаковой при каждом запуске.

Живое обновление вывода в консоли

Аналогия: вместо того чтобы печатать новую простыню текста при каждом изменении, экран «стирается» и перерисовывается на том же месте — как электронное табло, а не бесконечная лента чека.

import os

def render():
    os.system('cls' if os.name == 'nt' else 'clear')
    print(build_table())

while not all(task.done() for task in tasks):
    render()
    time.sleep(0.5)

Так выглядит вывод docker pull или apt upgrade: строки с прогрессом обновляются на месте. Для более серьёзного интерфейса (не просто очистка экрана) существует библиотека curses — про неё подробнее в 2.4 Архитектура и тесты, §12.

Конечный автомат состояний (state machine)

Аналогия: заказ в кофейне на табло: «в очереди» → «готовится» → «готов» / «отменён». В любой момент времени заказ находится ровно в одном из этих состояний, и переходы между ними подчиняются чётким правилам: готовый заказ нельзя снова поставить в очередь.

Ровно так живёт задача в пайплайне CI/CD или под в Kubernetes. Деплой, например:

from enum import Enum

class Status(Enum):
    PENDING = "ожидает"
    RUNNING = "выполняется"
    SUCCESS = "успешно"
    FAILED = "ошибка"
    ROLLED_BACK = "откачен"

ALLOWED = {
    Status.PENDING: {Status.RUNNING},
    Status.RUNNING: {Status.SUCCESS, Status.FAILED},
    Status.FAILED: {Status.ROLLED_BACK},
}

class Deployment:
    def __init__(self, version: str):
        self.version = version
        self.status = Status.PENDING

    def move_to(self, new: Status):
        if new not in ALLOWED.get(self.status, set()):
            raise ValueError(f"нельзя перейти из {self.status.value} в {new.value}")
        self.status = new

Enum — способ перечислить весь набор допустимых состояний явно, вместо того чтобы полагаться на произвольные строки («успешно», «Успешно», «success» — три разные строки для Python, три источника багов). Словарь ALLOWED описывает разрешённые переходы, и метод move_to проверяет каждый: попытка перевести успешный деплой обратно в «выполняется» закончится понятной ошибкой, а не тихо испорченным состоянием. Из SUCCESS и ROLLED_BACK переходов нет вовсе — это конечные состояния.

Асинхронное программирование

Аналогия: синхронный код — это как готовить ужин по одному рецепту зараз: сварил суп, потом только начал жарить котлеты. Асинхронный — как опытный повар: поставил суп вариться и, пока он варится (не отвлекая руки), уже режет овощи для другого блюда.

import asyncio
import aiohttp

async def check(session, url):
    async with session.get(url, timeout=aiohttp.ClientTimeout(total=3)) as resp:
        return url, resp.status

async def main(urls):
    async with aiohttp.ClientSession() as session:
        results = await asyncio.gather(*(check(session, url) for url in urls))
    for url, status in results:
        print(status, url)

asyncio.run(main(["https://example.com/healthz", "https://example.org/healthz"]))

Ключевые слова async и await — синтаксическая основа асинхронности в Python. async def объявляет не обычную, а «асинхронную» функцию — вызвать её напрямую как обычную нельзя, она возвращает специальный объект-обещание («корутину»), который нужно либо дождаться через await, либо явно запустить через asyncio.run. await внутри такой функции означает «здесь можно приостановиться и отдать управление кому-то другому, пока не придёт результат этой операции» — именно в этот момент, пока одна проверка check ждёт ответа сервера по сети, интерпретатор может переключиться и продолжить другую. asyncio.gather запускает сразу несколько таких асинхронных функций и ждёт, пока все они закончатся — так все проверки идут «одновременно» (пока одна ждёт ответ по сети, выполняется другая) — вместо того чтобы ждать каждую по очереди. Сто адресов с ответом по секунде проверятся примерно за секунду, а не за сто.

⚠️Лайфхак: не давай программе падать на одной ошибке

Если один адрес из ста не отвечает, скрипт проверки не должен падать — он должен проверить остальные и собрать сводку в конце. Это общий принцип реальных скриптов автоматизации: одна неудачная операция не должна валить весь батч. В asyncio.gather для этого есть параметр return_exceptions=True, а в простом цикле — try/except на каждую операцию:

results = []
for url in urls:
    try:
        results.append(await check(session, url))
    except (aiohttp.ClientError, asyncio.TimeoutError) as e:
        results.append((url, f"ошибка: {type(e).__name__}"))

GIL: почему в Python процессы, а не потоки


Аналогия: GIL (Global Interpreter Lock) — как единственный ключ от кассы в маленьком магазине: сколько бы кассиров (потоков) ни стояло у одной кассы, реально пробивать чек может только тот, у кого сейчас ключ. Открыть вторую кассу (процесс) с отдельным ключом — единственный способ работать по-настоящему параллельно.

В стандартном Python (CPython) только один поток одновременно может выполнять байткод — даже на процессоре с 8 ядрами. Поэтому:

  • Потоки (threading) отлично подходят, когда программа ждёт (сеть, диск, time.sleep) — во время ожидания GIL освобождается, и другой поток может работать.
  • Процессы (multiprocessing) нужны, когда программа реально считает (математика, обработка данных) — у каждого процесса свой Python-интерпретатор и свой GIL, поэтому они действительно выполняются параллельно на разных ядрах.

Именно поэтому для сжатия логов (§2) выбраны процессы, а не потоки: сжатие — это не ожидание сети, а реальная работа процессора, и потоки упёрлись бы в GIL.

💡Лайфхак

Если код в основном ждёт (запросы к API, чтение файлов) — асинхронность (§6) или потоки эффективнее и дешевле по памяти, чем процессы. Если код в основном считает — только процессы дают настоящий параллелизм в Python. Путать эти два случая — частая причина, почему «многопоточный» скрипт не ускоряется вообще.

ℹ️GIL сегодня: free-threading

Начиная с Python 3.14 (октябрь 2025) существует официально поддерживаемая сборка без GIL — она перестала считаться экспериментальной. Но три оговорки, без которых ответ на собеседовании будет неполным:

  • это отдельный бинарник (3.14t), а не поведение по умолчанию — его надо ставить осознанно;
  • однопоточный код в нём работает на 5–10% медленнее;
  • если импортировать C-расширение, не объявившее себя потокобезопасным, интерпретатор тихо включает GIL обратно на весь процесс — потоки продолжат работать, но параллельности не будет.

План сообщества — сделать отключение GIL управляемым флагом в ближайшие релизы, а поведением по умолчанию не раньше конца десятилетия. Практический вывод на 2026 год: писать код надо по-прежнему исходя из наличия GIL, но знать про free-threading стоит — вопрос всплывает.

concurrent.futures — практичный способ запускать параллельно

Аналогия: вместо того чтобы вручную нанимать каждого работника, вести учёт и по одному встречать со смены, ты нанимаешь бригаду фиксированного размера и просто отдаёшь ей список задач.

Ручное создание Process из §2 полезно для понимания, но в рабочем коде почти всегда берут пул — он сам следит за количеством, собирает результаты и корректно закрывается.

from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor, as_completed

def check_host(host: str) -> tuple[str, bool]:
    ...   # проверка по сети — код ЖДЁТ

with ThreadPoolExecutor(max_workers=20) as pool:
    futures = {pool.submit(check_host, h): h for h in hosts}
    for fut in as_completed(futures):
        host = futures[fut]
        try:
            name, alive = fut.result()
        except Exception as e:
            print(f"{host}: проверка не удалась — {e}")
        else:
            print(f"{name}: {'жив' if alive else 'мёртв'}")

Красота в том, что переход между режимами — это замена одного слова: ThreadPoolExecutor для ожидания, ProcessPoolExecutor для вычислений. Остальной код не меняется.

as_completed отдаёт результаты по мере готовности, а не в порядке отправки — так первые ответы видны сразу, не дожидаясь самого медленного. Исключение внутри задачи не роняет пул: оно всплывает при вызове fut.result(), и его можно обработать локально, продолжив остальные.

max_workers — не «чем больше, тем лучше». Для процессов разумный ориентир — число ядер (os.cpu_count()), для потоков зависит от того, сколько одновременных соединений выдержит та сторона.

Race condition и блокировки

Аналогия: два человека одновременно смотрят на остаток в 100 рублей, каждый решает снять 60, и оба видят «хватает». В сумме снимают 120 — банк уходит в минус, хотя каждая проверка по отдельности была верной.

Гонка возникает там, где несколько исполнителей читают и меняют одни и те же данные, а между чтением и записью успевает вклиниться другой.

import threading

counter = 0

def worker():
    global counter
    for _ in range(100_000):
        counter += 1      # ✘ не атомарно: прочитать → прибавить → записать

threads = [threading.Thread(target=worker) for _ in range(4)]
[t.start() for t in threads]
[t.join() for t in threads]
print(counter)      # почти наверняка меньше 400 000

Строка counter += 1 выглядит одной операцией, но на самом деле их три, и переключение между потоками может произойти между ними. Лечится блокировкой:

lock = threading.Lock()

def worker():
    global counter
    for _ in range(100_000):
        with lock:            # ✔ внутрь пускается только один поток за раз
            counter += 1

with lock гарантирует, что участок кода выполняет строго один поток. Тот же механизм для процессов — multiprocessing.Lock.

⚠️Блокировка — не бесплатное решение

Слишком широкая блокировка убивает весь смысл параллелизма: если под ней оказалась вся работа, исполнители просто стоят в очереди. Слишком много разных блокировок — риск взаимной блокировки (deadlock): поток A держит замок 1 и ждёт замок 2, поток B держит замок 2 и ждёт замок 1, оба стоят навсегда. Простое правило, снимающее большинство таких случаев: всегда захватывать блокировки в одном и том же порядке.

Лучший способ избежать гонок — не разделять изменяемое состояние вовсе. Именно поэтому процессы с очередью (multiprocessing.Queue) из §2 часто проще и надёжнее, чем потоки с общими переменными: данные передаются сообщениями, а не правятся сообща.

// шаг 11/17 · теория · ~1 мин

Ограничение параллелизма и таймауты

Аналогия: попросить сто человек одновременно войти в дверь шириной в одного — быстрее не станет, а дверь можно и сломать.

Наивный asyncio.gather на большом списке запускает все задачи разом. На десяти тысячах URL это исчерпает лимит файловых дескрипторов, забьёт канал и, скорее всего, приведёт к бану на той стороне.

import asyncio

sem = asyncio.Semaphore(10)          # не больше 10 одновременных запросов

async def fetch(session, url):
    async with sem:
        async with session.get(url, timeout=aiohttp.ClientTimeout(total=15)) as r:
            return await r.text()

results = await asyncio.gather(*(fetch(s, u) for u in urls), return_exceptions=True)

Три обязательные детали в этом коде. Семафор ограничивает число одновременных операций — остальные ждут своей очереди. Таймаут обязателен всегда: без него зависшее соединение подвесит задачу навсегда, и скрипт в systemd-таймере будет копиться в памяти запуск за запуском. return_exceptions=True заставляет gather не падать на первой же ошибке, а вернуть исключения в списке результатов наравне со значениями — прямое продолжение принципа «одна неудача не валит весь батч» из §6.

Аналог для пулов из §8 — это сам max_workers: он и есть ограничитель параллелизма.

// шаг 12/17 · теория · ~2 мин

Повторные попытки: экспоненциальная задержка


Аналогия: если сервис прилёг под нагрузкой, а ты повторяешь запрос немедленно и без остановки — ты не пытаешься его дождаться, ты добиваешь его окончательно.

import random, time

def with_retry(func, attempts=5, base=1.0):
    for attempt in range(attempts):
        try:
            return func()
        except (TimeoutError, ConnectionError) as e:
            if attempt == attempts - 1:
                raise
            delay = base * (2 ** attempt) + random.uniform(0, 1)
            print(f"Попытка {attempt + 1} не удалась ({e}), жду {delay:.1f}с")
            time.sleep(delay)

Пауза удваивается с каждой попыткой: 1, 2, 4, 8 секунд. Это даёт сервису шанс восстановиться вместо того, чтобы получать волну повторов.

Слагаемое random.uniform(0, 1) — джиттер, и он не украшение. Если сто клиентов упали одновременно, то и повторят они одновременно, ровно через 1, 2 и 4 секунды — волна нагрузки повторится с прежней силой. Случайная добавка размазывает повторы во времени.

🛑Не всё можно повторять

Повтор безопасен только для идемпотентных операций — тех, которые от повторного выполнения не меняют результат. GET и PUT обычно идемпотентны, POST «списать деньги» — нет: ответ мог потеряться уже после того, как деньги списались, и повтор спишет их дважды. Для таких случаев на стороне API используют ключ идемпотентности — уникальный идентификатор операции, по которому сервер узнаёт повтор.

И отдельно: повторять имеет смысл только временные ошибки. Код 429 (слишком много запросов) и 503 — да. Код 400 или 404 — нет: запрос не станет корректнее оттого, что его отправили пять раз.

В рабочих проектах это редко пишут руками — берут библиотеку tenacity, где то же самое задаётся декоратором. Но понимать, что именно она делает, нужно.

// шаг 13/17 · итоги · ~1 мин

Если запомнить только главное

  • Процессы не делят память — для общих данных нужны специальные потокобезопасные структуры.
  • Enum фиксирует весь набор допустимых состояний явно — вместо произвольных строк, которые легко перепутать.
  • random.choices(weights=...) — случайность с разной вероятностью исходов, а не «50 на 50».
  • Асинхронность полезна, когда программа ждёт (сеть/диск), а не когда она реально считает (для чистого CPU нужна многопроцессность).
  • Одна упавшая операция в батче не должна валить весь скрипт — лови ошибку локально и продолжай.
  • Выбор режима — один вопрос: код ждёт (async или потоки) или считает (процессы). Потоки для вычислений не ускоряют ничего из-за GIL.
  • ThreadPoolExecutor / ProcessPoolExecutor — рабочий способ вместо ручных Process; переключение между ними меняет одно слово.
  • counter += 1 не атомарно — это гонка. Лечится with lock, но лучше не разделять изменяемое состояние вовсе.
  • gather без семафора запускает всё разом; таймаут обязателен всегда, return_exceptions=True не даёт упасть на первой ошибке.
  • Повторы — только с экспоненциальной задержкой и джиттером, только для идемпотентных операций и только на временные ошибки.
  • Free-threading официально поддерживается с Python 3.14, но отдельной сборкой и с оговорками — писать код пока следует исходя из наличия GIL.

Практика

Задания делаются на своей машине или в облаке. Отметь задание, когда выполнила проверку из его описания, — за каждое начисляется опыт.

💡В портфолио
  • Задание 2 (асинхронная проверка многих адресов с ограничением) — ядро M2.
  • Задание 3 (повторы с экспоненциальной задержкой) — отправка сообщений в M3.

Задание 1 — потоки против процессов

Напиши функцию, которая считает простые числа до 2 млн (нагрузка на CPU), и функцию, которая скачивает 20 страниц (нагрузка на ввод-вывод). Запусти каждую последовательно, через ThreadPoolExecutor и через ProcessPoolExecutor.
Проверка: таблица времени показывает, что для CPU помогают процессы, а для сети — потоки. Объясняешь результат через GIL.

Задание 2 — асинхронный проверяльщик

Через asyncio и aiohttp (или httpx) проверь доступность 50 адресов с ограничением в 10 одновременных запросов (Semaphore) и таймаутом 3 секунды.
Проверка: общее время — примерно максимум из таймаутов, а не их сумма; одновременно не больше 10 соединений.

Задание 3 — повторы с задержкой

Напиши декоратор retry с экспоненциальной задержкой и случайным разбросом (jitter), который повторяет только сетевые ошибки и не больше N раз.
Проверка: тест с функцией, которая падает дважды и на третий раз отвечает: вызвана ровно 3 раза, паузы растут.

Задание 4 — гонка и блокировка

Создай общий счётчик и увеличь его из 10 потоков по 100 000 раз без блокировки, затем с threading.Lock.
Проверка: без блокировки итог иногда меньше 1 000 000 (запусти несколько раз), с блокировкой всегда ровно 1 000 000.

Задание 5 — конечный автомат

Опиши состояния деплоя (pending, building, testing, deploying, done, failed) и разрешённые переходы. Недопустимый переход выбрасывает исключение.
Проверка: тесты на допустимые и недопустимые переходы.
