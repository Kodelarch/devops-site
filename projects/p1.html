P1 — Сервис на одном сервере

📦Стартовый каркас

Приложение shop-api с тестами, Dockerfile, Compose и пайплайном — точка старта для этого проекта. Что доделать, написано в его README.

Скачать shop-api-starter.zip

ℹ️Что получится

Виртуальная машина с Linux, на которой в Docker Compose работают приложение, PostgreSQL и nginx с HTTPS. Изменения в коде проходят через GitLab CI и сами выкатываются на сервер. Бэкапы базы делаются по расписанию и проверяются восстановлением, простой мониторинг присылает уведомления.

Это проект уровня «могу самостоятельно поднять и сопровождать сервис». Его можно сделать целиком на своём компьютере в VirtualBox, без облака и без затрат.

Уроки: 1.1 Linux, 1.2 Сети, 1.3 Bash, 2.5 Бэкенд-сервис, 2.11 Продвинутый SQL, 3.1 Docker, 3.2 CI-CD, 4.1 Compose и Swarm.

Архитектура

Интернет ──443──► nginx (TLS, reverse proxy)
                     │
                     ▼
                 app (Flask/FastAPI, gunicorn) ──► PostgreSQL (том)
                     
GitLab CI ──ssh──► сервер: docker compose pull && up -d
cron ──► backup.sh ──► pg_dump ──► /backup (7 копий)

Требования

Сервер

  • Ubuntu Server LTS, статический IP, часовой пояс UTC, unattended-upgrades.
  • Пользователь deploy, вход только по ключу, root запрещён (1.1 Linux, §11).
  • ufw: открыты только 22 (с твоего IP) и 80/443.

Приложение

Начни со стартового каркаса из папки _starter/shop-api в хранилище (на сайте курса — кнопка «Скачать» вверху этой страницы): первые три пункта в нём уже сделаны, твоя задача — понять, как они устроены, и описать это в README.

  • API с CRUD-ресурсом, /healthz и /readyz, логи в JSON в stdout (2.5 Бэкенд-сервис).
  • Конфигурация только из переменных окружения, без секретов в коде.
  • Тесты pytest на бизнес-логику и эндпоинты.

Контейнеры

  • Dockerfile: slim-база, multi-stage при необходимости, USER не root, HEALTHCHECK (3.1 Docker).
  • compose.yaml: app, db, nginx; база недоступна снаружи; depends_on с service_healthy; лимиты памяти; том для данных.
  • nginx: редирект HTTP → HTTPS, сертификат (Let's Encrypt при наличии домена, иначе самоподписанный), заголовки безопасности.

CI/CD

  • Стадии lint → test → build → deploy (3.2 CI-CD).
  • Образ в Container Registry GitLab с тегом коммита.
  • Деплой по SSH на сервер только из main, ключ — в защищённой переменной.
  • Уведомление в Telegram об успехе или провале.

Эксплуатация

  • backup.sh по cron: pg_dump -Fc, хранение 7 копий, логирование, set -euo pipefail (1.3 Bash).
  • Восстановление бэкапа проверено и описано в README пошагово.
  • logrotate или ограничение логов Docker (max-size).
  • Простая проверка доступности: cron-скрипт с curl -f /healthz и уведомлением в Telegram при ошибке (полноценный мониторинг будет в P2).

Структура репозитория

p1-server/
  app/                 # код приложения и тесты
  nginx/               # конфиг nginx
  scripts/
    backup.sh
    restore.md
    healthcheck.sh
  compose.yaml
  compose.prod.yaml
  Dockerfile
  .gitlab-ci.yml
  .env.example         # пример переменных, без реальных значений
  README.md

Готово, когда

  • Клонирование репозитория и docker compose up -d поднимает всё локально за пару минут.
  • Коммит в main через 5–10 минут работает на сервере без ручных команд.
  • Сервер переживает перезагрузку: всё поднимается само.
  • Ты можешь удалить базу и восстановить её из бэкапа по README.

Что рассказать на собеседовании

  • Почему nginx перед приложением, а не приложение напрямую на 443.
  • Как устроен деплой и что будет, если новая версия не стартует.
  • Как ты проверяешь, что бэкапы рабочие.
  • Что бы поменяла для продакшена с реальной нагрузкой (переход к P2 и P3).
