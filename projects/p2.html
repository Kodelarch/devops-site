P2 — Инфраструктура кодом в облаке

ℹ️Что получится

То же приложение из P1-Server-Basics, но инфраструктура больше не настраивается руками. Terraform создаёт в облаке сеть в двух зонах, машины и хранилище, Ansible настраивает машины, а стек мониторинга с логами и алертами разворачивается вместе с приложением. Весь стенд поднимается с нуля одной последовательностью команд и одной же уничтожается.

Это проект уровня «умею работать с облаком и автоматизировать инфраструктуру». Именно такой опыт чаще всего просят в вакансиях junior DevOps.

Уроки: 4.2 Облако, 4.4 Terraform, 4.3 Ansible, 4.5 Наблюдаемость, 1.4 Метрики и логи.

⚠️Деньги

Облако платное. Используй стартовый грант Yandex Cloud, прерываемые машины, бюджет с оповещением (4.2 Облако, §10) и всегда terraform destroy после работы. Стенд нужен только на время разработки и для скриншотов.

Архитектура

                Yandex Cloud, VPC 10.0.0.0/16
 ┌─────────────── zone a ───────────────┬─────────── zone b ───────────┐
 │ public:  bastion, lb (nginx)         │ public:  —                   │
 │ private: app-1                       │ private: app-2               │
 │ private: db-1 (PostgreSQL)           │                              │
 │ private: monitoring (Prometheus,     │                              │
 │          Grafana, Loki, Alertmanager)│                              │
 └──────────────────────────────────────┴──────────────────────────────┘
 Object Storage: состояние Terraform, бэкапы базы

Требования

Terraform

  • Удалённое состояние в Object Storage с версионированием и блокировкой (4.4 Terraform, §5).
  • Модули network, vm-group; подсети через for_each в двух зонах.
  • Группы безопасности ссылаются друг на друга: lb → app → db; SSH только через бастион.
  • Метки project, env, owner на всех ресурсах через locals.
  • Выходные значения передаются в инвентарь Ansible (или динамический инвентарь по меткам).
  • terraform fmt -check, validate и Checkov в CI; plan в merge request, apply вручную из main.

Ansible

  • Роли common (пользователи, SSH, ufw, UTC, node_exporter), docker, app, postgres, nginx, monitoring (4.3 Ansible).
  • Секреты в Ansible Vault, задачи с ними — no_log: true.
  • Повторный прогон даёт changed=0.
  • ansible-lint в CI.

Мониторинг

  • Prometheus, Grafana (provisioning), Loki + Alloy, Alertmanager (4.5 Наблюдаемость).
  • Метрики приложения: RPS, ошибки, p95; дашборд четырёх золотых сигналов.
  • blackbox_exporter: доступность снаружи и срок сертификата.
  • Алерты TargetDown, HighErrorRate, DiskWillFillIn4Hours с маршрутами в Telegram и runbook для каждого.
  • Grafana открыта только через nginx с HTTPS и паролем, остальное — во внутренней сети.

Данные

  • Ежедневный бэкап базы в Object Storage с правилом жизненного цикла.
  • Проверка восстановления описана и выполнена.

Структура репозитория

p2-infra/
  terraform/
    modules/{network,vm-group}/
    envs/dev/
  ansible/
    inventory/
    group_vars/
    roles/{common,docker,app,postgres,nginx,monitoring}/
    site.yml
  monitoring/
    prometheus/  alertmanager/  grafana/  runbooks/
  Makefile             # make up / make down
  .gitlab-ci.yml
  README.md

Готово, когда

  • make up (= terraform apply + ansible-playbook) с нуля поднимает рабочий стенд.
  • make down удаляет всё; в консоли облака ничего не осталось.
  • Остановка одной машины с приложением не роняет сервис — работает вторая зона.
  • Учебная авария (остановленный контейнер, заполненный диск) приходит алертом в Telegram, а по runbook ты находишь причину.
  • В README есть скриншоты дашбордов и уведомлений.

Что рассказать на собеседовании

  • Как разделены зоны ответственности Terraform и Ansible и почему.
  • Где хранится состояние и что будет при одновременном apply.
  • Почему приложение в двух зонах и что произойдёт при отказе одной.
  • Какие алерты ты завела, почему именно они и чем алерт на симптом лучше алерта на причину.
  • Сколько стоил стенд и как ты контролировала расходы.
