Портфолио: пет-проекты для junior DevOps

ℹ️Зачем это нужно

Работодатель не увидит твои заметки и не узнает, сколько уроков ты прочитала. Он откроет GitHub или GitLab по ссылке из резюме и за пять минут решит, звать ли на собеседование. Ему нужно увидеть работающие проекты с понятным README, историей коммитов и пайплайном, который проходит.

Три проекта ниже собирают практику уроков в то, что можно показать. Они идут по нарастающей: каждый следующий использует результат предыдущего, а последний — это итоговый проект из 6.3 Итоговый проект.

Три больших проекта

# Проект Когда делать Что показывает
1 Сервис на одном сервере После частей 1–3 Linux, сети, Docker, CI/CD, бэкапы
2 Инфраструктура кодом в облаке После части 4 Облако, Terraform, Ansible, мониторинг
3 Kubernetes и GitOps После частей 5–6 Kubernetes, Helm, Argo CD, DevSecOps

Для всех трёх используется одно и то же приложение — небольшой веб-сервис с базой данных (например, API магазина на Flask или FastAPI с PostgreSQL и учебной базой из SQL-уроков). Так проекты складываются в одну историю: «я взяла приложение и провела его от одного сервера до Kubernetes с GitOps».

Маленькие проекты на выходные

Большие проекты показывают систему целиком, маленькие — что ты доводишь до конца аккуратные самостоятельные вещи. Каждый занимает один-два выходных и становится отдельным репозиторием с зелёным пайплайном. Делай их по ходу курса, не дожидаясь больших.

# Проект Когда делать Что показывает
M1 Скрипт подготовки нового сервера После части 1 Bash, безопасность сервера, идемпотентность
M2 certwatch: проверка сертификатов После части 2 Python CLI, тесты без сети, упаковка, Docker
M3 Telegram-бот для алертов После части 4 Бэкенд, Alertmanager, метрики, секреты
M4 Универсальный Helm-чарт После части 5 Шаблоны Helm, проверки, публикация в OCI

Стартовый каркас

Чтобы не начинать P1 с пустой папки, есть каркас приложения shop-api: API магазина из урока 2.5 Бэкенд-сервис на учебной базе SQL-уроков, с тестами, Dockerfile, Compose и пайплайном. Он лежит в хранилище в папке _starter/shop-api, а на сайте курса его можно скачать архивом со страницы P1-Server-Basics. Каркас — точка старта, а не готовый проект: всё, что отмечено в его README как TODO, ты делаешь сама.

Требования к каждому репозиторию

Это то, что отличает проект в портфолио от учебной папки:

  • README на понятном языке (русский или английский): что это, схема архитектуры, как запустить одной-двумя командами, что внутри, какие решения и почему.
  • Пайплайн зелёный. Красный значок на главной странице репозитория — первое, что видят.
  • История коммитов осмысленная — Conventional Commits (0.1 Git, §14), а не «fix», «fix2», «финал».
  • Ни одного секрета в истории. Перед публикацией — gitleaks detect по всей истории (6.2 DevSecOps, §2).
  • Версии зафиксированы — образы, провайдеры, роли, чарты.
  • Есть .gitignore, LICENSE, .editorconfig.
  • Скриншоты дашбордов Grafana, интерфейса Argo CD, уведомлений — в README или docs/.

Как это выглядит в резюме

Не «знаю Docker, Kubernetes, Terraform», а результат с деталями:

Shop API — от одного сервера до Kubernetes · [github.com/…]

  • Развернула сервис Flask + PostgreSQL в Kubernetes (k3s, 3 узла) через Helm и Argo CD; деплой — merge request в репозиторий конфигурации.
  • Описала инфраструктуру Yandex Cloud в Terraform (VPC в 2 зонах, ВМ, Object Storage для состояния) и настройку узлов ролями Ansible.
  • Построила пайплайн GitLab CI: тесты, сборка образа, сканирование Trivy и gitleaks, выкладка в staging автоматически и в prod вручную.
  • Настроила мониторинг Prometheus/Grafana/Loki с алертами в Telegram и runbook для каждого алерта.
